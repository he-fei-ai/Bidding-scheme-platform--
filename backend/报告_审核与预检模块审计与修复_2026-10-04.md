# 审核与预检模块 审计与修复报告（2026-10-04）

## 二、功能架构与现状分析

- **废标检查**：`run_rejection_check` 三维度（rejection/spelling/logic）并行，多投标文件 `Semaphore` 并发；废标维度默认三轮（范围分析→Markdown 初稿→严格 JSON 定稿），任一轮失败降级单轮，两轮共用 `_finalize_rejection_issues`（编号校验+证据原文核验+去重）。错别字维度按批次 AI + `verify_spelling_error` 原文定位，收尾对整文重新锚定；`apply_spelling_fixes` 只改已核验条目，可回写项目正文小节。终态按各维度失败情况给真实 `completed/failed`（不再无条件 completed）。
- **一致性审计**：`FACT_PATTERNS`（工期/金额/人员/资质/质量/安全）正则抽取，双轨制纳入全局事实基准（`global_facts_json`）；冲突判定走归一化去重 `_distinct_values`；`suggest_fixes` 优先以基准值为目标、回摘要、再回频率投票；`apply_autofix` 经 `text_patch` 带数字边界保护的真实落文，成功才标 resolved，并 `invalidate_content_caches` 三层缓存失效。
- **字数预检**：`word_count` 路由聚合 `list_sections`（word_count 由 `_count_words(content)` 派生），输出总量/覆盖率/达标-缺字-空章节分组、逐层级/逐状态分组、每章节进度。
- **鉴权与并发**：四条路由均已接入 `enforce_project_access` / `enforce_task_access`（IDOR 收口）；废标/查重用 `task_lock` 组锁互斥（先抢锁再建任务、后台 finally 释放、命中缓存当场放锁）。

## 四、修复项与优化项清单

### 修复 TD-1 / 优化 TD-3：`app/services/consistency_auditor.py`

- 抽出 `_collect_fact_instances(project_id) -> dict[str, list[dict]]`：只负责「读库 + 正则抽取」，返回 `{fact_name: [instance,...]}`，不写库不判冲突。
- 新增 `count_extracted_facts(project_id) -> int`：本次全量抽取的真实事实实例数。
- `detect_conflicts` 增加关键字可选参数 `all_facts`（默认 None 自行抽取，**向后兼容**既有 `detect_conflicts(pid)` 调用）。
- `run_full_audit`：全量抽取**只跑一次**，`facts_count = sum(len(instances))` 取本次真实抽取数，`detect_conflicts(project_id, all_facts=all_facts)` 复用同一份数据，删除原「累加历史 audit_log」的错误分支。

**关键函数/路径**：`ConsistencyAuditor._collect_fact_instances` / `count_extracted_facts` / `detect_conflicts` / `run_full_audit`。

### 新增配置项

无新增环境变量/配置项。行为变化仅在既有接口返回值口径（`facts_extracted` 由恒 0 修正为真实值），请求/响应结构不变，**完全向后兼容**。

## 六、遗留问题与后续建议

1. **TD-2（人员/技术类基准纳入）**：如需一致性审计以事实基准统一「人员数量」等，须先统一 `global_facts` 与正文正则的取值口径（当前有意隔离，避免误报），建议单独立项评估。

## 七、遗留问题处置（2026-10-04 后续执行）

按最优方案逐条处置上述三项，均以测试 + 基线对比验证。

### 7.1 TD-2 → 定位并修复真正的误报缺陷（人员事实按岗位分桶）

评估 TD-2 时**经实测发现一处结构性误报**（而非简单的基准覆盖不足）：
- 依据（探针实测）：`extract_facts_from_text("项目经理1人、技术人员20人、管理人员5人")` 旧行为
  → `[('人员数量','1'),('人员数量','20'),('人员数量','5')]`，`detect_conflicts` 遂报
  「人员数量存在 3 种不同表述：1、20、5」——**不同岗位各自独立、互不矛盾**，属假阳性
  （与 2026-09-29 修复的「安全标准」正则过宽同类）。
- 最优修复：`FACT_PATTERNS["人员数量"]` 捕获岗位词作前缀，`extract_facts_from_text` 按岗位拆分
  事实名（`项目经理数量`/`技术人员数量`/`管理人员数量`…），**只有同岗位数量不一致才判冲突**；
  裸「人员」（施工/作业/后勤等未列举岗位）仍归入通用「人员数量」，保留跨章比对。
- `FACT_BASELINE_CATEGORIES` **不**纳入 personnel：`test_only_comparable_categories_are_injected`
  钉死了「personnel 基线不得冒充正则抽取值」的既有决策，强行纳入会破坏数据链一致性，故保留
  该设计取舍，仅更新该测试的 fact_name 过滤为「项目经理数量」（原意不变）。

### 7.2 word_count `section_stats` 排序修正

- `app/routers/word_count.py` 抽出 `_section_sort_key`：分层「缺字章节(按缺口大→小) → 已达标 →
  无目标」，无目标章节不再与达标章节交错；层内以稳定排序保留原始层级顺序。

### 7.3 端到端 HTTP 层链路验证

- 新增 `TestAuditPrecheckHttpChain`（TestClient）：验证 `consistency` / `word-count` 路由确实挂在
  `/api/v1` 下、`run_audit` 透传真实 `facts_extracted`（≥2、非恒 0）、`conflicts/summary` 响应契约、
  跨项目越权 HTTP 层 403（锁定 IDOR 守卫已接入路由）。均为无 AI 依赖的确定性路径。

## 八、结论

本轮定位并修复了审核与预检模块中的两处缺陷：①一致性审计「提取事实数」恒 0（统计口径自引用累加）；②人员事实不分岗位的结构性误报（不同岗位人数被合并成一条「人员数量」冲突）。顺带消除了大项目重复扫描的性能债，修正了字数预检无目标章节与达标章节交错的排序问题，并以 TestClient 补齐了审核/预检路由的 HTTP 层链路验证。测试从 867 → **886 passed**（+19）、零回归，改动向后兼容，前后端数据链与调用链路贯通。
