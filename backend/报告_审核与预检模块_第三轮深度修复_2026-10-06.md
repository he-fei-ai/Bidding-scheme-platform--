## 2. 功能架构与现状分析（要点，均有代码依据）

### 2.1 一致性审计数据流

```
global_facts_json（已确认基准，category∈schedule/quality/safety）
  + projects.notes（摘要）
  + sections.content（逐章正文）
        │
        ▼ extract_facts_from_text（FACT_PATTERNS 6 类正则，人员按岗位分桶）
_collect_fact_instances → {fact_name: [{value, source, section_id}]}
        │
        ▼ detect_conflicts（_distinct_values 归一化去重 ≥2 种才判冲突）
Conflict[] → _save_conflicts（清旧未解决 + upsert，幂等）
        │
        ├─ suggest_fixes（基准 > 摘要 > 频率投票）→ 修复建议文案
        └─ apply_autofix（text_patch 数字边界保护 → 落文 → invalidate_content_caches）
```

### 2.2 废标/查重数据流

```
POST /start → enforce_project_access → 抢组锁 → create_task → BackgroundTasks._run_safely
   → run_rejection_check / run_duplicate_check（三轮 AI / bigram+Dice / 图像双指纹）
   → finally 释放组锁
GET /status/{id} ← 前端每 2s 轮询
GET /result/{id}
GET /export-report/{id} → docx/xlsx
```

### 2.3 字数预检数据流

```
GET /word-count/overview/{id}  → _load_sections（to_thread + readonly）→ 聚合
GET /word-count/sections/{id} → 同上 → 分层排序（缺字>达标>无目标）
PATCH .../sections/{id}/target-words → 设目标字数
```

### 2.4 现状（前两轮已治理）

- IDOR：四路由全部 `enforce_project_access` / `enforce_task_access`。
- 事件循环：只读端点 `readonly + asyncio.to_thread`，AST 门禁看守。
- 缓存：autofix 落文后 `invalidate_content_caches`（内存/Redis/build_tree 三层）。
- 错误处理：`except HTTPException: raise` 防止 403 被吞成 500。

## 4. 修复项清单（代码方案 / 文件路径 / 关键函数）

### 4.1 BUG-R3-1（P1）：「采纳建议并修复」正文污染

**根因链**：
1. 后端 `consistency_auditor.suggest_fixes` 返回一段**人类可读文案**：
   ```
   建议将以下内容统一为：450（已确认的全局事实基准）
   待修正取值：500
   ```
2. 前端 `ConsistencyPage.tsx` 第 423 行（修复前）：
   ```tsx
   newValue: suggestionModal.suggestion || "",   // ← 整段文案塞进输入框
   ```
3. 用户点"应用修复"→ `applyAutoFix(conflictId, projectId, 整段文案)`。
4. 后端 `apply_autofix` 把它当 `new_value`，用 `text_patch.replace_values`
   把正文里所有旧值（"500"）替换成**整段说明文字** —— 正文被污染。

**修复方案**：把"目标值"从文案里**结构化拆出**，双端透传。

- **后端** `services/consistency_auditor.py`：
  - 抽出 `_build_suggestion(values, sources) -> (target_value, text)` 类方法，同源推导。
  - `suggest_fixes()` 仍返回 `text`（**保持 str 契约，向后兼容既有 3 处断言**）。
  - 新增 `suggest_fix_target_value() -> str | None` 返回纯目标值。
  - 新增 `_load_suggestion_payload()` 共用读库逻辑。
- **后端** `routers/consistency.py::get_fix_suggestion`：响应新增 `target_value` 字段，
  `suggestion` 字段保留（向后兼容）。
- **前端** `api/index.ts::getFixSuggestion`：返回类型加 `target_value?: string | null`。
- **前端** `ConsistencyPage.tsx`：
  - `suggestionModal` state 加 `targetValue`。
  - 「采纳建议并修复」按钮 `newValue: suggestionModal.targetValue`（**纯值**），
    且 `disabled={!suggestionModal.targetValue}`（无纯目标值时不可点）。

**向后兼容**：`suggestion` 字段名/文案完全不变；新增 `target_value` 是可选字段，
旧前端忽略它不会报错。

### 4.2 BUG-R3-2（P2）：duplicate 轮询端点阻塞

- **后端** `routers/duplicate.py::get_status` / `get_result`：
  ```python
  # 修复前：task = duplicate.get_task(task_id)          # 同步直调写锁
  task = await asyncio.to_thread(duplicate.get_task, task_id)
  ```
- **门禁** `tests/test_async_blocking_gate.py::_HEAVY_REGISTRY`：
  补登 `("app.services.duplicate", "get_task")`，防止未来回退为同步直调。

   "新增 DB 读函数被 async 路由调用时必须登记或 to_thread"。

   这两个页面依赖文件上传、轮询、AI mock，搭建成本较高；建议后续按
   `ConsistencyPage.dom.test.tsx` 范式补"轮询状态机"和"误报标记交互"两个关键点。
3. **`rejection.list_all_schedules` 越权**：前两轮已加 `_require_admin()`，保持。
4. **`ai_config.py` 7 处棘轮存量**：与本模块无关，保持冻结。
5. **一致性人员/技术类纳入全局基准**：前两轮已论证有意不做，保持。

## 8. 结论

本轮在前后两轮（共 ~2400 测试通过）的稳固基线上，通过**真实 DOM 交互 + 行为层并发断言**
定位并修复了两个前两轮横向扫描遗漏的真问题：

- **P1 正文污染**：一致性「采纳建议并修复」把整段说明文案当替换值，会污染正文。
  修复方式是后端结构化下发 `target_value`、前端采纳纯值，双端透传，**向后兼容**。
- **P2 轮询阻塞**：`duplicate` 两个高频轮询端点同步直调写锁 DB，且 AST 门禁因
  `_HEAVY_REGISTRY` 漏登而未报警。修复方式是 to_thread + 补登门禁。

新增后端 4 例（含心跳推进量的决定性并发断言）+ 前端 4 例（含真实 DOM 交互下
`applyAutoFix` 实参断言）。全量回归 **后端 2504 passed / 0 failed，前端 77 passed**，
零回归。所有结论均有代码位置或测试结果支撑。
