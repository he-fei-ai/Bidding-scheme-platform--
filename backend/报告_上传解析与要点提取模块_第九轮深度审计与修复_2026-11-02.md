## 2. 架构现状要点（步骤 2）

- **并发防护**：`_get_upload_write_lock(project_id)` 项目级写锁只覆盖「查重→建任务→落盘」；文本提取（可耗时数秒~OCR）在锁外。`get_db()` 写锁（RLock）覆盖单个事务块，**docstring 明确禁止锁内磁盘 I/O**（会把持锁推过 `_db_write_lock_timeout=8s`）。
- **容错/降级**：提取失败/降级提示串判 failed；.txt 落盘失败降级 failed 并回写任务行；OCR 三引擎降级；PPT COM 超时兜底；PDF 提取线程超时护栏。
- **错误处理**：路由统一 `_upload_http_error` + `X-Error-Code` 头；AI 失败映射 502。
- **配置项**：`UPLOAD_MAX_FILE_SIZE_MB`、`PARSE_TASK_RETENTION`、`PARSE_TASK_STALE_MINUTES`。

## 4. 修复项清单与关键函数（步骤 4-5）

### B1 — 图片异步落库失败回滚物理文件
`app/services/files.py::_save_upload_image_async`（INSERT 失败 except 分支）
```python
except Exception as e:
    logger.error("图片上传落库失败: %s", e)
    # BUG-FIX 2026-11-02（B1 孤儿图片）：与 save_upload 同步路径同口径回滚
    try:
        _orphan = Path(file_path)
        if _orphan.exists():
            _orphan.unlink()
    except Exception as _ce:
        logger.warning("清理孤儿图片文件失败 %s: %s", file_path, _ce)
    _update_parse_task(project_id, "failed", 0, f"保存文件记录失败: {e}", filename)
    return {"status": "failed", ...}
```

### B2 — INSERT 前内容复核 + 后到者回滚
- 新增辅助 `app/services/files.py::_discard_parse_task(project_id, filename)`：删除后到者刚创建的 `processing` 任务行（精确匹配 project+filename+processing），保证「duplicate 不留 processing 残留」不变式。
- `save_upload` 在 `uploaded_files` INSERT 前补一次 `_find_duplicate_upload` 复核（**在写锁外**执行，遵守锁内禁 I/O）；命中非 failed 同内容行即判后到者：回滚 `file_path`/`text_path`、删任务行、返回 `duplicate`（返回结构与既有 duplicate 分支完全同口径）。

### B3 — 自愈删除旧行物理文件 + 复用原名
`save_upload` 去重命中 `status=='failed'` 分支：删除旧行前先 `SELECT extracted_text_path`，删行后 `for _orphan in (_dup_path, _dup_text_path): unlink()`。因命中行按内容哈希匹配、其 `path` 正是同内容旧文件，删除后同名重传可复用原名（不再触发 `file_path.exists()` 改名 `_1`），且清理旧提取文本孤儿。整段处于项目写锁内，删除与落盘原子。

### B5 — 任务状态默认值收敛
`app/db_migrations.py` file_parse_tasks DDL：`status TEXT NOT NULL DEFAULT 'queued'` → `DEFAULT 'processing'`，附缺陷说明注释。仅对新建库生效，存量库无行为变更；`reclaim_stale_parse_state` 可正常回收「漏写落到默认值」的行。

## 7. 遗留问题与后续建议

1. **B2 残余竞态（诚实记账）**：本修复把击穿窗口从「整段提取时长」收敛到「复核与对方提交几乎同刻」的极窄窗口；无 `content_hash` 列时无法在写锁内做纯 DB 判重彻底消除。**永久修复**：给 `uploaded_files` 增**附加式** `content_hash` 列（NULL 兼容存量行 + 索引），`_find_duplicate_upload` 改为 `WHERE project_id=? AND content_hash=?` 等值查——既能在锁内安全判重（无磁盘 I/O）、又移除现有全项目文件扫描、顺带提速去重。属可加列的低风险迁移（区别于 B4 的侵入式 rewire）。
2. **B4 `file_parse_tasks.file_id`**：加 `file_id` 列并把 `_update/_force/_discard_parse_task` 由 filename 匹配改为 file_id 精确匹配，根除同名串写。需配套迁移 + 全调用点 rewire，建议独立一轮处理。
3. **前端组件级交互测试**：本轮后端修复未改前端可见契约，`FileUploadPage` 现有 5 套 vitest 仍适用。可另行补「duplicate（并发后到者）」与「同名自愈重传」两条前端交互断言，进一步固化前后端同步。
4. 技术债观察：`files.py` 已 2460 行，`save_upload` 单函数职责偏重（命名/落盘/提取/落库/去重/回滚）——建议下一轮按「提取管线 / 去重与自愈 / 落库与回滚」抽子模块，降低单函数认知负载。
