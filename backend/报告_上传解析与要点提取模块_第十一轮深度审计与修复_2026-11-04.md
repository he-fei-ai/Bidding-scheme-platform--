## 3. 现状分析（架构与实现）

### 3.1 上传链路（已高度加固）
`save_upload`（files.py:772）当前流程：内容 SHA-256 → `_get_upload_write_lock` 内 `_find_duplicate_upload`（content_hash 等值优先，R1）→ failed 命中自愈（删旧行+孤儿文件，B3）→ `_create_parse_task`（返回 task_id，B4）→ 落盘（同名加 `_1` 后缀）→ 图片走 `_save_upload_image_async`、其余走同步提取 `_persist_file_extraction`。**锁内只做 DB 等值判重、零磁盘 I/O**，符合写锁临界区约定。

### 3.2 要点提取数据链（完整）
上传 → `latest_extracted_text`（合并主文件 + 辅助 200 行摘要，`_text_cache` 版本化）→ `routers/ai.py` 的 summary/scoring/boq/work-interface/construction-method/scheme-extraction/facts 全部消费同一份 `full_text`；空文本返回 400「请先上传文件」，与前端 `checkReadyForExtraction` 门禁同口径。

### 3.3 格式识别（单一真相）
`SUPPORTED_EXTENSIONS`（files.py:52）是唯一真相，`routers/files.py:28 ALLOWED_EXTENSIONS` 由它派生；`_sniff_extension` 按魔数兜底 %PDF / ZIP（docx/xlsx/pptx）/ OLE2；`.wps` 走 OLE2 降级链（Gap-6）。

### 3.4 错误处理（分级回填）
- 空文本 → `EMPTY_TEXT_MESSAGE` 提示，status=success（与既有契约一致）。
- 降级提示串（`is_extraction_notice`）→ status=failed。
- 写盘失败 → status=failed + `text_preserved`（F-G）。
- 解析质量 error（控制字符/替换符/大文件近空）→ `_parse_quality_error_message` 回填（R9）。

### 3.5 任务行状态端点（`routers/tasks.py:306`）
聚合 `processing` / 近 5 分钟 `recent_completed` / `recent_failed`，`asyncio.to_thread` 移出事件循环（2026-10-12 修复），`readonly` 连接不抢写锁。

### 3.6 测试方式（现状）
后端服务级 + TestClient 端点级；前端纯函数（utils）+ 组件 DOM 交互（antd 真实渲染，仅 mock API 层）。`vitest.config.ts` 用 `singleFork` + `testTimeout: 300000` 消除 antd/jsdom 冷启动 flaky。
