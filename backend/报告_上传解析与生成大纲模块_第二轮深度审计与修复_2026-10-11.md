## 四、修复项清单（含代码依据）

### 4.1 L3 脏标题判定缺口（用户主诉根因）

**根因定位（4 类漏网形态，探针实测确认）**：

1. **半角括号** `总体实施策划(2)` —— 原 `_ORDINAL_SUFFIX_RE = r"（\s*第?\s*[0-9一二三四五六七八九十百]+\s*项?\s*）\s*$"` 只认全角括号 → 判脏漏判 + 归一化剥离漏剥 → 与 `总体实施策划` 双双保留。
2. **裸数字结尾** `总体实施策划2` —— 代码库自己的 `_uniquify_outline_titles` 裸数字回退 `f"{new_title}{_cnt}"`（原 :1286-1289）正是这么产出的，形成自我污染源。
3. **`总体实施策划（其3）`** —— `_disambiguate_title` 极端兜底产物；**决策：视为合法**（模块既有设计，可读性优于裸编号），不判脏、不剥离。
4. **顺序缺陷**：v51 质量收口为「去重 → 清洗」，去重归一化时把末尾 `（2）` 剥离后判定碰撞、给原标题追加维度词 → 得到 `总体实施策划（2）专项方案`，裸编号从末尾移到中间，而 `_cleanup_placeholder_titles` 依赖末尾匹配 → 脏标题静默漏出。

**修复（`outline_common.py`）**：

| 位置 | 改动 |
|---|---|
| `_ORDINAL_SUFFIX_RE` | → `r"[（(]\s*第?\s*[0-9一二三四五六七八九十百]+\s*项?\s*[）)]\s*$"`（兼容半角，不含「其」，附设计决策注释） |
| 新增 `_BARE_NUM_TAIL_RE` | `r"[0-9]{1,4}(?![0-9A-Za-z%％\u4e00-\u9fff])\s*$"` —— 排除数字/字母单位、百分比、任意 CJK 量词，故 `工期365天`、`2026年施工组织计划`、`25mm` 均不误伤 |
| `_is_dirty_l3_title` | 新增裸数字判定但**收窄**：仅当去掉尾部数字后主体 ∈ `(_GENERIC_ONLY_TITLES \| _L3_L2LIKE_TITLES)` 才判脏（避免误伤 `工序交接流程5`、`危大工程3类`） |
| `_strip_ordinal_suffix` | 现可剥半角括号编号；**刻意不剥裸数字**（否则 `_uniquify_outline_titles` 的 `while _core(f"{new_title}{_cnt}") in seen` 对任意 `_cnt` 都得到同一 core → 必然死循环，历史事故） |
| `_semantic_fallback_title` Step 4 | 裸数字 while 循环 → 「维度词 × 中文序数（之一…之十）」全组合 + `第N条` 绝对兜底 |
| `_uniquify_outline_titles` 回退 | `f"{new_title}（其{_cnt}）"`（`（其N）` 不被剥离，故无死循环） |
| `_disambiguate_title` 开头 | 防御性归一化：`_strip_ordinal_suffix` + 收窄后的裸数字剥离 |

**修复（`workflows_outline_v51.py`）**：

- 两处质量收口顺序改为**清洗 → 去重**（原约 :5271-5272、:5293-5294），附完整根因注释；:4169-4178 原本顺序正确，未动。
- `_generate_differentiated_l3_title`：`f"{core}专项{n}"` / `f"{core}实施要点"` 生产者 → `_semantic_fallback_title`；移除已废弃的 `_extract_title_core` 导入。

**根因修复前后对比（探针实测）**：

```
修复前：['总体实施策划（2）专项方案', '总体实施策划(2)专项方案（其2）', '总体实施策划（第6项）专项方案']
修复后：['总体实施策划补充措施',     '总体实施策划实施方案',     '总体实施策划保障措施']
```

**判定精度验证**：16 脏例 / 26 合法例判定全对；60 个 `总体实施策划` 重复 → 60 个唯一、清洗后 0 脏标题；8 个混合形态 → 8 个唯一、0 脏标题、无死循环。

### 4.2 O-5（P0）：`repair_l3_generic_titles` L4+ 漏修

**位置**：`services/ai/workflows_outline_utils.py:994-1063`（原 :994-1072）

**根因**：`repair_tasks` 构造循环硬编码 `if len(parts) != 3: continue`，且 `_repair_one` 用 `repaired[i]["children"][j]["children"][k]["title"]` 三层下标直写。`validate_l3_specificity._check_l3` 会递归进 L3 子节点，一旦深层节点带 `level=3` 显式标记（AI 直出路径常见），warning 的 path 就是 `"1.2.3.4"` 这类 4 段路径 → 被 `continue` 静默跳过，AI 自检报出问题、日志显示「已修复」，实际脏标题原样保留。

**修复**：

1. 新增模块级助手 `_locate_by_path(tree, path, ancestors=None)`：按 1-based 点分路径递归定位，返回 `(node, parent_title, ancestor_titles)`，支持任意深度，路径非法/越界返回 `(None, "", [])`。
2. `repair_tasks` 元素改为 `(path, node, title, parent_title, ancestors)`；`_repair_one` 内 `l1_title = ancestors[0]`、`l2_title = parent_title`，写入改为 `node["title"] = new_title`（`repaired` 是 deepcopy，持引用直改安全）。

**调试收获（避免误修的教训）**：初版 `_locate_by_path` 迭代实现里 ancestors 累积逻辑把「直接父节点」错误纳入返回的 ancestors 链，导致 `l1_title` 取到空字符串，AI 生成时上下文缺失 → 探针 `provider.calls == 1` 通过但修复标题质量骤降。改为递归版本后 ancestors 语义清晰：完整祖先链，最外层 L1 在前。

### 4.3 I-6（P0）：Excel/PPTX 错误串识别

**位置**：`services/files.py:320-390`

**根因**：Excel/PPTX 分支的降级返回值是 f-string 动态拼接（`f"[Excel 解析错误] {e}"`），无法纳入 frozenset 精确登记 → `is_extraction_notice` 返回 `False` → save_upload / Celery parse_and_extract_file / latest_extracted_text 全部按「提取成功」处理。

**修复策略**：登记表仍只收完整常量串，动态串单独走**前缀匹配 + 长度上界**双重防御：

```python
EXTRACT_ERROR_PREFIXES: frozenset[str] = frozenset({
    "[Excel 解析错误]",
    "[Excel 文件损坏]",
    "[Excel 文件不存在]",
    "[Excel 权限不足]",
    "[PPTX 解析错误]",
})
EXTRACT_ERROR_MAX_LEN = 120  # 错误串 = 前缀 + str(e)，正常不超过这个量级
```

前缀后必须紧跟空白 / 冒号 / 字符串结尾，避免 `[Excel 解析错误] xxx真实正文` 这类伪造输入被误判。前缀两两不互相前缀由 `test_each_prefix_is_registered_with_distinct_body` 守卫。

**测试补充**：新增 `test_registry_no_drift_with_error_prefix_literals` 正则扫描 `files.py` 源码里所有 `return f"[Excel|PPTX ...] {e}"` 字面量，防止后续新增前缀未登记。

### 4.4 I-8（P1）：异步解析任务空文本跳过

### 4.6 O-6（P0）：`_save_nodes.status` 与 UPDATE 同源

**位置**：`routers/sse/sse_db_ops.py:703-779`

**修复**：抽出 `_node_status` 变量，UPDATE 写入 DB 与 `saved_node["status"]` 共用同一份：

```python
_node_status = "pending"
```

## 十、后续修复：O-7（P1）V5.1 分阶段审核窗口层级防护（2026-10-11 追加）

### 10.1 缺陷根因

`resume_v51_task`（`backend/app/services/v51_state.py:108-155`）此前**无条件接受任意 `edited_outline`**，不校验 outline 深度是否符合 `state.current_phase`：

```python
if edited_outline is not None:
    state.edited_outline = edited_outline  # ← 无条件写入
```

工作流在 `_wait_for_v51_review` 拿到 `edited` 后：
- `level1` 阶段审核 → 调用 `_generate_level2_v51(level1=edited, ...)`；
- `_generate_level2_v51` 内 `_build_level2_skeleton`（`workflows_outline_v51.py:2107`）按 `l1_node["title"]` **完全重建 L2+L3 骨架**，忽略 `l1_node["children"]`。

**后果**：用户在 L1 审核窗口若提交了 L3 完整树（如从浏览器工具改 payload，或前端刷新后缓存了旧 outline 直接提交），用户精心编辑的 L2/L3 被静默丢弃，AI 重新生成一套骨架覆盖之，且没有任何错误提示 —— 数据安全级问题。

### 10.2 修复方案

在 `resume_v51_task` 加「phase → 允许 outline 深度区间」校验，拒绝写入 `state.edited_outline`；路由层按 `_last_reject_reason` 区分 HTTP 状态码。

**修改点**：

| 文件 | 改动 |
|---|---|
| `backend/app/services/v51_state.py` | 新增 `_V51_PHASE_ALLOWED_DEPTH` 常量（`level1: [1,1]`、`level2: [1,2]`、`level3: [1,3]`、`final: [0,∞]`，未知 phase 兜底放行）；新增 `_outline_max_depth(outline)` 递归计算深度；`V51TaskState.__init__` 加 `_last_reject_reason` 字段；`resume_v51_task` 在写入 `edited_outline` 前校验深度，非法时拒写并置 `_last_reject_reason="depth_mismatch"`；`invalid_outline`（非 list）单独区分；成功后清空 `_last_reject_reason`；新增 `get_v51_last_reject_reason(project_id)` 和 `get_v51_phase(project_id)` 查询函数 |
| `backend/app/routers/sections.py` | `v51_confirm_route` 在 `resume_v51_task` 失败分支按 `reason` 分流：`depth_mismatch`/`invalid_outline` → `400 Bad Request` + 可操作 detail（含 phase 允许范围和实际深度）；`version_conflict`/其他 → `409 Conflict`（保持旧行为） |
| `backend/tests/test_regression_2026_10_11.py` | 新增 `TestO7ResumePhaseDepthValidation` 类，共 13 个用例：`_outline_max_depth` 边界（空/非 list/纯 dict/多层/空 children）+ 各 phase 正例反例（L1↔L1、L1↔L3、L2↔L2、L2↔L3、L3↔L3、final 无上限）+ 兼容性（`edited_outline=None` 保持旧行为）+ 错误路径（非 list 400、版本冲突 409、成功清空残留 reason、状态不存在 404）+ 路由源码守卫（`depth_mismatch`/`invalid_outline`/`409` 三分支齐全） |

### 10.3 关键设计决策

1. **未知 phase 走宽松兜底**（放行）而非拒绝：避免历史持久化状态或迁移后 phase 值未同步导致误伤。
2. **拒绝时不写入 `edited_outline`**：而非「写入但标记」—— 下游若读取 `edited_outline` 就一定会用到，标记方案需要修改所有下游读取点。
3. **保留 `edited_outline=None` 语义**：不触发深度校验，纯确认不编辑的老路径完全不变。
4. **HTTP 状态码细分**：409 是并发冲突（可重试），400 是请求错误（用户输入问题），语义正确映射，前端可给出精准提示。
5. **未知 phase 的拒绝原因**：`_phase_allows_depth` 对未知 phase 返回 True（放行），因此不会误报 `depth_mismatch`。

### 11.1 修复项概览

### 11.2 修改点详解

#### I-11：`_strip_invisible` 完整剥除不可见字符

**根因**：旧实现只剥首字符 `\ufeff` 和全部 `\x00`，中后段出现的 BOM（多次追加拼接导致）、零宽字符（`\u200b` / `\ufeff`）和 C0/C1 控制字符均未被清除。

**修复**：用正则一次遍历剥除全部不可见字符：
- BOM（所有出现位置）
- NUL
- 零宽字符（`\u200b` / `\u200c` / `\u200d` / `\ufe0e` / `\ufe0f`）
- 行/段分隔符（`\u2028` / `\u2029`）
- C0 控制字符（保留 `\t` `\n` `\r`）
- DEL + C1 控制字符

#### I-12：`_read_text_auto` 支持 UTF-16LE 无 BOM

**根因**：无 BOM 的 UTF-16LE 此前走 utf-8 → gb18030 → 兜底替换，中文内容全部变成乱码。部分系统导出的 xlsx 说明文本、Windows Notepad 另存为「Unicode」时的中间态属于此类。

**修复**：增加 BOM 探测失败后的奇偶零字节启发式检测：
- 采样前 512 字节
- 若 0x00 字节占比 > 30%，判断 LE/BE（比较奇数位和偶数位的 0x00 数量）
- 尝试 UTF-16LE/BE 解码

#### P-3：`_create_parse_task` 失败改为 raise

**根因**：旧实现仅 warning 后 return，导致任务行缺失、状态端点无解析痕迹、前端进度条永远卡在 processing。

**修复**：
1. `_create_parse_task` 改为 `raise`（而非 return）
2. 两个调用方（`save_upload` 和 `re_extract`）包裹 `try/except`，捕获异常后返回失败响应
3. 日志级别从 `warning` 提升为 `error`

#### I-10：`latest_extracted_text` 竞态窗口加版本号

**根因**：并发上传/删除时，`latest_extracted_text` 可能在 DB 查询和文件读取之间读到中间态，最终写入陈旧缓存覆写已清空的缓存。

**修复**：引入项目版本号机制：
- 新增 `_project_versions: dict[int, int]`
- `_text_cache_clear` 时递增版本号
- `_text_cache_set` 接受 `since_version` 参数，若版本已变更则跳过写入
- `latest_extracted_text` 在读取开始时记录版本号，写入时传入检查

#### O-8：`l3_filled` 语义漂移分离

**根因**：旧实现把「差异化修正数」（`diff_fixed`）和「占位清洗数」（`cleaned`）累加进 `l3_filled`，导致日志输出「已填充 X > Y（共 Y 个）」的语义漂移。

**修复**：新增 `l3_repaired` 计数器，`l3_filled` 仅记录原始填充数。进度回调消息更新为「共修复 N」。

#### O-9：`_cleanup_placeholder_titles._collect` 包含 L1 自身

**根因**：旧实现只收集 L1 的 children（L2+），遗漏 L1 自身标题。清洗后的 L3 标题可能与同项目 L1 标题撞名。

**修复**：在 `_collect` 之前先遍历 L1 自身，将 L1 标题加入 `_used` 集合。

### 11.3 关键设计决策

1. **I-11 正则范围**：保留 `\t`（tab）、`\n`（换行）、`\r`（回车）三个合法空白字符，其余 C0/C1 控制字符一律剥除。
2. **I-12 启发式阈值**：0x00 字节占比 > 30% 才尝试 UTF-16 解码，避免误判普通文本。
3. **P-3 异常传播**：`_create_parse_task` 改为 `raise`，但调用方包裹 `try/except` 返回失败响应，保证 API 契约不变（返回 dict 而非抛异常）。
4. **I-10 版本号机制**：版本号在 `_text_cache_clear` 时递增，`_text_cache_set` 在写入前检查版本是否变更。版本不变时正常写入，版本变更时跳过写入（避免陈旧数据覆写）。
5. **O-8 计数器分离**：`l3_filled` 仅记录原始填充数，`l3_repaired` 记录后处理修复数，语义清晰。
6. **O-9 L1 收集**：在 `_collect` 之前先遍历 L1 自身，将 L1 标题加入 `_used` 集合，避免清洗后的 L3 与 L1 撞名。

### 12.2 修改点详解

#### O-10：去重 `_uniquify/_cleanup_placeholder_titles` 双次调用

**根因**：`_generate_level3_v51` 内部调用 `_cleanup_placeholder_titles` + `_uniquify_outline_titles`（4183/4191 行），但 `generate_outline_v51` 在 `_ensure_min_children` / `_tech_enhance_titles` 之后又会调用一次（5292/5293 行）。由于 `_ensure_min_children` 和 `_tech_enhance_titles` 可能引入新的占位标题或修改标题，外部的清洗+去重调用是必需的，而此处的内部调用是冗余的（会被外部调用覆盖）。

**修复**：
1. 移除 `_generate_level3_v51` 内部的 `_cleanup_placeholder_titles` + `_uniquify_outline_titles` 调用
2. 移除 `l3_repaired` 中的占位清洗计数（仅保留差异化修正数）
3. 更新进度回调消息为「占位清洗和去重由后续统一处理」
4. 在 retry 路径（`_generate_level3_v51` 之后）添加清洗+去重调用，与主路径保持一致

#### O-11：删除 `_renumber_items` 死代码

**根因**：`_renumber_items` 在 `workflows_outline_utils.py` 中定义，但**没有任何生产调用方**（零生产调用方），落库目录树从不携带 `number` 字段。这是三份路径式编号实现中的死代码。

**修复**：
1. 从 `workflows_outline_utils.py` 删除 `_renumber_items` 函数
2. 更新 `test_outline_hardening_2026_10_08.py`：移除生产代码导入，添加本地副本以保留测试覆盖

#### O-12：后端 `get_section_path` 标记为唯一权威实现

**根因**：`get_section_path`（`sections.py:1014`）与前端 `collectHeadingPaths`（`utils.ts:161-195`）为独立实现，审核态可能显示不同编号。

**修复**：在 `get_section_path` 的 docstring 中标记为后端路径式编号的**唯一权威实现**，并注释前端实现对齐需求。

#### P-2：`auto_confirm` 改为配置项

**根因**：`sse_outline.py` 硬编码 `auto_confirm=True`，多阶段人工审核闸门不可达。用户无法选择「分阶段审核」模式。

**修复**：
1. 在 `config.py` 新增 `OUTLINE_AUTO_CONFIRM` 配置项（默认 `True`，保持向后兼容）
2. `sse_outline.py` 两处 `auto_confirm=True` 改为 `auto_confirm=OUTLINE_AUTO_CONFIRM`
3. 用户可通过环境变量 `OUTLINE_AUTO_CONFIRM=false` 启用多阶段人工审核

### 12.3 关键设计决策

1. **O-10 移除内部调用**：`_generate_level3_v51` 内部调用是冗余的，因为 `generate_outline_v51` 在 `_ensure_min_children` / `_tech_enhance_titles` 之后会再次调用清洗+去重。移除内部调用可避免重复遍历和重复修复。
2. **O-11 删除死代码**：`_renumber_items` 零生产调用方，删除可减少维护负担和编号口径漂移风险。测试文件保留本地副本以验证编号逻辑。
3. **O-12 标记而非修改**：前端实现对齐需要 Node 环境，本轮仅在后端标记唯一权威实现，前端对齐留待后续。
4. **P-2 配置项默认 True**：保持向后兼容，生产环境行为不变。用户可通过环境变量启用多阶段审核。
