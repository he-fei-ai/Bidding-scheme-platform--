## 三、深度探索关键发现

1. **版本控制/回滚已具备且正确**：`prompt_versions` 表 + `routers/prompts.py::rollback_prompt`/`list_prompt_versions`/`get_prompt_version`，编辑/重置/回滚均归档旧内容，每 key 保留 ≤50 版本（L94-120、L314-367）。`_validate_prompt_content`（L54）校验 `{shared:NAME}` 引用有效性、禁止静默删除默认变量（`force=true` 可跳过）。
2. **模板校验已具备**：同上。
3. **占位符覆盖完整（核心结论，本轮用 AST 静态审计 + 人工复核双验证）**：
   - 每个注册提示词的 `__X__`/`{var}` 变量，均在至少一个注入点被实际提供——**零真实缺口**。
   - 5 个易被误判为"缺口"的 KEY（`L3_TITLE_REPAIR_PROMPT`/`OUTLINE_REVIEW_*`/`SCORING_REVIEW_*`）实际经 `render_prompt(template_var, **kwargs)` 或 `_fill_template(..., labels=)` 完整注入（见 `workflows_outline_utils.py:854`、`workflows_quality.py:563`、`workflows_analysis.py:103/148`）。
   - 用户强调的「解析提取结果/全局事实/目录树/图表指令/专项方案名称」注入情况：
     - 解析结果：`CONTEXT`/`SUMMARY` 经分析链路注入；
     - 全局事实：`build_chapter_content_messages` 以「事实变量:」消息注入（L727-737，按章节相关性筛选 + 2000 字上限）；
     - 目录树：`CONTENT_ORCHESTRATION_USER` 的 `__OUTLINE__` 注入 leaf_json；正文生成以「上级/同级章节」消息注入承接关系（L739-761）；
     - 图表指令：正文生成以「正文编排决策」消息注入（L808-834），与 `CONTENT_SECTION_SYSTEM` 的配图铁律呼应；
     - 专项方案名称：`chapter_title_templates.json`（28 个顶层专项方案类别，含 level2/level3 数百条章节标题子项）由 `workflows_base._get_chapter_templates` 消费，目录生成阶段注入。
4. **渲染器分裂（R5，技术债）**：同一平台存在 4 套变量注入机制：
   - `render_prompt`（统一、单遍、共享解析、`sanitize/desensitize` opt-in）—— 规范形态；
   - `_fill_template`（`workflows_base.py`，单遍但**不解析 `{shared:}`、不脱敏**）—— 审核链路；
   - `_render_orch_user`（`workflows_orchestration.py`，**手写 `.replace`/`.format`**）—— 编排链路；
   - `_render_arrange_sys` → `get_prompt(key, **kwargs)`（已用统一渲染器）—— 图表链路。
   手写 `.replace` 链路存在跨变量二次替换的潜在注入面，且与全平台口径不一致。

## 五、增强优化清单（本轮新增）

- **统一编排渲染器**：`_render_orch_user` 由手写 `.replace`/`.format` 收编到 `render_prompt`，一次传入 v2（`__OUTLINE__` 风格）与历史（`{leaf_list_json}` 风格）所需的全部变量名，兼容两种占位符风格、单遍替换消除跨变量注入面，并保留「模板未含项目概述时兜底补一段」的质量防御。
- **`_fill_template` 解析共享规则**：在渲染前先 `_resolve_shared(template)`，使审核类模板未来引用 `{shared:NAME}` 时与统一渲染器口径一致，不再残留字面量。
- **占位符覆盖静态护栏（新增测试）**：`test_prompt_placeholder_coverage_complete` 用 AST 扫描全部注入点，断言每个注册提示词的模板变量都被实际提供，固化「上下文完整注入」要求，防止回归。

## 八、遗留问题与后续建议（处置状态）

1. **渲染器分裂未彻底消除** → **【本轮已处置·降级为有意设计】** 经评估，`_fill_template` 的「首现=数据/后续=标签」语义是有意的 token 控制设计，强行并入 `render_prompt` 会污染通用路径或破坏评审提示词体积控制；故保留为 `render_prompt` 之外的**必要例外**，并在函数头注释明确其边界，同时补齐与 `render_prompt` 一致的安全能力（`sanitize`/`desensitize` opt-in，对每个数据值处理）。至此渲染器分裂已从「技术债/不一致」降级为「清晰边界 + 安全对齐」。
2. **`_fill_template` 未默认脱敏** → **【本轮已处置】** 已补齐 `sanitize`/`desensitize` opt-in 开关（默认关、向后兼容），并在审核链路 `_build_outline_review_texts` 开启 `sanitize=True`（注入评分点/目录/概述等外部衍生数据，与全平台高注入风险链路口径对齐、纵深防御）。
3. **正文生成链路未接 `assemble_prompt_context`** → **【维持前批决策】** 精细分段消息拼装是为保前缀缓存收益的有意选择，且经核验完整注入；`build_prompt_with_context` 已就绪备用，不强行改动。
4. **端到端实机验证** → **【环境受限·声明】** 本机无 Node 运行时、无可用 AI Key（见项目记忆 `env_no_node_runtime`），无法跑通整链 HTTP 实机；结论基于代码级静态审计 + 单元/集成测试，跨模块不回归已由 `test_chart_fence_pipeline.py` 等验证。
5. **`chapter_title_templates.json` 规模校验** → **【本轮已处置】** 新增 `tests/test_chapter_title_templates.py`（3 用例）捕捉该数据源静默降级（文件损坏/缺失时模块仅 warning 回退空 dict，原无显式护栏）。注：实际顶层专项方案类别为 **28 个**（前文 324+ 为误记，应为 level2/level3 子项累加），已同步更正。

### 9.4 结论

- 渲染器分裂：从「技术债/不一致」降级为「清晰边界 + 安全能力对齐」——`_fill_template` 因差异化语义保留，但安全口径已与 `render_prompt` 完全一致；`_render_orch_user` 已并入 `render_prompt`。
- 审核链路：外部衍生数据注入已纳入 `sanitize=True` 纵深防御，与全平台高注入风险链路一致。
- 数据源护栏：`chapter_title_templates.json` 静默降级被显式测试捕捉。
- 所有改动**零行为回归**（默认关开关、参数化默认值），并已补回归测试 + 跑通。
- 仍不适用项：端到端实机验证（环境无 Node/AI Key）、正文生成链路接入 `assemble_prompt_context`（维持前缀缓存决策）。
