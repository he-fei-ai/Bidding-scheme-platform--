## 2. 重点实施说明

### 2.1 P-22 正文提示词分层多消息（最关键的结构改造）

**问题**：旧实现把 system 约束、项目摘要、事实变量、评分点、章节任务全部拼进**单条 user message**，且用 `messages[0].content += ...` **条件性**追加约束（取决于该章节有无编排决策）—— 有编排的章节与无编排的章节 system 前缀不同，直接破坏前缀缓存。

**新结构**（对齐易标规格四.4 / 九「稳定前置、任务差异后置」）：

```
[0] system              —— 恒定，跨章节完全一致（缓存命中区间起点）
[1] 项目稳定上下文       —— 项目摘要 / 承包范围 / 工程作法原文
[2] 事实变量             —— 按章节相关性排序（故与 [1] 分开）
[3] 上级章节             —— 承接关系
[4] 同级章节             —— 避免重复
[5] 当前章节任务         —— 标题/概要/评分要点/目标字数/编排决策（唯一变化）
```

**缓存收益**：同项目同事实集下，`[0]+[1]` 命中前缀缓存；`[2]…[5]` 随章节变化。这是易标规格九主张的核心收益，旧实现因 system 漂移完全无法获得。

**验证**：`_tmp_p22.py` 断言 5 条消息、SYSTEM 恒定、无 `messages[0].content +=` 残留，通过。

### 2.3 P-9 已有方案 vs 无方案差异化流程

**问题**：平台此前对「招标文件已载明工程作法」与「完全无方案」两种情形走同一套正文生成逻辑，导致已有方案的项目被 AI 另起炉灶提出冲突工艺。

**实施**：
1. `sse_utils._fetch_project_data_async` 的 SELECT 增加 `construction_method_json`，结果字典增加 `construction_method` 键
2. `sse_content` 提取并透传到 `_run_sections`（主生成 + 重试两处）
3. `generate_sections` 的 `kw_to_ctx` 增加映射
4. `build_chapter_content_messages` 分支：
   - **有原文** → 稳定上下文注入「工程作法（原文摘录）」+ 任务指令要求「承接并细化原文已有工艺，不提出冲突替代方案，原文未覆盖处方可补充」
   - **无原文** → 任务指令要求「自行拟定完整技术方案，明确工艺选择依据与评分响应关系」

**验证**：`_tmp_p9.py` 断言 4 种场景（有方案/无方案/空数组/超长截断）+ system 前缀恒定 + 透传链完整，全部通过。

### 2.7 P-23 缓存命中率监控

**问题**：平台缓存**只有读路径、没有计量** —— 正文/图片/导出各自维护局部 `_hits`/`_misses` 变量，Anthropic prompt cache（`cache_control`）用量完全未采集。运营侧无法回答「分层提示词改造后命中率多少」「命中率低是否说明分层没生效」。

**实施**：新增 `services/ai/cache_metrics.py`（线程安全，零依赖零 IO）：
- `record_store(name, hit, size)` —— 各缓存组件命中/未命中
- `record_prompt_cache(usage)` —— 从 AI 响应 `usage` 采集 `cache_creation_input_tokens` / `cache_read_input_tokens`；非 Anthropic 端点无 cache 字段时不计数（避免稀释命中率）
- `snapshot()` —— 返回含命中率的分层快照
- `reset()` —— 测试用

**埋点**：
- `_do_generate_section_with_optimizations`：正文缓存命中/未命中（`use_cache=False` 的探针不计入）
- 响应解析处采集 prompt cache token 用量

**API**：`GET /api/v1/ai/cache-metrics`

**命中率口径**：`cache_read / (cache_read + cache_creation)` —— 即「本次输入有多少是从缓存里读出来的」。

**验证**：`_tmp_p23.py` 断言 section_content 66.7%、image 33.3%、prompt_cache 60.0%、requests_with_cache=2，全部通过。
