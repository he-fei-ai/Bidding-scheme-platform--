## 2. 文件信息提取

### 2.1 文档→Markdown（纯机械，无 AI）
- **Word**：`docx2python`（本软件对应用 python-docx/docx2python）。DOCX 三阶段：`mammoth→HTML→cleanHtml(cheerio)→preserveTables(占位)→turndown→restoreTables(保留原始 HTML 表)`。
- **PDF**：`pdfplumber`（表格感知）+ 双引擎：`pdf-parse getTable` + `pdfjs-dist` 自建矢量线表格重建（并查集 + 网格聚类）。
- **表格标记**：`[表格内容]/[表格结束]`（`全功能模块.txt`）。
- **图片剥离**：技术方案/废标/知识默认 `preserveImages=false`；查重用 `true`。
- **格式探测**：魔数（magic-number）判类型；3 provider：local / mineru-accurate-api / mineru-agent-api。

### 2.2 AI 提取项目概述与技术评分要求（STEP02）
- `bidAnalysisTask.cjs`：18 项逐项 AI 提取；**缓存预热**：`projectOverview` 先跑 → 等待 5s（`PROMPT_CACHE_WARMUP_DELAY_MS=5000`）→ `Promise.all` 其余（共享稳定前缀命中缓存）。
- **多标段规则检测** `bidSectionDetector` + AI 提取。
- **分段合并** `segmentedAiResultMerger.cjs`：多分段 AI 结果合并为单一结论。
- **聚合下游** `formatBidAnalysisFactsForPrompt`：把"项目信息 + 甲方信息 + 交货和服务"聚合成一段事实文本供 STEP03/05 使用。

### 2.3 知识条目提取（知识库，非 RAG，两轮 + 补漏）
`knowledgeBaseService.cjs`：
- **第一轮** `buildFirstRoundItemsMessage`：system="投标资料知识库分析助手"，输出 `{"items":[{"title","summary"}]}`，覆盖技术方案/项目管理/质量/安全/进度/服务/应急/人员设备/业绩。
- **第二轮补漏** `buildSupplementItemTaskMessage`：带 `first_round_items` 不重复。
- **分批匹配** `buildMatchMessage`：段落匹配助手，找强相关 block 范围（block ID `P000001`…）。
- **遗漏补漏** `buildRecoveryMessages`：把 block 归入 `matches`/`new_items`/`discarded` 三类，归属优先级 `matches > new_items > discarded`。
- 条目**轻量**：正文只存 id/title/summary（resume），生成时 AI 按需选、再回填 content（类 skill 机制，非常规 RAG）。

### 2.4 全局事实提取（STEP04）
`globalFactsTaskV2.cjs`（生效）/ `globalFactsTask.cjs`（V1 已停用，工具函数与规则细节最佳出处）：
- **定义铁律**：事实不是要求摘录，必须转写为"本方案已采用…"的**事实陈述**。
- **三模式** fabricate/omit/placeholder —— 选择逻辑相同，仅在"缺失值填写"上不同（默认 fabricate）。
- **必含**：工期/运维期/交货时间至少其一。
- **大项来源**：由项目文件 + 概述 + 解析 + 目录确定；知识库/原方案**只补充已有大项的 content**，不新增大项。
- **提取流程**：分段提取 → 知识库补充 → 原方案保留 → 合并去重。

## 4. 文件信息引入工作流程（缓存优化：大且稳定前置、任务差异最后）

| 阶段 | 引入的信息 | 引入方式 |
|------|-----------|----------|
| 目录生成 STEP03 | 项目概述、技术评分要求、全局事实（可选） | 前置稳定大块，分支意图置后 |
| 正文编排 STEP05a | 知识库条目(轻量)、项目概述、目录树、上级/同级章节、**全局事实标题** | `buildChapterContentPlanMessages` 顺序：知识库→招标关键→事实标题→上级→同级→额外→当前节 |
| 正文生成 STEP05b | 项目概述、上级章节、同级章节、当前节编排结果、**全局事实完整内容(按标题)** | `resolveGlobalFactsByTitles` 注入选中事实组 |
| 配图阶段 | 配图意图（illustration-plan） | `technical-plan.md` 标记 + `illustration-config.json` |
| 审核阶段 | 全局事实、正文全文 | `buildConsistencyAuditMessages` |

**缓存优化总则**：把"大且稳定的上下文"（招标原文、项目概述、全局事实清单）放前面形成共享前缀；把"任务差异"（当前分支/当前章节/额外要求）放最后。解析阶段用 projectOverview-first + 5s 预热放大命中。实测成本可降约一个数量级。

## 5. 关键结论（附依据）

1. 解析纯机械 + AI 结构化两段式：doc→md（机械）与 md→结构化条目（AI）严格分离（`fileService.cjs`/`convert.mjs`/`bidAnalysisTask.cjs`）。
2. 知识库是"轻量条目 + AI 按需选"而非传统向量 RAG，两轮提取 + 分批匹配 + 遗漏补漏三机制保证召回（`knowledgeBaseService.cjs`）。
3. 全局事实的核心是"转写为事实陈述 + 编排只选标题/生成注入全文"，实现事实与正文解耦并省 token（`globalFactsTaskV2.cjs` + 正文 `resolveGlobalFactsByTitles`）。
4. 全链路贯彻"稳定前缀前置"的缓存成本优化，并以预热/分段合并控制长文档（`bidAnalysisTask.cjs`、`segmentedAiResultMerger.cjs`）。
