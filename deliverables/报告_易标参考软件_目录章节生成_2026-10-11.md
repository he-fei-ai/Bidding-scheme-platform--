## 1. 输入（Input）

目录生成 STEP03 的输入由"文件 + 上游结构化产物"两类组成，均落到 Agent 工作目录：

| 输入 | 来源 | 格式/预处理 | 依据 |
|------|------|-------------|------|
| 招标文件全文 | STEP01 fileService→Markdown | 纯机械 doc→md，无 AI | 解析提取报告 |
| 项目概述 | STEP02 `projectOverview`（必填项） | AI 提取，落 `technical_plan_bid_items` | 招标解析报告 |
| 技术评分要求 | STEP02 `techRequirements` + `TECHNICAL_SCORE_GROUPS_SCHEMA` | 拆成 R1/R2… 评分组，含 `detail_points[]` | `outlineGenerationTaskV2.cjs` |
| 知识库 | `knowledge_item_ids_json`（挂在节点上） | 轻量条目，AI 按需选 | 正文报告同源 |
| 用户输入/选择 | `taskControl.waitForOutlineSelection()` | Agent 中途可 ask-user | V2 主状态机 |
| 原方案 / 无评分模式 | 模式开关 `originalOnly` / `noTechnicalScoreMode` / `normal` | 决定初始文件依赖 | `runOutlineGenerationTaskV2` |

**初始文件依赖随模式而变**（`runOutlineGenerationTaskV2`）：normal 需评分项；`originalOnly` 只依据上传原方案；`noTechnicalScoreMode` 无评分表时走通用生成。开发者模式下并行做"模板抽取"，用 `AbortSignal.any` 取消。

## 2. 生成思路（三种范式 + 稳定输出）

### 2.1 短标书 + 强模型：一次性生成
强模型直接产出完整三级 JSON。对应本软件 `OUTLINE_DIRECT_SYSTEM`（本软件 2026-10-05 已引入，见引入报告）。

### 2.2 长标书 + 普通模型：分步生成
V2 是**七阶段 Agent 状态机**，把长目录拆成可控小步：
1. 初始生成（`createInitialPrompt`，字段 1-9）
2. 评分规划（`createScorePlanningPrompt`，**必须 ask-user 一次**，输出 `SCORE_DIRECTORY_PLAN_SCHEMA`：按 `score_item_level` 把 R 编号映射到 `target_title`/`additional_titles`）
3. 叶子配额（`createLeafAllocationPrompt` → `createLeafAllocationSchema`：allocated / agent-decides）
4. 逐分支扩子（`createChildrenPrompt`，`branch_id` 稳定、`score_item_level` 1-6）
5. 叶子数调整（`createLeafAdjustmentPrompt`，3 个固定选项）
6. 编号统一（`renumberOutline`）
7. 审核（`createOutlineReviewPrompt`，13 规则，喂"确定性审核上下文"`buildOutlineReviewContext`）

### 2.3 弱模型稳定输出
`max_retries:0` —— 单次不让模型自行重试，改由**外层结构**保障：语法校验→Schema 校验→业务规则→JSON 修复→分步拆分→模型审核→反馈回灌→二次生成。

### 2.4 目标叶子数与编号规则
- `deriveTargetLeafCount`（自带报告 + 源码）：`sectionWords` 默认 3000；
  - min&max 都有 → `ceil(((min+max)/2)/sectionWords)`
  - 只有 max → `floor(max/sectionWords)-2`
  - 只有 min → `ceil(min/sectionWords)+2`
  - 都无 → null
- `enforceMinimumLeafTarget` 兜最小叶子数；`countAiLeaves` 统计 AI 叶子。
- 编号：`renumberOutline` 统一位置式点号；`stripOutlineInternalFields` 去除内部 `branch_id`；id 正则 `^[1-9]\d*(?:\.\d*)*`，最深 6 级。

## 3. 工作流程（输入→生成→校验→修复→重试→分步→审核→二次生成→输出）

```
初始生成(强模型直出 / 普通模型分步)
   → JSON 语法校验 (aiService.collectJsonResponse)
   → Pydantic/Schema 校验 (createDirectoryNodeSchema/OUTLINE_JSON_SCHEMA)
   → 业务规则校验 (叶子数量/评分覆盖/去重/专业结构)
   → JSON 修复 (最小必要改动)
   → 分步拆分 (children 逐分支生成)
   → 模型审核 (OUTLINE_REVIEW_SCHEMA: passed/simple_fix/user_feedback/user_refuse)
   → 反馈回灌 + 二次生成
   → renumberOutline 编号统一 + strip 内部字段
   → 写 technical_plan_outline_nodes (saveOutline)
```

**saveOutline reason 协议**（自带报告）：`replace`/`edit`/`delete`/`add-root`/`add-child`/`sort` —— 用带原因的操作流落库，支持人工与 Agent 混合编辑。

**审核状态机** `OUTLINE_REVIEW_SCHEMA.status` ∈ `passed | simple_fix | user_feedback | user_refuse`；`issues[].category` ∈ `leaf-count | score-coverage | duplicate-directory | professional-structure`；`confirmation_required` 决定是否回灌给用户。

## 4. 提示词清单（System / User / JSON 结构 / 顺序优化 / 审核 / 修复）

| 提示词/函数 | 作用 | 关键约束 |
|-------------|------|----------|
| `createInitialPrompt` | 初始目录 | 字段 1-9；`attr` 枚举（通用/商务/资信/技术/其他）；`content_mode`（ai-generate/template-fill/point-to-point/other） |
| `createScorePlanningPrompt` | 评分→目录映射 | 必须 ask-user 一次；R1/R2 编号 |
| `createLeafAllocationPrompt` | 叶子数量分配 | allocated / agent-decides 两态 |
| `createChildrenPrompt` | 逐分支扩子 | `branch_id` 稳定；`score_item_level` 1-6 |
| `createLeafAdjustmentPrompt` | 叶子数微调 | 3 个固定选项 |
| `createOutlineReviewPrompt` | 审核 | 13 规则；喂确定性上下文 `buildOutlineReviewContext`（target±2 可接受） |

**顺序优化**：目录阶段稳定大块（评分项清单、原方案）前置，任务差异（当前分支/调整意图）放最后，与正文/解析一致的缓存策略。

## 5. 校验与修复（语法 / Schema / 业务 / JSON 修复 / 重试）

- **JSON 语法**：`collectJsonResponse` 统一封装，`normalizer` 归一、`validator` 校验、失败按 `max_retries` 处理（目录 V2 设 0，交由外层）。
- **Schema**：`createDirectoryNodeSchema(level)` 递归约束（叶子含 `content_mode`、分支 `children` minItems:2、最深 6）；`OUTLINE_JSON_SCHEMA{outline:[]}`；`TECHNICAL_SCORE_GROUPS_SCHEMA{groups:[{requirement_id ^R\d+, title, description, detail_points[]}]}`；`SCORE_DIRECTORY_PLAN_SCHEMA`；`OUTLINE_REVIEW_SCHEMA`。
- **业务规则**：`collectOutlineStructure`/`collectScoreMappingCoverage`/`isMissingTechnicalScoreItems` 检查评分覆盖；`buildOutlineReviewContext` 检查叶子数（target±2）；去重与专业结构由审核 `issues.category` 覆盖。
- **JSON 修复**：最小必要改动原则；`isMissingTechnicalScoreItems` 触发补生成。
- **重试/回灌**：审核 `simple_fix` 走程序修，`user_feedback` 回灌用户后二次生成；`user_refuse` 终止。

## 7. 参考软件自带报告记录的 7 项风险（要点）

超长上下文截断、评分覆盖漏检、叶子数量抖动、编号不一致、Agent 中途 ask-user 阻塞、分步生成的跨分支口径漂移、`content` 权威性与 `content_sections` 状态表双写一致性。→ 这些正是"引入本软件"时应重点设防之处。
