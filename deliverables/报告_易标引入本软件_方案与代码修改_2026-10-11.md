# 易标方法论引入本软件：现状对照、引入方案与代码修改方案

- **日期**：2026-10-11
- **对应任务**：「五、报告汇总」「六、引入本软件」「七、输出」
- **本软件**：招投标方案平台（FastAPI 后端，定位建筑工程专项施工方案编写）
- **前置报告**：整体探索 / 目录章节生成 / 正文生成 / 文件信息提取汇总引入（同目录 4 份）

> 核心结论：**本软件已在两轮改造（2026-10-05、2026-10-12）中把易标的方法论大量落地为代码模块**（源码注释直接写"移植自 OpenBidKit 易标"）。因此本轮"引入"不是从零移植，而是 **①把已实现但未接入主流程的模块接入（补齐 ENHANCE 报告"后续工作/集成到主流程"清单）②把桩实现升级为对齐易标的完整实现 ③保持所有门禁默认关闭以零行为变更**。本报告给出精确到文件/函数/配置项的差距矩阵与代码修改方案。

## 1. 引入原则（对齐任务「六.1」）

1. 复用成熟思路而非照搬代码：易标是 Electron/CJS/Agent-文件契约，本软件是 FastAPI/SSE/DB 表，**思路映射**而非翻译代码。
2. 保持架构/接口/数据链兼容：不改 REST/SSE 契约、不改 `Section`/`GlobalFact`/`KnowledgeItem` 字段名与语义。
3. 不破坏现有功能：每个引入项走 `config` 门禁，**默认值 = 现有行为**。
4. 新增配置默认保持现有行为或关闭（唯一例外 `CONSISTENCY_UNIQUE_EDIT_STRICT` 属"更安全收紧"，默认 true，见 §4.5）。
5. 适配建筑工程专项施工方案：九大章节 / 六大类危大工程 / 行业词表 / 暗标脱敏 / 防雷同——这些是本软件**独有且必须保留**的能力，易标无对应，不做替换。

## 3. 目标叶子数/字数预算（易标 deriveTargetLeafCount）——引入项 A

- 易标：`deriveTargetLeafCount`（sectionWords=3000，min/max→ceil/floor±2），`enforceMinimumLeafTarget`。
- 本软件：`writing_length_config.py` 有字数档位（brief/standard/detailed/long + `level2_target`），但**叶子数量配额与"评分项权重→目标节数"联动未系统化**（`analysis_reports/…v5.md:248` 记录 `L1=500/L2=3500/L3=300` 硬编码未接行业）。
- **引入方案（A）**：新增 `derive_target_leaf_count(scoring_points, section_words)` 工具（放 `workflows_outline_utils.py`），把评分项权重折算目标叶子数，喂给 V5.1 叶子数量合规校验（`OUTLINE_V51_SELFCHECK` count_violation 判据）与 `chapter_title_templates` 展开深度。`section_words` 新配置默认取现值，保持行为不变。

## 4. 逐项代码修改方案（精确到文件/函数/配置/兼容）

### 4.1 #5 目录↔评分一一对应接入（`ALIGN_OUTLINE_TO_SCORING`）
- **改什么**：`workflows_outline_v51.py::generate_outline_v51` 在 `_generate_level1_v51` 产出 L1 之后、扩 L2 之前，插入
  ```python
  if ALIGN_OUTLINE_TO_SCORING:
      from .outline_alignment import align_outline_to_scoring
      res = align_outline_to_scoring(outline=l1, scoring_text=scoring_text, strict=False)
      if not res.success:
          l1 = apply_alignment_suggestions(l1, res.suggestions)  # 非严格：回灌补章/合章
  ```
- **为什么**：易标 SCORE_DIRECTORY_PLAN 把 R 编号强制映射到章节；本软件 OUTLINE_V51_LEVEL1 已在提示词层要求"数量=评分项数"，但缺**程序化后校验**，弱模型常漏映射。
- **涉及文件/函数**：`workflows_outline_v51.generate_outline_v51`、`outline_alignment.align_outline_to_scoring`、`config.ALIGN_OUTLINE_TO_SCORING`(default false)。
- **兼容**：默认 false 零变更；true 时仅在 L1 后追加确定性对齐建议，不改数据表结构。回归：目录数量==评分点数±1。

### 4.2 #8 正文分层消息栈接入（`SPLIT_PROMPT_LAYERS`）
- **改什么**：`workflows_sections.py:1414` 的 `build_chapter_content_messages(section, **context)` 改为门禁分派：
  ```python
  if SPLIT_PROMPT_LAYERS:
      from .prompt_layering import build_chapter_content_messages as _layered
      messages = _layered(system_rules=..., project_overview=..., global_facts=...,
                          reference_material=..., plan_decision=..., parent_chapters=...,
                          sibling_chapters=..., current_section=...)
  else:
      messages = build_chapter_content_messages(section, **context)  # 现路径
  ```
- **为什么**：易标"大且稳定前置、任务差异最后"实测输入成本降约 10×（config.py:443 注释已记录收益）；`prompt_layering.py` 已实现 8 层栈但**无调用者**，等于能力闲置。
- **涉及**：`workflows_sections.py:1414`、`prompt_layering.build_chapter_content_messages:141`、`config.SPLIT_PROMPT_LAYERS`(false)。
- **兼容**：false 走旧路径逐字不变；true 仅改变消息数组排布（内容集合不变），Provider 侧对多 user 消息通用兼容。回归：同一章节 true/false 语义等价（可选 gold 断言）。

### 4.3 #10 编排升级为"知识库 item_ids + 事实 titles"两级选择
- **改什么**：`workflows_orchestration.py` 编排结果新增 `knowledge_item_ids` 与 `fact_titles` 字段（提示词 `CONTENT_ORCHESTRATION_SYSTEM` 增补两字段，参照易标 `buildChapterContentPlanMessages` 的 `knowledge.item_ids`/`facts.titles`）；生成阶段按 `fact_titles` 用现有 `_context.build_chapter_context(global_facts=resolve(titles))` **只注入被选中事实组全文**。
- **为什么**：现状把全部 `GLOBAL_FACTS` 整块塞进正文上下文（优先级 100 但不筛选），既费 token 又难防矛盾；易标"编排只选标题、生成按标题注入全文"是核心省 token + 一致性机制（正文报告 §4）。
- **涉及**：`prompts/content.py`（编排 JSON 增字段）、`workflows_orchestration`、`_context.build_chapter_context`、新配置 `CONTENT_FACT_TITLE_SELECTION`(default false)。
- **兼容**：false 时编排忽略新字段、生成仍整块注入 → 行为不变；true 时才走"标题筛选"。回归：true 时正文对未选事实不引用、对已选事实零矛盾。

### 4.4 #11 配图预编排由桩升级为易标式（`PRE_PLAN_ILLUSTRATIONS`）
- **改什么**：把 `illustration_planning.py` 的关键词 `detect_illustration_types` 升级为 **AI 全文编排 + 严格校验**，对齐 `contentIllustrationPlanning.cjs`：
  - 输入：`technical-plan.md`（叶子 `<!-- yibiao-section-start/end -->` 标记）+ `outline-tree.json` + `illustration-config.json`；
  - 三类 `html>ai>mermaid`、每类 limit、priority 1-5、title≤20 字无"图:"前缀、section_ids 存在且唯一、html 多节同父连续、occupied 互斥、标题标准化去重（重复即抛）；
  - 产出 `illustration_plan`（落表/JSON），生成阶段按 plan 注入配图意图。
  - 接入 `sse_content.py`：正文成功→（PRE_PLAN_ILLUSTRATIONS 时）先编排→再配图生成（复用现有 `image_engine`/`mermaid_*`/`image_providers`）。
- **为什么**：易标配图是"全文级、互斥、可校验"的独立阶段；本软件当前是章节内嵌、关键词判定，跨章节易重复、位置不可控。桩文件已存在但质量不足以开启。
- **涉及**：`illustration_planning.py`（升级）、`prompts/illustration.py`（补 13 规则编排提示词）、`sse_content.py`（接入点）、`config.PRE_PLAN_ILLUSTRATIONS`(false)/`ILLUSTRATION_PLAN_MAX_SECTIONS`(20)。
- **兼容**：false 完全保持现章节内嵌配图；true 才启用全文预编排。暗标锁定无图时该阶段整体跳过（复用现有暗标门禁）。

### 4.5 #13 一致性唯一命中修复接入（`CONSISTENCY_UNIQUE_EDIT_STRICT`，默认 true）
- **改什么**：`consistency_repair.repair_with_ai` 与 `consistency.apply_autofix` 的补丁执行改调 `utils/text_edit.apply_text_edit(text, old, new)`（唯一命中才替换，多命中/零命中返回错误、**绝不追加末尾**）；替换失败原因回灌下一轮（参照易标 `buildConsistencyRepairMessages` 上次失败回灌）。
- **为什么**：`text_edit.py` 已实现但**修复路径无调用者**；`CONSISTENCY_UNIQUE_EDIT_STRICT` 配置默认 true 却未被消费——存在"配置宣称已收紧、实际未收紧"的落差，属潜在静默污染风险（易标 textEdit.cjs 正是为此设计）。
- **涉及**：`consistency_repair.py`、`routers/consistency.py::autofix`、`utils/text_edit.apply_text_edit`、`config.CONSISTENCY_UNIQUE_EDIT_STRICT`。
- **兼容**：这是**行为收紧且更安全**，故默认 true；如需回退旧"多处也替换"行为可显式置 false。回归：冲突修复仅改目标处，`diff` 行数与预期一致。

### 4.6 #14 Agent 修复持久工作区（`AGENT_REPAIR_PERSIST_WORKSPACE`）
- **改什么**：`agent_repair.prepare_agent_workspace` 在 true 时把 `global-facts.md`/`technical-plan.md`/冲突清单写入 `AGENT_REPAIR_WORKSPACE_SUBDIR`（相对 DATA_DIR），支持"搜索关键词→分段读取→建索引→多轮改→程序校验回写"，完成后校验回写 DB。
- **为什么**：对齐易标 D1 Agent 修复；现仅 jsonl 日志、无可续跑工作区。
- **涉及**：`agent_repair.py`、`config.AGENT_REPAIR_PERSIST_WORKSPACE`(false)/`AGENT_REPAIR_WORKSPACE_SUBDIR`。
- **兼容**：false 保持 jsonl 行为。

### 4.7 #16 知识库两轮补漏接入 + 三态遗漏恢复（`KNOWLEDGE_REFILL_TWO_ROUND`）
- **改什么**：知识库入库/目录生成后调用 `refill_knowledge_gaps(outline, existing, bid_text, ai_call)`；并把现有"只补新条目"升级为易标 `buildRecoveryMessages` 的 **matches/new_items/discarded 三态**（已有 block 归入既有条目优先，其次新增，垃圾舍弃）。
- **涉及**：`routers/knowledge.py` 或 `workflows_outline_v51`（目录成稿后触发）、`knowledge_refill.refill_knowledge_gaps:187`、`config.KNOWLEDGE_REFILL_TWO_ROUND`(false)/`KNOWLEDGE_REFILL_BATCH_SIZE`(10)。
- **兼容**：false 保持单轮提取。

### 4.8 #17 解析预热（`ANALYSIS_WARMUP`，新配置，默认 false）
- **改什么**：`workflows_analysis` 解析多条目时，先跑 `projectOverview`→（可选小延迟）→ 并发其余，共享 `ANALYSIS_SYSTEM`+`ANALYSIS_CONTEXT_BLOCK` 稳定前缀（该前缀本软件已具备，见 `prompts/analysis.py:32-54` 注释"缓存共享前缀"），预热仅进一步抬高命中率。
- **兼容**：默认 false 保持现并发；true 时改串并混合调度。
