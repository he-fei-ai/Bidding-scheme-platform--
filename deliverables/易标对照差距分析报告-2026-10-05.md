## 〇、结论摘要

**总体实现度约 62%**，但分布极不均匀：

| 模块 | 实现度 | 定性 |
|------|--------|------|
| 一、解析提取 | **~70%** | 已实现且引擎更强（MinerU/pypdf、python-docx/docx2python 双层） |
| 二、目录生成 | **~85%** | 已实现且流程更细（V5.1 六阶段管线） |
| 三、全局事实 | **~55%** | 核心方案已实现，但「按章节选事实」「Agent 修复」缺失 |
| 四、正文生成 | **~50%** | 骨架上下文齐全，**选材与配置面缺失** |
| 五、审核与预检 | **~90%** | **显著超越**规格（双路径审计 + 补丁安全） |
| 六、导出文档 | **~80%** | 已实现，风格约束逐字一致 |
| 七、知识库（非 RAG） | **~40%** | 思路正确，但**只落在可研子系统**，主流管线未接入 |
| 八、opencode 集成 | **0%** | 完全未实现 |
| 九、提示词顺序优化 | **~30%** | 内部顺序稳定，但未分层多消息，且存在破坏缓存的写法 |

**最重要的三个缺口**（按投入产出比排序）：

1. **正文生成的 knowledge.item_ids 选材缺失** — 规格核心主张「参考知识库是技能/素材清单而非 RAG」，平台只在可研子系统实现了该思路，主流投标管线完全没有知识素材注入通道。
2. **编排层参数无配置面** — `max_ai_images` / `table_ratio` / `useAiImages` / `useMermaidImages` 算法全在，但调用点硬编码默认值，用户完全无法控制图片数量与表格密度。
3. **priority 语义跨层冲突** — 通用编排提示词用 0/1/2/3，图表专用提示词用 3/4/5，跨层比较时无效。

**一个明确的反例（平台比规格更好）**：审核与预检模块。规格只描述了「分组 → old_text/new_text → 唯一命中」三步；平台实现为 `consistency_auditor`（宿主确定性路径）+ `consistency_repair`（AI 语义路径）双通道，并额外做了行号区间加速、整节回灌拦截、渲染失败图号回滚。这部分不需要补齐，反而可以作为规格的反哺。

### 有意偏离（增强，非缺口）

- **Word 引擎**：规格要求 `docx2python`；平台实现为 **python-docx 主引擎 + docx2python 回退**（`docx_extractor.py:3,17-20,66-131,138-175`）。理由是 python-docx 提取质量更好、docx2python 作为「结果不足 50 字符或无表格时」的补充引擎。这是更稳健的双层设计。
- **PDF 引擎**：规格要求 `pdfplumber`；平台实现为 **pypdf 主引擎 + MinerU VLM/OCR 降级**（`files.py:404-484`，`app/services/ocr_parser.py:3-6`，MinerU 支持 109 种语言）。这是**能力增强**——`pdfplumber` 无法处理扫描件，MinerU 可以。

### 缺口

| 编号 | 规格要求 | 现状 | 影响 |
|------|---------|------|------|
| P-1 | PDF 按页提取并**添加页码标识** | 未实现 | 事实审计/审核时无法回溯「工期矛盾来自第几页」 |

## 七、知识库模块（非 RAG）— **本模块差距最大**

### 已实现（思路正确，但落点错误）

平台的**可研报告子系统**完整实现了规格第七节的「非 RAG」思路，且 `feasibility_knowledge.py:1-17` 的模块注释**明确记载了对易标的对照与差异化设计**：

> 为什么不能照搬易标（两平台知识库结构不同）：
> - 易标是「文档 → 轻量条目（id / title / resume）」两层，条目正文另存，选材靠 `chapter.knowledge_item_ids` 或「章节标题字符重合度」取 top3；
> - 本平台 `knowledge_items` 粒度更细且自带 `title / summary / content / keywords / source_doc_id`，正文可直接使用，因此选材流程设计为：
>   1. 用户在「报告目录」步骤勾选**参考文档**（document 级，落 `feasibility_meta`）；
>   2. 系统按「章节标题 + 写作重点」与「条目标题 + 摘要 + 关键词 + 正文」的**字符重合度打分**，每章节自动取 top-N（默认 3，score >= 2）；
>   3. 章节可写 `knowledge_item_ids` 精确指定条目，**人工选择覆盖自动匹配**；
>   4. 素材注入提示词时必须**改写到当前项目语境**，禁止提及「知识库 / 历史文档 / 资料来源」。

| 规格项 | 实现 | 证据 |
|--------|------|------|
| 不用 RAG，技能/素材清单而非文档片段检索 | ✅（可研子系统） | `feasibility_knowledge.py:1-17` |
| **字符重合度打分替代 embedding** | ✅（可研子系统） | `feasibility_knowledge.py:43-44` `_unique_content_chars`、`:27` `SCORE_MIN = 2`、`:29` `DEFAULT_TOP_N = 3` |

| 章节精确指定条目，人工覆盖自动匹配 | ✅ | `:207-214`；`feasibility.py:833` `save_node_knowledge_items`；路由 `routers/feasibility.py:262` |
| 素材改写而非直接搬运 | ✅ | `feasibility_prompts.py:386`（「改写到本项目的语境与数据体系中」）、`:369-375`（「仅用于理解行业背景」） |

**关于 RAG 的关键发现**：规格明确批评 RAG（「给 AI 一个错误的参考，还不如什么都不给」），而平台**两套机制并存**：

- 主流知识库模块 `app/services/knowledge.py` 在 `:1006-1011` 使用 `EmbeddingService` + `VectorStore`（BGE-M3 向量嵌入）——**这是 RAG**。
- `app/services/rag/retriever.py:15` `HybridRetriever` 定义了完整检索器，但**在整个 `app/` 下从未被实例化**（grep 确认只有定义处 `rag/__init__.py:3` 导出，无调用点）——**是死代码**。

即：平台保留了 RAG 的存储侧（向量化入库），但**检索侧从未接入任何生成链路**，因此 RAG 的语义误召回风险事实上未发生；同时非 RAG 的正确做法也没落到主流管线。

## 十二、总结

1. **审核与预检是唯一显著超越规格的模块**（双路径审计 + 行号加速 + 整节回灌拦截 + 覆盖度诚实上报），无需补齐。
2. **知识库是差距最大的模块**：规格的核心主张（非 RAG、技能清单、改写而非搬运）平台在**可研子系统已经完整实现**，注释里还明确写了与易标的对照——但**没有下沉到主流投标管线**。这是最遗憾的差距，也是投入产出比最高的补齐点。
3. **导出文档的 AI 生图风格约束是逐字移植**（「工程项目图示风格，结构清晰、专业克制」「避免品牌标识、水印、夸张营销元素」「专业实景照片风格，真实、克制」），移植保真度最高。
4. **两处规格实现被平台以「更工程化」的方式替代**：PDF 用 MinerU 替代 pdfplumber（支持扫描件）、Word 用双层引擎替代单引擎。这些是增强而非缺失。
5. **发现的两个真实实现缺陷**（D-1 priority 跨层冲突、D-3 system prompt 条件 mutate）不在规格清单里，但都直接影响规格的核心收益（排序正确性、缓存命中率）。
6. **一处设计成果作废**：`prompts/content.py` 的正文提示词从未被引用（D-4），仅存于注释中。
