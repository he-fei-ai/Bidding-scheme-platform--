# 性能瓶颈分析与优化方案（2026-10-05）

**范围**：`backend/app/`（FastAPI + SQLite 单 worker 部署，单事件循环）
**方法**：AST 静态扫描（async 端点内的同步 I/O 全量清点）+ 热路径追踪 + 前端轮询频率交叉验证
**承接**：2026-09-16 报告 B-W1 ~ B-W7（已验证全部接线/处置到位）

---

## 一、总体结论

上一轮修复确认有效：`build_sort_lookup`/`executemany`/记忆化环检测/`files.py to_thread`
均已落码并有回归测试。但扫描发现 **同两类问题在其他路由模块大面积残留**，
且前端存在 3~10s 高频轮询（FeasibilityReportPage 3s、DuplicateCheck/RejectionCheck 轮询、
SectionEditor 10s、Layout/健康检查），正文生成高峰期写锁争用时，
这些同步 I/O 会冻结事件循环——SSE 心跳、其他所有请求一并卡死，用户可感知。

## 二、瓶颈清单

### P-1（B-W4' 蔓延，本轮主修）：42 个 `async def` 端点在事件循环内做同步 SQLite I/O

AST 扫描（`async def` 端点体内直接 `with get_db()` 且无 `to_thread`）：

**(a) 抢全局写锁（`get_db()` 无 readonly，锁超时 60s）— 28 处，最危险**

| 文件 | 端点 |
|---|---|
| consistency.py | `get_conflicts`(纯读却抢写锁)、`get_audit_summary`(纯读却抢写锁) |
| content_version.py | list / get / save / restore / delete（5 个） |
| images.py | `generate_image` / `list_image_tasks` / `get_image_task` / `get_image_file`（后 3 个纯读） |
| export.py | `download_export` |
| templates.py | upload / list / delete / audit_coverage（4 个） |
| prompts.py | update / reset / rollback（3 个） |
| sections.py | `v51_confirm_route`、`generate_illustration` |
| knowledge.py | `get_stats`(纯读)、`upload_document`(`mkdir`+`write_bytes` 大文件写) |
| ai_config.py | provider 配置 save/activate/clear 等 8 个写路径（**本轮追加已全部收敛**，见附 B） |

**(b) 事件循环内同步 readonly 查询 — 14 个 ai_config/prompts 端点**（不抢写锁，
但连接获取失败时 `time.sleep(0.5)` 重试同样发生在 loop 线程）。

**(c) 权限门函数（每个请求必经）— 3 处**：
- `routers/sections.py::require_project_permission`（sections 全路由 + 经
  `project_access.enforce_project_access` 被 facts/rejection/duplicate/consistency/export 复用）
- `routers/tasks.py::_ensure_project_access`（同逻辑副本）

**修复模式**（与 files.py 既有做法一致，锁仍在 worker 线程阻塞、事件循环不受影响，
符合「单 Worker 部署与并发一致性策略」）：
1. 纯读端点：`get_db()` → `get_db(readonly=True)`（跳过写锁）+ `asyncio.to_thread` 包装；
2. 真实写入端点：DB/文件块提取为同步内部函数，`await asyncio.to_thread(...)` 调用；
3. 权限门：DB 读取段收敛到 `_load_project_owner_row` 同步函数，`to_thread` 调用。

### P-2（B-W5 收口，本轮主修）：`build_tree` 缓存 miss 全量加载 content 并逐行 `count_words`

- 60s TTL 每项目一次树重建走 `list_sections`（`SELECT *` 含 MB 级正文），
  而树节点实际只需要：轻量列 + `bool(content)` + 4 个图表 JSON 的「非空/非空串」标志 + word_count。
- `word_count` 列自 2026-10-04（BUG-C）起已在 `update_section` 写入路径持久化，
  但存量行为默认 0 且**无回填**（chunk 直写 SQL 的路径不维护该列）。
- **修复**：`build_tree` 改用列投影查询（不含 `content`/`ai_prompt_snapshot`），
  `has_content` 用 `length(content) > 0` 在 SQL 侧判定；`word_count` 持久化列为 0 且
  正文非空时视为「可能陈旧」，仅对这些行按 id 单独回读正文重算（计数口径
  `_count_words` 是 Python 中文计数，SQL 无法下推，回读是正确性兜底而非偷懒）。
- **收益**：常见项目（已维护 word_count）树重建不再传输/扫描任何正文；
  存量脏数据项目也只回读脏行正文，正确性与原实现逐字段一致。

### P-3（观察项，不改）：死代码

`services/perf_optimizations.py` 8 个导出中仅 `build_sort_lookup` 接线；
`cached_image_font`/`redis_list_count_simplified`/`precompute_inline_chart_types`/
`has_inline_marker_optimized` 已被生产代码就地实现取代
（`mermaid_common._load_truetype_cached`、`export._detect_inline_chart_types`）；
`list_sections_light`/`delete_tree_recursive_cte` 为逻辑重复的内联版。
删除会牵动既有测试，建议单列技术债任务处理，本轮仅在文件头注记。

### 附 B（本轮未动，留后续）

- `ai_config.py` 8 个写路径端点的 to_thread 化（save_ai_config / quick_setup /
  save_image_model_config / clear_provider_history / save_text_provider_config /
  activate_text_provider_config / save_image_provider_config /
  activate_image_provider_config）：**已于本轮追加全部收敛**，模式与 P-1 一致
  （写段整块 `def _write()` + `await asyncio.to_thread`；save_ai_config /
  save_image_model_config 的只读回读改 `readonly=True`+to_thread；
  activate_text 的写段在 `asyncio.Lock` 内派发，d 物化为 dict 后跨线程回传）。
  ai_config 其余纯读 GET 端点走 `readonly=True`，本就不在扫描器违规集。
  已从测试 `_P1_DEFERRED_ALLOWLIST` 移出并加入已修复断言列表。
- `images.py::generate_image`：旧实现在 `with get_db()`（写锁）内 `await`
  异步图像生成（外部 HTTP 秒~分钟级），全局写锁跨整个生成期——**已于本轮追加修复
  **（单独立项）。重构口径：`ImageGenerationService.__init__` 的 `db_conn`
  改为可选，写点（`_record_task`/`_update_task_success`/`_download_image` 回写）
  统一走 `await self._execute_write(...)`，生产路径在 worker 线程内开“即用
  即关”的短事务（`get_db()`），外部 HTTP 期间不再持锁；`load_image_config` 纯读改
  `readonly=True`。路由 `generate_image` 不再用 `with get_db()` 包整段，端点体内
  已无 get_db 调用。已从 `_P1_DEFERRED_ALLOWLIST` 移出（现白名单为空，护栏收紧
  为“全库零阻塞端点”）并加入已修复断言列表；新增行为不变式测试：外部 HTTP
  生成期间活跃 DB 会话数必为 0。
- `word_count` 一次性全量回填迁移（P-2 的兜底回读在其落地后可移除）。

## 三、确认过的"非瓶颈"

| 疑点 | 结论 |
|---|---|
| 同步 `def` 端点做 DB I/O | FastAPI 自动派发线程池，不阻塞事件循环，无需改动 |
| `run_audit`/`apply_autofix`/`suggest_fixes` | 已 `to_thread`（2026-09-18 P2 修复） |
| `require_project_permission` 的 PRAGMA | 已有进程级一次性缓存，只剩单次 SELECT |
| `build_tree` 60s TTL + 淘汰锁 | 缓存结构本身健康，仅 miss 路径待优化（P-2） |
| `projects` 列表 `SELECT *` | 已有 Redis 5min 缓存（services/projects.py） |
