# 性能瓶颈分析与优化方案（2026-09-16）

**范围**：`backend/app/`（FastAPI + SQLite/aiosqlite 后端）
**方法**：静态代码审查 + 热路径追踪（DB 层 / 解析层 / AI 工作流层 / 路由层）

---

## 一、总体结论

代码库此前已经历多轮性能优化（大量 `PERF-*`/`BUG-FIX-*` 注释、`services/perf_optimizations.py` 专项模块），
以下瓶颈点均已就位：SQLite 连接池 + 写锁串行化、递归 CTE 替代 N+1 删除、
章节树 60s TTL 缓存、tender_context / 文件解析 / 合并文本多层缓存、
OCR 引擎单例、正文生成自适应并发 + 熔断器、导出图表指纹缓存、
count_words LRU、JSON 容错解析链（含早退优化）。

**本轮发现的核心问题：`perf_optimizations.py` 中的优化助手只被自己的测试引用，
从未接线到真实热路径（"死优化代码"）。** 此外另有若干残留热点。

## 二、瓶颈清单与修复

### B-W1（已修复）：`get_section_path` O(N²) 排序 —— B7 未接线
- **位置**：`services/sections.py::get_section_path`
- **问题**：排序键 lambda 内用 `next((r["sort_order"] for r in rows if r["id"] == sid), 0)`
  逐键线性扫描全部 rows；单父节点 N 个子章节时键计算为 O(N²)，大目录（数百同级章节）
  每次路径计算都白扫几十万次。`perf_optimizations.build_sort_lookup` 已实现但从未被调用。
- **修复**：一次遍历预建 `{id: (sort_order, created_at)}` 查找表，排序键 O(1)。
- **收益**：N=500 同级章节时，键计算从 ~25 万次比较降为 500 次建表 + 排序。

### B-W2（已修复）：`move_section` / `reorder_sections` 逐行 UPDATE
- **位置**：`services/sections.py::move_section` / `reorder_sections`
- **问题**：循环内逐条 `conn.execute("UPDATE ...")`，N 个兄弟节点 = N 次 SQL 编译与步进。
- **修复**：改为 `conn.executemany` 批量执行，语义不变（同一事务内）。

### B-W3（已修复）：`validate_outline_integrity` 环检测 O(N·depth)
- **位置**：`services/sections.py::validate_outline_integrity`
- **问题**：从每个节点各自向上走完整条祖先链，链状大纲（如 500 节点链）最坏 O(N²)；
  保存大纲前校验是用户可感知的同步路径。
- **修复**：记忆化（`safe_nodes` 缓存已确认无环节点），整体 O(N)；
  报错语义与原实现逐一对齐（环上每个起点各报一次）。

### B-W4（已修复）：files 路由同步 I/O 阻塞事件循环
- **位置**：`routers/files.py::list_files / get_file_text / delete_uploaded_file`
- **问题**：`async def` 端点内直接做同步 DB 查询 / 数 MB 文件读取 / `unlink`。
  正文生成高峰期 SQLite 写锁争用时，这些调用会卡住整个事件循环，
  拖慢所有并发 SSE 心跳与 API 响应。
- **修复**：统一包装 `asyncio.to_thread`（与同文件 `upload_file`/`re_extract` 既有做法一致）。

### B-W5（发现但未改动，留待后续）：`build_tree` 全量加载 content
- **位置**：`services/sections.py::build_tree` → `list_sections`（`SELECT *`）
- **问题**：树缓存 miss 时（每 60s 一次/项目）把全部章节正文（大项目可达 10MB+）
  传输到 Python 并逐条跑 `count_words`。`list_sections_light` 已备好但无法直接替换：
  树节点需要 `word_count`（中文计数无法下推 SQL）。
- **建议**：持久化 `word_count` 列（写入路径维护 + 一次性回填）后切换 `list_sections_light`，
  属 schema 变更，需单独评审，本轮未动。

### B-W6（发现但未改动，观察项）：`get_reference_outline_by_industry` 无缓存
- **位置**：`db.py::get_reference_outline_by_industry`
- **问题**：每次目录生成都查库读取大文本参考提纲。单次成本不高（有索引），
  但同一项目重复生成时完全可缓存。建议挂 10min TTL 项目级缓存。

### B-W7（发现但未改动，低优先级）：`validate_outline_integrity` 悬空 parent 检查
- 与 B-W3 同函数：第 1 步逐节点查 `pid not in all_ids` 已是 O(N)，无需处理。

## 三、显式确认过的"非瓶颈"（避免过度优化）

| 疑点 | 结论 |
|---|---|
| `upload_file` 阻塞事件循环（OCR/MinerU 秒~分钟级） | 已用 `asyncio.to_thread` 派发 |
| `extract_tender_context_async` 重复提取 4 万字上下文 | `tender_context.py` 已有 hash-key TTL 缓存 |
| `json_parser` 多级候选链对干净输入的白工 | 一级 `json.loads` 直接命中返回；`_extract_balanced_json` 已有首括号早退 |
| DB 层 `time.sleep` 重试 | 全部运行于 `asyncio.to_thread` worker 线程，不阻塞事件循环 |
| `generate_sections` 并发 | semaphore 钳制 + gather(return_exceptions) + ticker，无串行化缺陷 |
| OCR / PaddleOCR / MinerU 重复初始化 | 均已模块级单例 + 锁保护 |
| 导出重复渲染图表 | ChartCache 磁盘缓存 + `_strip_fig_no_for_cache` 键归一化 + L1 内存缓存 |
