# 生成正文代码与提示词：文档梳理与引入方案

## 一、参考文档工作流程梳理

这份文档聚焦正文生成的**最小可用闭环**，核心是两个难点和一套简洁的解决方案。

### 1. 两个核心难点

**难点一：字数太多，不能一次生成。**
一份标书几万到几十万字，直接让 AI 生成行不通。解决办法是**按提纲叶子节点逐节生成**，每个叶子节点发起一次生成请求，把大任务拆成小任务。

**难点二：分布生成导致上下文不连贯、内容重复。**
多部分内容之间不连贯是必然的，更严重的是——都基于同一份招标文件生成，很容易产出意思过于相近的内容，俗称“车轱辘话”。解决办法是**在每次请求中传入上级章节和同级章节信息**，让 AI 知道自己所处的位置，避免越界和重复。

### 2. 请求参数设计（ChapterContentRequest）

```python
class ChapterContentRequest(BaseModel):
    chapter: Dict[str, Any]                      # 当前章节信息（id、title、description）
    parent_chapters: Optional[List[Dict]]       # 上级章节列表，保持连贯性
    sibling_chapters: Optional[List[Dict]]      # 同级章节列表，避免内容重复
    project_overview: str                       # 项目概述，让 AI 知道核心需求
```

四个参数各司其职：`chapter` 是必填的当前章节，`parent_chapters` 解决“承接上一级逻辑”，`sibling_chapters` 解决“不与旁边章节重复”，`project_overview` 解决“知道要写什么”。

### 3. 核心提示词

**SystemPrompt 六条要求**：
1. 内容专业、准确，与章节标题和描述一致；
2. 技术方案不是宣传报告，朴实无华，不假大空；
3. 语言正式规范，但不用奇怪的连接词，不让人觉得像 AI 生成；
4. 内容详细具体，避免空泛；
5. 避免与同级章节内容重复，保持独特性和互补性；
6. 直接返回章节内容，不生成标题，不要额外说明或格式标记。

**UserPrompt 的拼接结构**：
- 项目概述信息；
- `context_info`（上级章节信息 + 同级章节信息，同级中排除当前章节）；
- 当前章节信息（ID、标题、描述）；
- 生成要求（与上级逻辑相承、避免同级重复、突出本章节独特性）。

### 4. 上下文拼接的关键细节

```python
context_info = ""
if parent_chapters:
    context_info += "上级章节信息：\n"
    for parent in parent_chapters:
        context_info += f"- {parent['id']} {parent['title']}\n  {parent['description']}\n"

if sibling_chapters:
    context_info += "同级章节信息（请避免内容重复）：\n"
    for sibling in sibling_chapters:
        if sibling.get('id') != chapter_id:   # 关键：排除当前章节
            context_info += f"- {sibling.get('id', 'unknown')} {sibling.get('title', '未命名')}\n  {sibling.get('description', '')}\n"
```

**两个工程细节值得注意**：同级章节必须排除当前章节，否则 AI 会把自己当作参考对象；字段访问用 `.get()` 加默认值，避免缺字段导致 KeyError。

### 5. 这套方案的定位

文档明确说：“就这么简单，生成正文不需要过多的逻辑推理，用最普通的大模型即可实现稳定输出，也几乎不存在生成失败的问题。”——这是**最小可用版本**，解决“能不能生成”的问题，但不解决“生成得好不好、前后一致不一致”的问题。


## 二、与本软件现有能力的差距

参考文档是“最小闭环”，本软件经过前几轮增强，已有更完整的机制。引入时需要**保留其简洁骨架，叠加本软件的增强能力**：

| 维度       | 参考文档                           | 本软件已有/需要                                        |
| ---------- | ---------------------------------- | ------------------------------------------------------ |
| 生成单位   | 叶子节点                           | L5 叶子节点，L1-L5 层级                                |
| 上下文参数 | chapter、parent、sibling、overview | 增加全局事实字段、配图意图、九大章节必含要素、适用规范 |
| 全局事实   | 未涉及                             | 编排选事实、生成注事实，禁止全部注入                   |
| 字数控制   | 未涉及                             | 四档控制（800/1200/2000/2500）、L3 约 300 字           |
| 顺序生成   | 未涉及                             | 按 sort_order 顺序生成，并发分批                       |
| 一致性     | 未涉及                             | 一致性审计 + 普通修复 + Agent 修复                     |
| 去 AI 化   | 已涉及（第 3 条）                  | 需强化：避免高频 AI 句式、避免空话套话                 |
| 同级防重复 | 已涉及（第 5 条）                  | 保留，并配合 other_outline 机制                        |

```text

使用 EnterPlanMode 或 TodoWrite 制定计划，列出：正文生成模块现有实现、参考文档的适配点、需要叠加的增强能力、与目录生成/全局事实/图表生成/导出文档的衔接、风险点与验证方式、执行顺序与优先级（P0/P1/P2）。

二、保留参考文档的核心骨架

1. 按叶子节点逐节生成
   - 以目录树 L5 叶子节点为最小生成单位；
   - 每个叶子节点发起一次生成请求；
   - 大任务拆成小任务，避免一次生成几十万字。

2. 请求参数设计（在本软件中扩展）
   - chapter：当前章节信息（id、title、description）；
   - parent_chapters：上级章节列表，保持逻辑相承；
   - sibling_chapters：同级章节列表，避免内容重复；
   - project_overview：项目概述（本软件中替换为“专项方案名称 + 主要施工内容 + 全局事实摘要”）；
   - 扩展参数：全局事实相关字段、配图意图、九大章节必含要素、适用规范清单、字数标准、当前节点在目录树中的位置。

3. 上下文拼接
   - 上级章节信息全部传入；
   - 同级章节信息传入时必须排除当前章节；
   - 字段访问使用安全取值，避免缺字段导致异常；
   - 上下文过长时按优先级截断，优先保留上级章节与当前章节信息。

4. SystemPrompt 六条核心要求（保留并适配）
   - 内容专业、准确，与章节标题和描述一致；
   - 技术方案不是宣传报告，朴实无华，不假大空；
   - 语言正式规范，不使用奇怪的连接词，不让人觉得像 AI 生成；
   - 内容详细具体，避免空泛；
   - 避免与同级章节内容重复，保持独特性和互补性；
   - 直接返回章节内容，不生成标题，不要额外说明或格式标记。
   - 适配补充：结合专项方案名称的主要施工内容；结合适用规范；不得编造关键数据。

5. UserPrompt 结构（保留并扩展）
   - 专项方案名称与主要施工内容；
   - 项目概述/全局事实摘要；
   - 上级章节信息；
   - 同级章节信息（请避免内容重复）；
   - 当前章节信息（ID、标题、描述、在目录树中的位置）；
   - 全局事实相关字段（按“章节 → 所需事实”映射表注入，不全部注入）；
   - 配图意图；
   - 九大章节必含要素清单；
   - 字数标准；
   - 生成要求（与上级逻辑相承、避免同级重复、突出本章节独特性、按施工逻辑展开）。

三、叠加本软件的增强能力

1. 全局事实精准注入
   - 编排阶段：AI 只看到全局事实的标题，判断当前章节需要哪些事实；
   - 生成阶段：程序根据标题取出完整事实，只注入当前章节；
   - 禁止把全部全局事实注入每一次请求；
   - 提示词硬约束：提供全局事实时必须优先使用不得前后矛盾；未提供时不编造人员、周期、质保、品牌、型号。

2. 顺序生成与并发分批
   - 按目录树 sort_order 顺序生成；
   - 并发时按顺序分批，批内并发、批间串行；
   - 落库顺序、展示顺序、导出顺序与目录树顺序一致；
   - 断点续生成记录最后成功节点，从下一节点继续。

3. 字数控制
   - L5 级目录按四档控制（简短 800、标准 1200、详细 2000、超长 2500）；
   - L3 级目录下除下级目录章节外，约 300 字正文文字；
   - 字数不足时启动扩展循环，单节最多 3 轮，批量调整批大小 10；
   - 字数充足但不堆砌空话。

4. 去 AI 化与语言质量
   - 避免模板化开头结尾、排比堆砌、空话套话；
   - 避免“首先、其次、最后”“综上所述”“值得注意的是”等高频 AI 句式；
   - 避免“根据实际情况”“视具体情况而定”等空话；
   - 按施工逻辑展开，先讲对象、再讲工序、再讲要点；
   - 允许适度口语化，保持专业性与正式度。

5. 一致性保障
   - 生成后审计：按目录顺序分组，每组与全局事实一起交给 AI，检查明确写出的事实冲突；
   - 普通修复：返回 old_text/new_text，唯一命中才替换；
   - Agent 修复：准备 global-facts.md 与 technical-plan.md，Agent 搜索、分段读取、多轮修改，程序校验后只回写变化小节；
   - 一致性边界：不能 100% 保证；全局事实本身错则一致地错；明确冲突可自动找，履约可行性/隐含逻辑/法律责任需人工复核。

6. 生成后自检
   - 检查九大章节必含要素是否齐全；
   - 检查是否与全局事实冲突；
   - 检查编号是否一致；
   - 检查图表是否同步、图号是否虚跳；
   - 检查是否出现【待补充】等占位标记；
   - 检查语言质量；
   - 发现问题自动修复或标记待人工处理。

四、适配本软件定位

1. 从“技术标”到“专项施工方案”
   - 参考文档的 SystemPrompt 是“标书编写专家”，本软件改为“建筑工程专项施工方案编写专家”；
   - 参考文档的“技术方案不是宣传报告”保留，并强化“施工方案要符合九大章节标准”；
   - 参考文档的“避免同级重复”保留，并叠加 other_outline 防重复机制。

2. 与九大章节标准衔接
   - 每个 L5 章节必须对应九大章节中的某一章节；
   - 每章节必含要素清单随请求注入；
   - 生成后自检九大章节必含要素是否齐全。

3. 与目录生成、全局事实、图表生成、导出文档的衔接
   - 目录生成提供 sort_order 与节点 ID，正文按序生成；
   - 全局事实按“章节 → 所需事实”映射表注入；
   - 图表生成接收配图意图，同步渲染；
   - 导出文档按标准 DOCX 输出，不引入 Word 2010+ 专有扩展。

五、BUG 修复重点

1. 同级章节未排除当前章节，导致 AI 自我参考。
2. 字段访问未用安全取值，缺字段导致异常。

7. 语言机器味重、空话套话、同级重复。
8. 生成后未自检，问题流入审核预检。
9. 一致性问题未审计，前后数据矛盾。
10. 与九大章节标准、目录、图表、导出的衔接断裂。
11. 修复过程中发现的其他所有 BUG。

六、验证与回归

1. 每完成一项引入，运行相关测试，建立基线并对比。

   - 同级章节是否排除当前章节；

   - 语言质量是否提升、同级是否重复；
   - 生成后自检是否生效；
   - 一致性审计是否发现并修复冲突。
3. 端到端验证：解析提取 → 提取项目 → 目录生成 → 全局事实 → 正文生成 → 图表生成 → 审核预检 → 导出 DOCX。
```

## 五、优化点说明

**1. 保留参考文档的“简洁骨架”**
参考文档的价值在于用四个参数、一段 SystemPrompt、一段 UserPrompt 就把正文生成跑通了。引入时不推翻这套骨架，而是在此基础上叠加，避免过度设计。

**2. 两个工程细节单独强调**
同级章节必须排除当前章节（否则 AI 自我参考）、字段访问用安全取值（避免 KeyError），这两个细节看似小，但直接影响生成质量与稳定性。

**3. 把 `project_overview` 适配为专项施工方案语境**
参考文档的 `project_overview` 是招标文件摘要；本软件替换为“专项方案名称 + 主要施工内容 + 全局事实摘要”，与之前的目录生成、全局事实机制保持一致。

**4. 明确“简洁骨架”与“增强能力”的分层**
参考文档解决“能不能生成”，本软件增强解决“生成得好不好、前后一致不一致”。引入时明确分层，避免把增强能力硬塞进 SystemPrompt 导致提示词臃肿。

**5. 补齐与九大章节、全局事实、图表、导出的衔接**
正文生成不是孤立的，必须与目录生成的 sort_order、全局事实的映射表、图表的配图意图、导出的标准 DOCX 对接，否则会形成“生成归生成、导出归导出”的断裂。

**6. 保留一致性边界**
参考文档没有一致性审计，本软件叠加了审计与修复，但明确“不能 100% 保证”“全局事实本身错则一致地错”“履约可行性/隐含逻辑/法律责任需人工复核”，避免对自动一致性产生不切实际的预期。
