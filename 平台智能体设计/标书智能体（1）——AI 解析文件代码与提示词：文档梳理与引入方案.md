# AI 解析文件代码与提示词：文档梳理与引入方案

## 一、参考文档核心机制梳理

这份文档是标书智能体的第一步——招标文件解析，解决的是“怎么把文件内容完整提取出来，再让 AI 提取出结构化信息”的问题。

### 1. 文件内容提取：两种解析器

**Word 用 `docx2python`**：能更好地处理表格和结构。表格识别为列表嵌套列表，用 `[表格内容]` 和 `[表格结束]` 标记，单元格用 `|` 连接；普通文本直接追加；最后 `del content` + `gc.collect()` 释放资源。

**PDF 用 `pdfplumber`**：按页提取，每页加 `--- 第 N 页 ---` 页码标识；表格用 `[表格 N]` 和 `[表格结束]` 标记，空行跳过，空单元格过滤；最后 `pdf.close()` + `gc.collect()` 释放资源。

**两个工程细节**：页码标识便于 AI 定位数据来源；资源释放放在 `try` 和 `except` 两处，避免异常时资源泄漏。

### 2. AI 流式请求封装：`AsyncOpenAI`

使用 `openai.AsyncOpenAI` 异步客户端，而不是同步客户端。原因是后续要一次性编写几十万字标书，需要并发请求提速，同步客户端会成为瓶颈。

`stream_chat_completion` 方法：接收 messages、temperature、response_format，调用 `client.chat.completions.create` 并设置 `stream=True`，异步迭代 `chunk.choices[0].delta.content` 逐块 yield，异常时 yield 错误信息。

### 3. 项目概述提取提示词

SystemPrompt 定义“专业标书撰写专家”，重点关注七方面：项目名称和基本信息、背景和目的、规模和预算、时间安排、实施的具体内容、主要技术特点、其他关键要求。工作要求三条：保持全面性和准确性尽量用原文不自己编写、只关注实施相关内容不提取商务信息、直接返回项目概述不返回其他内容。

UserPrompt 简单：`请分析以下招标文件内容，提取项目概述信息：{file_content}`。

### 4. 技术评分要求提取提示词（自我反思式结构化）

这是文档中最有价值的部分，采用“目标定位 → 提取内容要求 → 处理规则 → 输出示例 → 验证步骤”五段式结构：

- **目标定位**：识别“技术评分”“评标方法”“评分标准”“技术参数”“技术要求”“技术方案”“评审要素”相关章节，忽略商务、价格、资质等非技术类。
- **提取内容要求**：每项按四字段结构化输出——评分项名称、权重/分值、评分标准、数据来源，信息缺失标注“未提及”。
- **处理规则**：模糊表述按上下文判断、表格按行提取标注 `[表格数据]`、分层结构用缩进或编号体现、单位统一为“分”或“%”并注明原文单位。
- **输出示例**：给出两个完整的评分项示例，让模型知道期望格式。
- **验证步骤**：自检“所有技术评分项是否覆盖”“权重总和是否与文档声明的技术总分一致”。

**这套结构的价值在于“验证步骤”——让模型在输出前自我检查，而不是输出完再让人检查。**

```text

核心目标：
1. 文件内容完整提取，表格与页码可追溯；
2. AI 流式请求封装统一，支持并发；
3. 结构化提取提示词采用五段式方法（目标定位、提取内容要求、处理规则、输出示例、验证步骤），复用到本软件所有提取任务；
4. 将“项目概述提取”适配为“工程概况提取”，将“技术评分要求提取”适配为“专项方案类型与危大工程参数提取”。

一、任务计划（必须先执行）
使用 EnterPlanMode 或 TodoWrite 制定计划，列出：解析提取模块现有实现、文件解析器现状、AI 请求封装现状、提取提示词现状、需要适配的提取任务清单、与提取项目/目录生成/全局事实的衔接、风险点与验证方式、执行顺序与优先级（P0/P1/P2）。

二、文件内容提取

1. Word 解析
   - 使用 docx2python 或等价库，处理表格与结构；
   - 表格识别为 `[表格内容]` ... `[表格结束]` 包裹，单元格用 `|` 连接；
   - 普通文本直接追加；
   - 资源释放放在 try 与 except 两处，避免异常时泄漏。

2. PDF 解析
   - 使用 pdfplumber 或等价库，按页提取；
   - 每页加 `--- 第 N 页 ---` 页码标识，便于 AI 定位数据来源；
   - 表格识别为 `[表格 N]` ... `[表格结束]`，空行跳过，空单元格过滤；
   - 资源释放放在 try 与 except 两处。

3. 扩展文件类型（本软件需要）
   - 施工图（DWG/PDF）、勘察报告（PDF/Word）、施工组织设计（Word）、招标文件（PDF/Word）、地勘报告、专项方案原稿；
   - 每种类型明确解析器与表格/结构处理方式；
   - 统一输出格式：文本 + 页码标识 + 表格标记。

4. 解析质量校验
   - 提取后检查文本长度是否异常（过短可能解析失败）；
   - 检查表格数量是否符合预期；
   - 检查是否存在乱码、控制字符、编码异常；
   - 解析失败时给出明确错误，不静默返回空。

三、AI 流式请求封装

1. 使用 AsyncOpenAI 或等价异步客户端
   - 不使用同步客户端，避免并发瓶颈；
   - 本软件正文生成、目录生成、全局事实提取均为高频调用，异步是基础。

2. stream_chat_completion 等价方法
   - 接收 messages、temperature、response_format；
   - 设置 stream=True，异步迭代 chunk 逐块 yield；
   - 异常时 yield 错误信息，不静默吞掉；
   - 支持取消（AbortController 或等价机制），配合停止按钮。

3. 非流式请求封装
   - 提供 collect_chat_completion 等价方法；
   - 与 stream_chat_completion 共用客户端与错误处理。

4. JSON 模式兼容
   - 优先使用 response_format={"type": "json_object"}；
   - 不支持时自动降级为普通请求，不把稳定性绑定在 JSON 模式上（与前期已引入的 collect_json_response 协同）。

四、结构化提取提示词五段式方法

所有提取任务统一采用五段式结构：

1. 目标定位
   - 明确从文档中识别哪些章节、忽略哪些章节；
   - 例如“识别与工程概况、地质水文、周边环境相关的章节，忽略商务、报价等非技术内容”。

2. 提取内容要求
   - 每项按固定字段结构化输出；
   - 信息缺失标注“未提及”，不编造；
   - 字段顺序、命名统一。

3. 处理规则
   - 模糊表述按上下文判断；
   - 表格按行提取并标注来源；
   - 分层结构用缩进或编号体现层级；
   - 单位统一并注明原文单位。

4. 输出示例
   - 给出 1~2 个完整示例，让模型知道期望格式；
   - 示例覆盖正常情况与缺失情况。

5. 验证步骤
   - 让模型在输出前自检：是否覆盖全部关键项、数值是否与文档声明一致、是否有遗漏；
   - 自检结果不需要输出，但要求模型在自检通过后才返回结果。

五、本软件的提取任务适配

1. 工程概况提取（替代“项目概述提取”）
   - 目标定位：识别工程名称、地点、规模、结构形式、专项工程参数、地质水文、周边环境、参建单位相关章节；
   - 提取内容：工程名称、工程地点、建设规模、结构形式、专项工程特征参数（基坑深度、模板高度/跨度/荷载、脚手架类型/高度、吊装参数等）、地质条件、水文条件、周边环境、气候特征、参建单位；
   - 处理规则：数值保留原文单位，缺失标注“未提及”；
   - 输出示例：给出基坑工程与脚手架工程两个示例；
   - 验证步骤：自检是否覆盖九大章节工程概况所需的全部字段。

2. 专项方案类型识别（替代“技术评分要求提取”之一）
   - 目标定位：识别工程名称、专项工程描述、施工内容相关章节；
   - 提取内容：方案类型（基坑/模板/脚手架/起重吊装/拆除/其他）、主要施工内容、工序、工艺、对象；
   - 处理规则：方案类型按六大类危大工程分类匹配，无法确定时标注“待确认”；
   - 输出示例：给出“深基坑支护专项方案”“高大模板支撑专项方案”两个示例；
   - 验证步骤：自检方案类型是否与施工内容一致。

3. 危大工程判定参数提取（替代“技术评分要求提取”之二）
   - 目标定位：识别与开挖深度、支撑高度、跨度、荷载、起吊重量、搭设高度相关的章节；

七、BUG 修复重点

1. 文件解析器异常时资源未释放，导致文件句柄泄漏。
2. 表格识别失败，表格内容混入普通文本。
3. 页码标识缺失，AI 无法定位数据来源。
4. 解析失败静默返回空，下游误以为文件无内容。
5. 使用同步客户端导致并发瓶颈。
6. 流式请求异常时静默吞掉，用户不知道失败。
7. JSON 模式不支持时未降级，直接失败。
8. 提取提示词缺少验证步骤，模型输出未自检。
9. 提取字段缺失时编造，未标注“未提及”。
10. 单位不统一，数值无单位。
11. 与提取项目、目录生成、全局事实的衔接断裂。
12. 修复过程中发现的其他所有 BUG。

   - JSON 模式不支持时是否降级；

   - 缺失字段是否标注“未提及”而非编造；
   - 与提取项目、目录生成、全局事实的衔接是否正常。
3. 端到端验证：解析提取 → 提取项目 → 目录生成 → 全局事实 → 正文生成 → 图表生成 → 审核预检 → 导出 DOCX。
4. 所有测试通过，无回归。
```

## 五、优化点说明

**1. 保留“页码标识”这一关键细节**
参考文档在 PDF 解析时每页加 `--- 第 N 页 ---`，这是让 AI 能定位数据来源（如“第 5.2.3 条”）的基础。引入时保留并扩展到 Word 解析，便于后续提取任务标注“数据来源”。

**2. 保留“资源释放放在 try 与 except 两处”**
这是实际踩过坑的细节。只在 `finally` 释放不够，因为异常可能发生在 `open` 之前；只在 `try` 内释放不够，因为异常会跳过。两处都放才能保证任何路径都释放。

**3. 保留“AsyncOpenAI 异步客户端”**
参考文档明确说“因为之后要一次性编写几十万字标书，使用并发请求，必须使用 AsyncOpenAI”。本软件的正文生成、目录生成同样是高频调用，异步是基础，不能退回同步。

**4. 保留“五段式提示词方法”作为通用方法论**
参考文档的技术评分要求提取提示词采用“目标定位 → 提取内容要求 → 处理规则 → 输出示例 → 验证步骤”五段式，这是文档中最有价值的部分。引入时把它作为本软件所有提取任务的通用模板，而不是只用于一个任务。

**5. 强调“验证步骤”让模型自检**
很多提示词只告诉模型“要提取什么”，不告诉模型“提取完怎么检查”。参考文档的验证步骤让模型在输出前自检是否覆盖、数值是否一致、是否遗漏，这是提高提取质量的关键，引入时保留并扩展到所有提取任务。

**6. 把“项目概述”适配为“工程概况”**
参考软件是招投标工具，提取项目名称、背景、规模、预算等；本软件是专项施工方案工具，需要提取工程名称、地点、规模、结构形式、专项工程参数、地质水文、周边环境、参建单位，对齐九大章节工程概况的字段要求。

**7. 把“技术评分要求提取”替换为五个专项提取任务**
本软件不需要技术评分要求，但需要：专项方案类型识别（决定目录模板）、危大工程判定参数提取（决定是否超危大、是否需要专家论证）、编制依据清单提取（九大章节第二章）、施工条件提取（施工组织所需）。这五个任务替代技术评分要求提取，覆盖本软件的核心提取需求。

**8. 与前期已引入的机制协同**
与 `collect_json_response` 协同（JSON 模式降级）、与提示词顺序优化协同（稳定前缀前置）、与目录生成协同（专项方案类型决定模板、危大判定影响目录深度）、与全局事实协同（工程概况数值作事实候选、危大参数作判定依据）。
