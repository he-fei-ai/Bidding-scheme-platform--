# 提示词顺序优化与缓存命中：文档梳理与引入方案

## 一、参考文档核心机制梳理

这份文档解决的是"AI 应用成本大头在输入"的问题，核心结论是：**节约成本最好的办法不是精简提示词，而是调整提示词顺序，让服务商的 Prompt Cache 命中。**

### 1. 为什么吃不到缓存

大多数服务商的缓存看的是**请求前缀**，不是"内容一样就行"。如果一份很长的稳定文本被放在提示词后面，而前面先拼了很多每次都不一样的说明，服务商看到的是"两个不一样的请求，后面刚好有一大段相同"，缓存命中率自然高不起来。

### 2. 四条核心原则

| 原则                         | 说明                                                         |
| ---------------------------- | ------------------------------------------------------------ |
| system 只放稳定规则          | 通用角色、通用写作规范、通用输出要求，不放本次请求特有差异   |
| 最大最稳定的上下文尽量前置   | 招标文件全文、项目概述、技术评分要求、目录树、上级章节链     |
| 任务差异尽量放最后           | 提取项目概述、提取评分要求、生成目录、生成某章节正文         |
| 同一份数据的组织格式保持稳定 | 标题写法一致、换行数量一致、列表顺序一致、strip 一致、不塞随机信息时间戳 |

### 3. 三个改造案例

**案例一：文档解析（同一份招标文件做两次分析）**
旧写法：两次 `system_prompt` 不同 + `user_prompt` 前缀不同 + 大文本 `file_content` 放后面。
新写法：`system` 统一 + 全文单独一条 `user` + 任务说明单独一条 `user`。共同前缀清晰，缓存可命中。

**案例二：提纲编写（同一份 overview/requirements 反复使用）**
旧写法：把 overview + requirements 拼成一个大 `user_prompt`。
新写法：`system` 一条 + 项目概述一条 + 技术评分要求一条 + 任务说明一条。普通生成与旧目录扩写可共享前缀。

**案例三：正文编写（调用次数最多、重复上下文最长）**
旧写法：project_overview + parent_chapters + sibling_chapters + 正文规则全拼进一个大 `user_prompt`。
新写法：`system` 一条 + project_overview 一条 + parent_context 一条 + sibling_context 一条 + 当前章节任务一条。同一父章节下的多个叶子节点，前三条高度一致，只有最后一条变化最大。

### 4. 实测结果

OpenRouter + gemini-2.5-flash 解析几万字招标文件：
- 第一次：`prompt_tokens 19349`，`cached_tokens 0`，`cost 0.0058047`
- 第二次：`prompt_tokens 19737`，`cached_tokens 19442`，`cost 0.00067176`

输入成本降至约九分之一，接近 10 倍差距。

### 5. 缓存生效的四个条件

前缀稳定、大文本够长、第二次请求跟得足够快、模型和服务商本身支持缓存。满足这四个条件，省下来的钱可以直接从日志里看到。

### 6. 一个需要注意的细节

参考文档中 `sibling_chapters` 是**排除当前章节**后拼接的，这意味着同一父章节下不同叶子节点的 `sibling_context` 并不相同，缓存只能部分命中。这是一个可以进一步优化的点，后文引入方案中会给出改进建议。


## 二、引入提示词（完整版）

```text
请将参考文档《提示词顺序优化，让缓存命中，输入成本直降10倍》的四条原则与三个改造案例引入本软件，优化本软件所有高频 AI 任务的提示词组织顺序，提升缓存命中率、降低输入成本。

核心目标：
1. 把大且稳定的上下文前置，把任务差异放最后；
2. 同一份数据的组织格式保持稳定，避免缓存前缀被破坏；
3. 在日志中可观测缓存命中情况与成本变化；
4. 不改变生成质量，只优化提示词组织顺序与成本。

一、任务计划（必须先执行）
使用 EnterPlanMode 或 TodoWrite 制定计划，列出：本软件所有高频 AI 任务清单、每个任务的稳定上下文与任务差异划分、当前提示词组织方式、缓存命中现状、改造优先级（P0/P1/P2）、验证方式与回滚方案。

二、应用四条核心原则

1. system 只放稳定规则
   - 通用角色定义、通用写作规范、通用输出要求；
   - 不放本次请求特有的差异（如当前章节ID、用户额外要求、字数标准）；
   - 同一任务的所有请求，system 消息保持完全一致，包括标点、换行、空格。

2. 最大最稳定的上下文尽量前置
   - 专项方案名称与主要施工内容、项目概述；
   - 九大章节标准、适用规范清单；
   - 目录树结构（如每章节都需要）；
   - 全局事实标题清单（如每章节都需要，用于编排判断）；
   - 上级章节链（同一父章节下的多个叶子节点，上级章节完全一致）；
   - 这些内容越稳定、越长、越可能重复利用，越应该往前放。

3. 任务差异尽量放最后
   - 当前章节ID、标题、描述、在目录树中的位置；
   - 当前章节选中的全局事实字段（按“章节 → 所需事实”映射表取出，只注入当前章节）；
   - 配图意图（图表类型、标题、数据来源）；
   - 字数标准；
   - 用户额外要求；
   - 这些都是每次请求最容易变化的内容，放最后。

4. 同一份数据的组织格式保持稳定
   - 标题写法一致（如统一用“项目概述信息：”而非有时“项目概述：”有时“项目概述信息：”）；
   - 换行数量一致（如统一两个换行分隔，不用有时一个有时三个）；
   - 列表顺序一致（如上级章节按目录顺序排列，不随机）；
   - strip 规则一致（如统一对字符串 strip 后再拼接，不用一会儿 strip 一会儿不 strip）；
   - 不把随机信息、时间戳、request_id、随机数塞进共享上下文。

三、本软件高频 AI 任务的改造

1. 解析提取任务
   - 稳定前缀：system 规则、全文内容（单独一条 user）；
   - 任务差异：提取项目概述 / 提取专项工程特征参数 / 提取招标要求 等任务说明（最后一条 user）；
   - 效果：同一份文件做多次分析时，全文前缀命中缓存。

2. 目录生成任务
   - 稳定前缀：system 规则、专项方案名称与主要施工内容、项目概述、九大章节标准、适用规范清单；
   - 任务差异：生成一级目录 / 生成某章二三级目录 / 旧目录扩写 等任务说明、other_outline、json_outline 框架（最后一条 user）；
   - 效果：同一方案反复生成目录、旧目录扩写时，稳定前缀命中缓存。

3. 全局事实提取任务
   - 稳定前缀：system 规则、专项方案名称与主要施工内容、项目概述、全文内容；
   - 任务差异：提取哪类事实（工程概况类 / 编制依据类 / 施工计划类等）、已有事实清单（最后一条 user）；
   - 效果：同一方案多次提取不同类型事实时，稳定前缀命中缓存。

4. 正文生成任务（调用次数最多，优化价值最大）
   - 稳定前缀：system 规则、专项方案名称与主要施工内容、九大章节标准、适用规范清单、上级章节链（同一父章节下所有叶子节点一致）；
   - 任务差异：当前章节ID、标题、描述、当前章节选中的全局事实字段、配图意图、字数标准、用户额外要求（最后一条 user）；
   - 关键改进：sibling_chapters 改为传入完整兄弟列表（包含当前章节），在任务说明中写“请避免与除当前章节外的其他章节内容重复”，而不是预先排除当前章节。这样同一父章节下所有叶子节点的 sibling_context 完全一致，缓存命中率更高。
   - 效果：同一父章节下多个叶子节点并发生成时，稳定前缀命中缓存。

5. 正文编排任务
   - 稳定前缀：system 规则、专项方案名称与主要施工内容、项目概述、九大章节标准、全局事实标题清单、上级章节链；
   - 任务差异：当前章节ID、标题、描述、同级章节列表、用户图表配置（最后一条 user）；
   - 效果：同一父章节下多个叶子节点编排时，稳定前缀命中缓存。

6. 图表生成与渲染任务
   - 稳定前缀：system 规则、图表类型标准、风格要求、Mermaid 语法约束；
   - 任务差异：当前图表源码、图表数据、图表标题（最后一条 user）；
   - 效果：同类图表生成时，稳定前缀命中缓存。

7. 审核预检任务
   - 稳定前缀：system 规则、九大章节标准、适用规范清单、全局事实清单；
   - 任务差异：待审核的章节内容、审核范围（最后一条 user）；
   - 效果：多章节审核时，稳定前缀命中缓存。

四、缓存可观测性

1. 日志记录
   - 每次 AI 调用记录：prompt_tokens、cached_tokens、cost、任务类型、章节ID；
   - 计算缓存命中率：cached_tokens / prompt_tokens；
   - 计算成本节省：与无缓存情况对比。

2. 监控指标
   - 各任务类型的缓存命中率；
   - 各任务类型的输入成本；
   - 缓存命中率趋势，识别退化。

3. 告警
   - 缓存命中率低于阈值告警；
   - 输入成本异常升高告警。

五、验证方法

1. 改造前后对比
   - 对同一批任务，分别用旧提示词顺序与新提示词顺序各执行一次；
   - 对比 prompt_tokens、cached_tokens、cost；
   - 对比生成质量（内容完整性、一致性、字数），确认只优化成本不改质量。

2. 缓存命中测试
   - 连续两次调用同一任务，第二次应命中缓存；
   - 改变任务差异部分（如换一个章节），稳定前缀部分仍应命中缓存；
   - 改变稳定前缀部分（如改一个字），缓存应失效。

3. 格式稳定性测试
   - 连续多次调用同一任务，稳定前缀的字节级内容应完全一致；
   - 用 diff 工具比对两次请求的稳定前缀部分，应无差异。

六、适配本软件的注意事项

1. 与全局事实“编排选事实、生成注事实”机制协同
   - 全局事实标题清单可放在稳定前缀（每章节都需要，用于编排判断）；
   - 全局事实具体字段按章节变化，必须放在任务差异部分；
   - 不要把全部全局事实注入稳定前缀，导致前缀过长且包含大量无关内容。

2. 与顺序生成、并发分批协同
   - 按 sort_order 顺序生成时，同一父章节下的叶子节点可连续调用，充分利用缓存；
   - 并发分批时，同一批内的叶子节点应属于同一父章节，使稳定前缀一致。

3. 与九大章节标准、适用规范协同
   - 九大章节标准、适用规范清单对所有章节一致，放在稳定前缀；
   - 不要在任务差异部分重复写九大章节标准。

4. 与去 AI 化、语言质量要求协同
   - 去 AI 化的写作规范放在 system 中，保持稳定；
   - 不要在每次请求中重复不同的写作要求。

七、BUG 修复重点

1. system 中混入了本次请求特有的差异内容。
2. 大且稳定的上下文被放在任务差异之后。
3. 同一份数据的组织格式不稳定（标题写法、换行、列表顺序、strip 规则不一致）。
4. 共享上下文中混入了时间戳、request_id、随机数。
5. sibling_chapters 排除当前章节导致缓存前缀不一致。
6. 全局事实全部注入稳定前缀，导致前缀过长且包含大量无关内容。
7. 缓存可观测性缺失，无法判断优化效果。
8. 改造后生成质量下降（内容完整性、一致性、字数变化）。
9. 修复过程中发现的其他所有 BUG。

八、验证与回归

1. 每完成一项改造，运行相关测试，建立基线并对比。
2. 验证：
   - 四条原则是否落实（system 稳定、稳定上下文前置、任务差异后置、格式稳定）；
   - 各高频任务的稳定前缀与任务差异是否划分正确；
   - 缓存命中率是否提升、输入成本是否下降；
   - 生成质量是否保持（内容完整性、一致性、字数）；
   - sibling_chapters 改进是否生效；
   - 缓存可观测性是否生效。
3. 端到端验证：解析提取 → 提取项目 → 目录生成 → 全局事实 → 正文生成 → 图表生成 → 审核预检 → 导出 DOCX。
4. 所有测试通过，无回归。

九、输出要求

用中文回答，代码注释用中文。先输出各高频任务的稳定前缀与任务差异划分方案，再输出提示词改造代码与文件路径，再输出缓存可观测性方案，再输出改造前后成本对比与质量对比，再输出验证结果。提供任务前缀划分表、缓存命中率对比表、成本对比表。新增配置项说明默认行为与兼容性。所有结论必须有日志数据、代码依据或测试结果支撑。
```

## 四、优化点说明

**1. 保留四条原则作为通用规则**
参考文档最有价值的不是某个具体改造，而是四条可复用的原则：system 只放稳定规则、稳定上下文前置、任务差异后置、格式保持稳定。引入时把四条原则作为本软件所有高频 AI 任务的通用规则，而不是只改造文档提到的三个任务。

**2. 覆盖本软件全部高频 AI 任务**
参考文档只讲了文档解析、提纲编写、正文编写三个任务；本软件高频任务更多（解析提取、目录生成、全局事实提取、正文生成、正文编排、图表生成、审核预检），逐一定义稳定前缀与任务差异划分，避免只改一部分。

**3. 指出并改进 sibling_chapters 的缓存缺陷**
参考文档中 `sibling_chapters` 排除当前章节，导致同一父章节下不同叶子节点的 `sibling_context` 不同，缓存只能部分命中。这是文档未意识到的细节，引入时改为传入完整兄弟列表（包含当前章节），在任务说明中说明排除当前章节，使 `sibling_context` 完全一致，缓存命中率更高。

**4. 明确全局事实的划分边界**
本软件有“编排选事实、生成注事实”机制，全局事实标题清单每章节都需要，可放稳定前缀；但全局事实具体字段按章节变化，必须放任务差异。明确这个边界，避免把全部全局事实注入稳定前缀导致前缀过长且包含大量无关内容，反而降低缓存价值。

**5. 增加缓存可观测性**
参考文档靠手动看日志判断缓存效果；本软件应把 `prompt_tokens`、`cached_tokens`、`cost`、任务类型、章节ID 记录到日志，计算命中率与成本节省，设置告警，让缓存优化可量化、可持续。

**6. 强调“只优化成本不改质量”**
提示词顺序调整如果处理不当，可能影响生成质量（如把九大章节标准从 system 移到任务差异，可能导致模型忽略）。引入时明确验证方法：改造前后对同一批任务各执行一次，对比成本的同时对比生成质量，确认只优化成本不改质量。

**7. 补齐格式稳定性的具体检查项**
参考文档说“格式保持稳定”但未给出检查方法；引入时明确标题写法、换行数量、列表顺序、strip 规则四项，并要求用 diff 工具比对两次请求稳定前缀的字节级一致性，避免“看起来差不多但字节不同”导致缓存失效。
