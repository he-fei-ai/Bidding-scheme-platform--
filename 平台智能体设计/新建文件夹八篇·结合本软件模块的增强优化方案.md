## 二、增强优化项（按优先级）

### P0-1 ｜E-1：落地 Agent 一致性修复（A1「Agent修复」原文）

**现状**：一致性修复只有普通模式（分组审计 + 精确补丁）。文章明确指出普通模式处理几十万字时要「反复分组、审计、返回 JSON、逐条修复」，Agent 模式把「超长上下文问题」转化为「搜索文件并修改文件」，效率与覆盖面都更好。

**方案**（复用已有 Agent 基建，不新造轮子）：

1. 新增 `POST /consistency/agent/{project_id}`（`routers/consistency.py`）：
   - 准备两个工作区文件：`global-facts.md`（全局事实 + 招标文件关键解析结果）、`technical-plan.md`（技术方案完整正文，每个章节带固定开始/结束标记与章节 ID）；
   - 调用既有 Agent 运行时（按 `doc/AIAgentRuntime设计方案.md` / `doc/yibiao-opencode-server-aiservice-proxy-plan-v4-final.md` 的 opencode 隔离运行时）执行多轮修复；
   - Agent 完成后程序重新解析并校验：章节无增删/重排、标记与 ID 完整、修改在允许正文范围内、Diff 仅落变化的叶子小节；
   - 校验失败 → 保留原正文并上报；成功 → 走既有 `refresh_conflict_states()` 收敛冲突状态。
2. 复用点：章节标记契约可复用导出侧章节定位逻辑；冲突状态刷新复用 `consistency_repair.refresh_conflict_states`。
3. **验收**：10 万字项目 Agent 修复目标 < 15 分钟；修复后叶子数/顺序/ID 与修复前全等；幻觉修改 0 落库。

### P0-2 ｜E-2：编排 JSON 补齐 knowledge.item_ids 通道（A8 + 非 RAG 知识库主张）

**现状**：《易标对照差距分析报告-2026-10-05》P-10 指出编排输出结构只有 `table/mermaid/image`，无 `knowledge` 字段——「非 RAG 知识库」在主流程落空，正文生成没有知识素材通道。

**方案**：

1. `_ORCH_SYSTEM` 输出结构增加 `"knowledge": {"item_ids": [...]}`；编排请求上下文注入本项目的轻量知识条目清单（id + 标题 + 一句话摘要，来自 `services/knowledge.py`，不给全文）。
2. 生成正文时按 `item_ids` 取条目内容注入：`build_chapter_content_messages` 增加可选 knowledge 消息段（仍守稳定前缀原则：知识条目按 id 排序拼接，保证同章节多次请求前缀一致）。
3. 兜底：编排失败降级 `_fallback_plan` 时 knowledge 置空；知识条目被删除时按 id 取不到即跳过，不阻塞生成。
4. **验收**：带知识库项目生成时，命中条目的小节正文引用素材；单测覆盖「编排输出 knowledge 解析 + 注入 + 条目缺失降级」。

### P0-3 ｜E-3：缓存成本度量闭环（A6 实测章节的工程化）

**现状**：分层消息结构与 `_resolve_shared()` 共享片段已落地；但仅 Anthropic 走 `cache_control`（provider 层 base_url 判断），OpenAI 兼容供应商无任何缓存命中观测——文章证明缓存可省 90% 输入成本，本软件却「省没省不知道」。

**方案**：

1. **采集**：provider 层透传 `usage.prompt_tokens_details.cached_tokens`（OpenAI 兼容）与 Anthropic `cache_read_input_tokens`，落 `usage_stats` / `ai_monitor`，按 workflow 维度（analysis/outline/content/orchestration/audit）聚合。
2. **规范**：把 A6 四规则固化为检查脚本（scripts/）：① system 只放稳定规则；② 大稳定上下文前置；③ 任务差异最后；④ 同数据组织格式稳定（strip/换行/顺序一致）。重点盯 `build_chapter_content_messages` 的拼接不得插入时间戳/随机数。
3. **看板与告警**：`routers/monitor.py` 增加缓存命中率指标；正文生成阶段命中率 < 50% 时 SSE warning（大概率是前缀被破坏）。
4. **验收**：同一项目连续两次正文生成日志可见 cached_tokens；监控页有命中率曲线。


### P1-4 ｜E-4：超长正文「先骨架再填空」（A8 超长文本机制，差距报告 P-12）

**现状**：正文按叶子节点独立生成，跨章叙事连贯仅靠父子章节列表注入；几十万字时存在「各章各自成文、缺少全篇骨架」的风险。

**方案**：

1. 正文编排阶段新增一步「全篇骨架」：对一级/二级章节生成 3–5 句的篇章级叙事骨架（各章定位、推进逻辑、承上启下句式约定），一次性生成、落库复用。
2. `build_chapter_content_messages` 在父子章节消息后注入「全篇骨架（本章节相关段）」消息位——骨架内容稳定，不破坏缓存前缀。
3. 单章重生成/扩写走同一骨架，保证重生成章节仍贴合全篇。
4. **验收**：同一项目骨架只生成一次并复用；抽章重生成后前后文衔接人工评审通过。

### P1-5 ｜E-5：事实清单 ↔ 审计结果双向回流（A1 闭环补全）

**现状**：事实提取 → 编排注入 → 事后审计链路已通；但审计发现「事实清单之外的新不一致」时没有回流机制，扩写场景「原方案优先保留」也缺校验。

**方案**：

1. 审计（`ConsistencyAuditor.extract_facts_from_text`）发现的高频稳定取值（同一数值出现 ≥ N 章且无冲突）→ 提示用户「是否沉淀为全局事实」，一键入清单后走既有 dedup/normalize。
2. 扩写链路（`workflows_expand.py`）生成前对比「原方案人员/设备/周期/服务承诺」与事实清单，存在冲突时强制进入用户确认，不允许静默以清单覆盖原方案承诺。
3. **验收**：审计 → 沉淀 → 再生成不再复现同类冲突；扩写冲突确认有 UI 留痕。

### P1-6 ｜E-6：文章方法论复用到平台特有模块

### P2-7 ｜E-7：图表链路补课（A8 关联，承接图表模块调研报告既有结论）

1. `chart_validators.py` v3.1 全套校验接入生成主链路（当前零接入）；
2. `repair_mermaid` 按原设计补 P0–P4 分级修复 + 3 轮兜底（当前仅去围栏/压空行、修复 1 次）；
