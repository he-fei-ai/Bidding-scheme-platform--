# 弱模型稳定输出复杂 JSON：文档梳理与引入方案

## 一、参考文档核心机制梳理

这份文档解决的是“弱模型生成复杂 JSON 不稳定、质量靠抽卡”的问题。核心结论是：**弱模型不是不能用，而是不能裸用；稳定性不靠神奇 Prompt，靠完整工作流。**

### 1. 弱模型常见的七类问题

JSON 语法错误（少逗号少括号）、外面套 markdown 代码块、返回解释文字、字段名写错（`children` 写成 `child`）、只生成两级没达到三级、一级目录和评分项对不上、分步生成时编号混乱。

### 2. 完整工作流（九步闭环）

原来：用户输入 → 模型生成 → 返回结果。
现在：用户输入 → 模型生成 → JSON 解析 → Schema 校验 → 业务校验 → JSON 修复 → 多轮重试 → 分步生成 → 目录审核 → 建议回灌 → 二次生成 → 返回结果。

**模型不是“答一次就结束”，而是有批改、有返工、有兜底。**

### 3. 四个标准结构（Pydantic 定义）

- `OutlineItem`：id、title、description、source_requirement_id、source_requirement_title、children、content；
- `OutlineResponse`：outline 列表；
- `OutlineChildrenResponse`：children 列表（分步生成用）；
- `OutlineReviewResponse`：passed + suggestions（审核用）。

**关键认知：合法 JSON ≠ 可用 JSON。** 只有一级目录的 JSON 语法合法，但不满足三级结构，必须业务校验（`_validate_complete_outline` 检查 `_outline_depth >= 3`）。

### 4. 统一封装 `collect_json_response`

所有 JSON 输出走同一个函数：请求模型 → 优先 JSON 模式 → 不支持 `response_format` 时自动降级为普通请求 → 提取返回中的 JSON → Pydantic 校验 → 业务校验 → 失败进入修复流程 → 连续失败抛错。

**降级不是功能降级，而是兼容不同模型接口**，不把系统稳定性绑定在 JSON 模式上。

### 5. JSON 修复助手（定向修复，不推倒重来）

修复提示词五条要求：优先最小必要修改不整体重写；保留原有结构字段值节点顺序；缺必填字段结合上下文补齐不用空字符串敷衍；修正多余说明/代码块包裹/字段名错误/children 结构不规范/顶层包裹错误；只返回修复后的完整 JSON。

修复时传三部分信息：目标结果类型、当前校验问题、模型刚才返回的原始内容。

**弱模型生成复杂 JSON 不稳定，但修一个已接近正确的 JSON，成功率高很多。**

### 6. 校验问题格式化（明确告诉模型）

`_format_json_issues` 把 JSON 解析错误和 Pydantic 校验错误格式化成可读问题。比如模型少了 `description` 字段，修复助手拿到的不是“格式不对”，而是 `outline.0.children.1.description: Field required`。**模型知道具体哪里错，修复成功率自然更高。**

### 7. 完整目录失败切换分步生成（兜底策略）

一次性生成失败 → 切换分步：先生成一级目录 → 遍历每个一级目录单独生成二三级 → 组装 → 程序统一重编号 → 最后完整目录校验。**弱模型一次生成不了大 JSON，就让它每次只生成一小段。**

### 8. 程序统一重编号（不信任模型）

`_renumber_items` 递归重排：一级用 `str(index)`，子级用 `parent_prefix.index`。文档明确指出：“即使提示词告诉了模型你生成的是第二章，返回的编号仍然从 1 开始，甚至乱编号。”**能用代码保证的事情，就不要交给模型保证。**

### 9. 目录审核 + 建议回灌

`OutlineReviewResponse` 返回 `passed` + `suggestions`。审核不通过时，把 suggestions 回灌给生成 Prompt 重新生成。**JSON 格式正确不代表目录质量正确**，可能漏评分项、一级目录对不上。

### 10. 一一对应模式（程序锁死一级目录）

先从评分要求提取评分大类 → 程序直接构造一级目录（标题、顺序、关联评分项锁死）→ 模型只生成二三级 → 校验一级目录与评分大类完全一致。**不要让模型决定所有事情，能由程序确定的结构就用程序确定。**

### 11. 九条工程原则

提示词要明确但不能只靠提示词；所有 JSON 输出走统一解析校验；校验不只看语法还看业务规则；失败优先修复已有结果不推倒重来；修复时把具体错误告诉模型；大 JSON 失败拆小 JSON；编号映射等确定性逻辑交给程序；生成后要审核且建议能回流；长流程通过 SSE 告诉用户进度。

## 三、引入提示词（完整版）

```text
请将参考文档《如何让弱模型也能稳定输出复杂 JSON》的九步工作流、四个标准结构、统一封装函数、JSON 修复、业务校验、分步兜底、程序重编号、目录审核、一一对应模式、九条工程原则引入本软件的目录生成模块，适配“建筑工程专项施工方案编写”定位。

核心目标：弱模型也能稳定输出 L1 至 L5 的复杂目录 JSON，不依赖模型能力抽卡，靠工作流保证稳定性。

一、任务计划（必须先执行）
使用 EnterPlanMode 或 TodoWrite 制定计划，列出：目录生成模块现有实现、九步工作流的落地位置、四个标准结构的适配点、统一封装函数的改造范围、与前期已引入的两套方案与五个机制的协同方式、与九大章节标准/L2数量3~5/L4数量4~7/L5深度的衔接、风险点与验证方式、执行顺序与优先级（P0/P1/P2）。

二、定义四个标准结构（Pydantic 或等价）

1. OutlineItem：id、title、description、source_chapter_id（关联九大章节）、source_chapter_title、children、content、sort_order。
2. OutlineResponse：outline 列表。
3. OutlineChildrenResponse：children 列表（分步生成用）。
4. OutlineReviewResponse：passed + suggestions（审核用）。

三、统一封装 collect_json_response 等价函数

1. 所有 JSON 输出走同一函数，包括目录生成、全局事实提取、正文编排、审核预检等。
2. 流程：请求模型 → 优先 JSON 模式 → 不支持 response_format 时自动降级为普通请求 → 提取返回中的 JSON → Pydantic 校验 → 业务校验 → 失败进入修复流程 → 连续失败抛错。
3. 降级不是功能降级，是兼容不同模型接口，不把系统稳定性绑定在 JSON 模式上。
4. 记录日志：是否使用 JSON 模式、是否降级、校验失败类型、修复次数、最终结果。

四、业务校验（合法 JSON ≠ 可用 JSON）

1. 目录不能为空。
2. 目录深度必须达到 L5（替换文档中的三级）。
3. L1 必须覆盖九大章节（工程概况、编制依据、施工计划、施工工艺技术、安全保证措施、人员配备、验收要求、应急处置、计算书与图纸）。
4. L1 下 L2 数量必须在 3~5 项。
5. L2 下 L4 数量必须在 4~7 项。
6. L5 必须存在且为叶子节点。
7. 编号连续、不重复、不跳号。
8. 业务校验不通过时，错误信息要具体到路径与原因。

五、JSON 修复助手（定向修复）

1. 修复提示词五条要求：优先最小必要修改不整体重写；保留原有结构字段值节点顺序；缺必填字段结合上下文补齐不用空字符串敷衍；修正多余说明/代码块包裹/字段名错误/children 结构不规范/顶层包裹错误；只返回修复后的完整 JSON。
2. 修复时传三部分信息：目标结果类型（完整目录/一级目录/章节子目录）、当前校验问题、模型刚才返回的原始内容。
3. 修复后重新走 Pydantic 校验与业务校验，通过则接受，失败则进入重试。

六、校验问题格式化（明确告诉模型）

1. JSON 解析错误：格式化行号、列号、错误信息。
2. Pydantic 校验错误：格式化错误路径（如 outline.0.children.1.description）与错误消息。
3. 业务校验错误：格式化具体规则与违反位置（如“L2 数量 3~5，第 2 章下有 6 个 L2”）。
4. 修复助手拿到具体错误位置，而不是“格式不对”，提高修复成功率。

七、多轮重试与分步兜底

1. 重试机制：校验失败 → 修复 → 再校验 → 失败重试，最多 3 次；连续失败抛出明确错误。
2. 完整目录失败切换分步生成：一次性生成完整目录失败 → 切换为分步：先生成一级目录 → 遍历每个一级目录单独生成下级目录 → 组装 → 程序统一重编号 → 最后完整目录校验。
3. 分步生成时每章单独走 collect_json_response，避免一次性大 JSON 失败。
4. 分步生成时传入 other_outline 防重复（与前期已引入的机制协同）。

八、程序统一重编号（不信任模型）

1. 递归重排：一级用 str(index)，子级用 parent_prefix.index。
2. L1 中文数字（第一章）、L2 阿拉伯数字（1）、L3 带点（1.1）、L4（1.1.1）、L5（1.1.1.1.1）。
3. 不信任模型输出的编号，无论提示词怎么写，最终由程序统一重排。
4. 重排后校验编号连续、不重复、不跳号。

九、目录审核 + 建议回灌

1. 审核提示词：严格审核目录是否符合专项施工方案九大章节标准；检查是否完整覆盖九大章节；检查 L1 名称是否专业准确；检查层级是否清晰达到 L5；检查 L2 数量 3~5、L4 数量 4~7；检查是否存在明显遗漏错位重复；只返回 JSON {passed, suggestions}；不通过时 suggestions 给出具体可执行的修改建议。
2. 审核不通过时，把 suggestions 回灌给生成 Prompt 重新生成。
3. 二次生成后再次审核，仍不通过则标记待人工介入，不无限循环。

十、一一对应模式（适配为九大章节对齐模式）

1. 先从专项施工方案标准中提取九大章节（固定，不需要模型提取）。
2. 程序直接构造一级目录，标题、顺序、关联章节都锁死。
3. 模型只负责生成每个一级目录下的 L2 至 L5 子目录。
4. 校验一级目录与九大章节完全一致。
5. 方案类型特殊章节可在此基础上增补，但不删减九大章节。
6. 核心思想：不要让模型决定所有事情，能由程序确定的结构就用程序确定。

十一、九条工程原则落地

1. 提示词要明确，但不能只靠提示词。
2. 所有 JSON 输出必须走统一解析和校验。
3. 校验不只看语法，还要看业务规则。
4. 失败后优先修复已有结果，不推倒重来。
5. 修复时把具体错误原因告诉模型。
6. 大 JSON 生成失败，拆成多个小 JSON。
7. 编号、映射关系等确定性逻辑尽量交给程序。
8. 生成后要审核，审核建议要能回流到下一轮生成。
9. 长流程通过 SSE 告诉用户系统正在做什么。

十二、与前期已引入机制的协同

1. 与两套方案协同：一次性生成与分步生成不是二选一，而是“一次性优先，失败自动切分步”的兜底关系。
2. 与五个关键机制协同：代码生成框架 + AI 补全、check_json 校验、重试、other_outline 防重复、并发生成，全部纳入 collect_json_response 与分步生成的统一流水线。
3. 与提示词顺序优化协同：稳定前缀（system、方案名称、九大章节标准）前置，任务差异（当前章节、校验问题、修复指令）后置，保证修复与重试时缓存命中。
4. 与全局事实、正文生成协同：目录生成结果作为全局事实设定输入；sort_order 写入供正文按序生成；节点 ID 与正文、图表、导出编号一致。

十三、BUG 修复重点

1. 只靠提示词不靠工作流，弱模型输出不稳定。
2. 合法 JSON 未做业务校验，只生成部分层级也通过。
3. 统一封装函数缺失，各模块各自处理 JSON。
4. JSON 模式不支持时未降级，直接失败。
5. 修复助手推倒重来而非定向修复。
6. 修复时未传具体错误，模型反复犯同样错误。
7. 完整目录失败未切换分步生成。
8. 分步生成后未重编号，模型输出的编号混乱。
9. 目录审核缺失或审核建议未回灌。
10. 一一对应模式缺失，一级目录被模型随意合并改写。
11. 与九大章节标准、L2/L4 数量约束、L5 深度的衔接断裂。
12. 修复过程中发现的其他所有 BUG。

十四、验证与回归

1. 每完成一项引入，运行相关测试，建立基线并对比。
2. 验证：
   - 四个标准结构是否完整、Pydantic 校验是否生效；
   - 业务校验是否覆盖 L5 深度、九大章节覆盖、L2 数量 3~5、L4 数量 4~7、编号连续；
   - collect_json_response 是否统一封装、JSON 模式是否优先、降级是否生效；
   - JSON 修复是否定向修复、是否传递具体错误、修复后是否重新校验；
   - 多轮重试是否生效、最多 3 次、连续失败是否抛出明确错误；
   - 完整目录失败是否切换分步生成、分步生成是否组装并重编号；
   - 程序重编号是否生效、编号是否连续；
   - 目录审核是否生效、建议是否回灌、二次生成是否执行；
   - 一一对应模式是否锁死一级目录、校验是否一致；
   - 九条工程原则是否落地；
   - 与前期机制的协同是否正常。
3. 用弱模型（如 LongCat-Flash-Lite 或等价的低价模型）实测，验证稳定性。
4. 端到端验证：解析提取 → 提取项目 → 目录生成 → 全局事实 → 正文生成 → 图表生成 → 审核预检 → 导出 DOCX。
5. 所有测试通过，无回归。

十五、输出要求

用中文回答，代码注释用中文。先输出九步工作流的落地方案，再输出四个标准结构与统一封装函数的实现方案，再输出 JSON 修复、业务校验、分步兜底、程序重编号、目录审核、一一对应模式的实现方案，再输出与前期机制的协同方案，再输出代码修改方案与文件路径，再输出弱模型实测结果与验证对比。提供标准结构定义、collect_json_response 流程说明、校验规则清单、验证对比表。新增配置项说明默认行为与兼容性。所有结论必须有代码依据或测试结果支撑。
```

递归重排，L1 中文数字、L2 阿拉伯数字、L3 带点、L4、L5 按标准；不信任模型输出，无论提示词怎么写最终程序重排；重排后校验编号连续。

八、目录审核 + 建议回灌

九、一一对应模式
从专项施工方案标准提取九大章节（固定不需模型提取）→ 程序直接构造一级目录锁死标题顺序 → 模型只生成 L2 至 L5 → 校验一级目录与九大章节一致；方案类型特殊章节可增补不删减。

## 五、优化点说明

**1. 把“三级目录”适配为“L1 至 L5”**
参考文档统一三级深度；本软件要求生成至 L5 级，L5 为正文生成最小叶子节点。业务校验中的深度检查从 `_outline_depth < 3` 改为 `< 5`，并新增 L2 数量 3~5、L4 数量 4~7 的检查。

**2. 把“评分要求/评分大类”适配为“九大章节”**
参考软件是招投标工具，一级目录对齐技术评分要求；本软件是专项施工方案工具，一级目录必须对齐九大章节标准。一一对应模式适配为“从专项施工方案标准提取九大章节（固定，不需要模型提取）→ 程序直接构造一级目录锁死 → 模型只生成 L2 至 L5”。

**3. 与前期已引入的两套方案与五个机制协同**
第二期讲了“一次性生成 + 分步生成”两套方案与“代码框架 + AI 补全、check_json、重试、other_outline、并发生成”五个机制；第五期是更完整的工程框架，把第二期机制纳入统一流水线，并新增 JSON 修复、业务校验、目录审核、一一对应模式。引入时明确“一次性优先，失败自动切分步”的兜底关系，避免两期内容互相冲突。

**4. 保留 `collect_json_response` 统一封装这一核心设计**
参考文档最有工程价值的设计是把所有 JSON 输出收敛到一个函数，统一处理“请求 → JSON 模式 → 降级 → 提取 → Pydantic → 业务校验 → 修复 → 抛错”。引入时扩展为覆盖本软件全部 JSON 输出场景（目录、全局事实、正文编排、审核），避免各模块各自处理 JSON 导致标准不一致。

**5. 保留“合法 JSON ≠ 可用 JSON”这一关键认知**
很多工程只做 `json.loads()` 就算通过，导致只生成部分层级的 JSON 也能过。引入时明确业务校验清单（L5 深度、九大章节覆盖、L2/L4 数量、编号连续），把业务校验作为 Pydantic 校验之后的第二道门。

**6. 保留“定向修复”而非“推倒重来”**
弱模型生成复杂 JSON 不稳定，但修一个已接近正确的 JSON 成功率高很多。修复提示词五条要求（最小必要修改、保留结构字段值、缺字段结合上下文补齐、修正具体问题、只返回 JSON）是实际踩坑总结出来的，完整保留。

**7. 保留“校验问题格式化”这一细节**
很多修复失败是因为给模型的错误信息太笼统（“格式不对”），模型不知道改哪里。引入时明确把 JSON 解析错误、Pydantic 错误、业务错误都格式化为具体路径与原因，让修复助手拿到 `outline.0.children.1.description: Field required` 这样的信息。

**8. 保留“程序统一重编号”**
文档明确指出“即使提示词告诉了模型你生成的是第二章，返回的编号仍然从 1 开始”。引入时明确不信任模型输出，无论提示词怎么写最终程序重排，并补充 L1 中文数字、L2 阿拉伯数字、L3 带点、L4、L5 的编号规则。

**9. 补齐与提示词顺序优化的协同**
参考文档第五期和第四期（提示词顺序优化）是配套的。引入时明确：稳定前缀（system、方案名称、九大章节标准）前置，任务差异（当前章节、校验问题、修复指令）后置，保证修复与重试时缓存命中，避免修复流程本身成为成本黑洞。

**10. 强调用弱模型实测**
文档测试用的是 LongCat-Flash-Lite。引入时明确要求用弱模型（如 LongCat-Flash-Lite 或等价的低价模型）实测稳定性，而不是只用强模型验证。强模型能过不代表弱模型能过，这是本文档的核心价值所在。
