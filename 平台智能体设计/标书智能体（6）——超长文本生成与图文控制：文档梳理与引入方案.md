# 超长文本生成与图文控制：文档梳理与引入方案

## 一、参考文档工作流程梳理

这份文档解决的是“几十万字标书里，何时配图、配在哪里、配什么图”的问题，核心是一套**预编排 + 正文生成 + 配图分离**的三阶段工作流。

### 1. 问题背景

按目录树叶子节点逐节生成正文时，配图面临三个矛盾：每个叶子节点都配图成本太高且有些章节不适合；完全交给 AI 判断会导致图片与正文无关、浪费 token、数量不可控；只设生图上限按顺序生成会导致头重脚轻。

### 2. 预编排阶段（核心创新）

**配图不是正文写完后再加，而是在正文生成前先规划好。** 拿到目录后，先对全文目录做编排，判断每个子节点是否需要知识库素材、表格、Mermaid 图、AI 生图，并给出优先级分数。

正文生成任务分为四步：收集所有叶子节点 → 对所有叶子节点做正文编排 → 根据编排结果并发生成正文 → 正文生成完成后执行配图。

### 3. 正文生成配置

```json
{
  "useAiImages": true,
  "maxAiImages": 6,
  "useMermaidImages": true,
  "tableRequirement": "heavy"
}
```

不做硬编码规则（如“标题里有流程就画流程图”），而是**让 AI 先提名，再由程序做全局控制**。表格选择“少量”时 AI 提名后程序最多选 20%，“适中”最多 40%，“大量”宽松；AI 生图 AI 可提名很多候选，最终按 `maxAiImages` 择优执行。

### 4. 正文编排 JSON 结构

每个叶子节点生成一个编排结果：

```json
{
  "knowledge": { "item_ids": ["knowledge_001"] },
  "table": { "needed": true, "purpose": "用于归纳实施步骤、责任分工和输出成果" },
  "mermaid": { "needed": false, "title": "实施流程", "code": "flowchart TD...", "priority": 3, "reason": "..." },
  "image": { "needed": true, "style": "engineering_diagram", "title": "系统部署架构", "prompt": "...", "priority": 4, "reason": "..." }
}
```

`needed: true` 只表示进入候选池，不代表一定执行；真正执行时还会过全局选择。

### 5. 正文编排提示词

编排阶段只做判断不写正文，提示词强调“克制、合情合理、不要为了形式而硬插”。Mermaid 只适合简单抽象文本节点型关系图，AI 生图适合设备、现场、系统架构等具象画面。`priority` 3 表示有价值、4 推荐、5 强推荐，只有达到 3 才将 `image.needed` 设为 true。`knowledge.item_ids` 只能从参考知识库轻量条目中选择，不编造 id。

### 6. 正文生成阶段：只写正文，不碰图片

正文生成时携带：项目概述、上级章节、同级章节、当前章节、编排选中的知识库素材、编排决定的表格需求、编排决定的配图意图、用户额外要求。

**关键设计**：预编排结果不只给程序看，也传给正文生成模型。正文知道后面要配“系统部署架构示意图”，就会先把系统分层、网络边界、服务关系讲清楚，再由图片承接，避免图文两张皮。

正文生成提示词明确：可以使用 Markdown 段落、列表、表格；表格必须服务内容不要硬插；**严禁输出 Mermaid、PlantUML、Graphviz、flowchart 等图表代码块、mermaid.ink 链接或图片 Markdown**，配图由系统另行处理；表格单元格多项内容用编号、顿号、分号或短句，不用 HTML `<br>`。

### 7. 配图阶段

正文全部生成完后才进入配图，分 Mermaid 图和 AI 生图两类。**不混在正文生成里，因为图和文字的失败成本不一样**：正文失败是真失败，配图失败不应影响正文结果。

**AI 生图流程**：用编排阶段的 `image.prompt`，再补固定风格要求（工程项目图示风格/专业实景照片风格，结构清晰、专业克制、避免品牌标识水印夸张营销元素），防止生成“宣传海报风”“科技蓝大屏风”。

**Mermaid 配图流程**：编排阶段返回的 code 不能直接相信，先校验能否渲染，不能渲染再让 AI 修复。修复提示词要求：优先 `flowchart TD`、节点 ID 只用 ASCII 字母数字下划线、中文节点标签写成 `A["中文标签"]`、不用多节点连接简写、不用分号、不输出代码围栏、复杂图简化为可渲染核心流程图。修复成功后追加到正文后面。

**Mermaid 执行链路**：页面预览前端本地渲染 → 正文存储保存代码块 → Word 导出再转图片插入，比一开始就存图片更灵活。

### 8. 最终保存与全局拍板

`mermaid.needed` 和 `image.needed` 可同时为 true，但 `illustration_type` 最终只能是一个：`ai`、`mermaid`、`none`。**AI 负责提名，程序负责拍板**。全文 80 个小节 AI 认为 20 个适合生图，但用户只允许 6 张，程序就把候选小节分段，每段选优先级最高的，避免前面章节把额度用完。

### 9. 成本控制

生图成本最低一张也要两毛钱还不能保证质量，所以严格限制数量：AI 提名候选，程序全局择优，分段控制防止头重脚轻。

二、引入预编排阶段

1. 触发时机
   - 目录生成完成后、正文生成前；
   - 先对全文目录做编排，再生成正文，最后配图。

2. 正文生成任务四步
   - 第一步：收集所有 L5 叶子节点；
   - 第二步：对所有叶子节点做正文编排；
   - 第三步：根据编排结果并发生成正文；
   - 第四步：正文生成完成后执行配图。

3. 编排配置
   - 配置结构：是否启用数据型图表、最多生成几张图表、是否启用 Mermaid、表格需求（none/light/moderate/heavy）、是否启用 AI 生图（默认关闭）；

   - 表格“少量”AI 提名后程序最多选 20%，“适中”最多 40%，“大量”宽松；
   - 图表提名后按数量上限择优执行。

4. 编排 JSON 结构（适配本软件）
   - knowledge.item_ids：引用的知识库/目录库素材 id；
   - table.needed/purpose：是否需要表格及用途；
   - mermaid.needed/title/code/priority/reason：Mermaid 图候选；
   - chart.needed/type/title/data/priority/reason：数据型图表候选（柱状/折线/饼/散点/甘特图/架构图/劳动力图表）；
   - image.needed/style/title/prompt/priority/reason：AI 生图候选（默认关闭）；
   - priority：3 有价值、4 推荐、5 强推荐，只有达到 3 才将 needed 设为 true；
   - needed: true 只表示进入候选池，不代表一定执行。

5. 编排提示词
   - 只做判断不写正文，提示词克制；
   - 只返回 JSON，不输出解释、总结或 Markdown；
   - 表格仅在明显提升表达清晰度时使用（归纳职责、步骤、参数、风险、措施、成果）；
   - Mermaid 只适合简单抽象文本节点型关系图（少量节点流程、层级、时间线、职责关系），不用于复杂工程场景或实物示意；
   - 数据型图表适合有明确数据支撑的对比、占比、趋势、分布；
   - 甘特图适合进度计划、任务依赖、里程碑；
   - 架构图适合组织机构、管理层级、系统部署、职责关系；
   - 劳动力图表适合工种配置、人数分布、峰值分析；
   - AI 生图默认关闭，启用时适合设备、现场、系统架构等具象画面；
   - 不要求用满数量上限，没有合适对象时不要硬插；
   - knowledge.item_ids 只能从参考轻量条目中选择，不编造 id。

三、引入正文生成阶段：只写正文，不碰图片

1. 上下文携带
   - 项目概述/专项方案名称与主要施工内容；
   - 上级章节、同级章节（排除当前章节）；
   - 当前章节信息（ID、标题、描述、在目录树中的位置）；
   - 编排阶段选中的知识库素材；
   - 编排阶段决定的表格需求；
   - 编排阶段决定的配图意图（图表类型、标题、数据来源或生成提示词）；
   - 全局事实相关字段（按“章节 → 所需事实”映射表注入）；
   - 九大章节必含要素清单；
   - 字数标准；
   - 用户额外要求。

2. 编排结果传给正文生成模型
   - 正文知道后面会配什么图表，提前铺垫；
   - 例如后面要配“施工工艺流程图”，正文先把工序、判断节点、流向讲清楚，再由图片承接；
   - 避免图文两张皮。

3. 正文生成提示词
   - 保留参考文档的六条核心要求（专业准确、朴实无华、正式规范不像 AI、详细具体、避免同级重复、只返回内容不生成标题）；
   - 适配补充：结合专项方案名称主要施工内容、结合适用规范、不编造关键数据；
   - 可以使用 Markdown 段落、列表、表格，表格必须服务内容不要硬插；
   - 严禁输出 Mermaid、PlantUML、Graphviz、flowchart、sequenceDiagram 等图表代码块、mermaid.ink 链接或图片 Markdown，配图由系统另行处理；
   - 表格单元格多项内容用编号、顿号、分号或短句，不用 HTML `<br>`。

四、引入配图阶段

1. 配图与正文分离
   - 正文全部生成完后再配图；
   - 图和文字的失败成本不一样：正文失败是真失败，配图失败不应影响正文结果；
   - 配图失败最多提示“这张图没生成成功，正文已保留”。

2. 配图类型
   - Mermaid 图：流程图、层级图、职责关系图；
   - 数据型图表：柱状图、折线图、饼图、散点图，使用 PIL 或等效渲染；
   - 甘特图：任务、起止时间、依赖关系、里程碑；
   - 架构图：层数、节点、关系、布局方向；
   - 劳动力图表：工种、人数、时间段、峰值；
   - AI 生图：默认关闭，启用时用编排阶段的 prompt 加固定风格要求。

3. Mermaid 校验与修复
   - 编排返回的 code 不能直接相信，先校验能否渲染；
   - 不能渲染再让 AI 修复；
   - 修复提示词要求：优先 flowchart TD、节点 ID 只用 ASCII 字母数字下划线、中文节点标签写成 A["中文标签"]、不用多节点连接简写、不用分号、不输出代码围栏、复杂图简化为可渲染核心流程图；
   - 修复成功后追加到正文后面；
   - Mermaid 执行链路：页面预览前端本地渲染 → 正文存储保存代码块 → 导出 DOCX 再转图片插入。

4. 数据型图表与 AI 生图
   - 数据型图表按编排阶段的数据来源渲染，失败降级不占图号；
   - AI 生图启用时补固定风格要求：工程资料风格、结构清晰、专业克制、适合专项施工方案插图；避免品牌标识、水印、夸张营销元素和无关文字；
   - 图表标题格式：图{章号}-{序号} {图名}；图名提取优先级：载荷 title > 图表 title > 引导语 > 类型通用名。

5. 最终保存与全局拍板
   - mermaid.needed、chart.needed、image.needed 可同时为 true，但最终采用的图表类型只能是一个（mermaid/chart/image/none）；
   - AI 负责提名，程序负责拍板；
   - 全文 N 个 L5 小节 AI 认为 M 个适合配图，但用户只允许 K 张，程序就把候选小节分段，每段选优先级最高的，避免前面章节把额度用完；
   - 保存最终编排结果，包含 plan 与 illustration_type。

五、适配本软件定位

1. 图表全部自动生成
   - 不设置人工配图、生图功能和按钮；
   - AI 生图默认关闭，启用时也是自动触发，不提供用户点击入口；
   - 图表类型限定为 Mermaid、数据型图表、甘特图、架构图、劳动力图表。

2. 与九大章节标准衔接
   - 每个 L5 章节对应九大章节之一；
   - 编排时结合九大章节必含要素判断是否需要图表；
   - 配图必须服务于方案内容，不引入与方案无关的装饰性图片。

3. 与全局事实、字数控制、顺序生成协同
   - 编排阶段可读取全局事实标题，判断哪些图表需要事实数据支撑；
   - 正文生成按 sort_order 顺序执行，配图在正文全部完成后统一执行；
   - 字数控制与配图不冲突，图表不计入正文字数。

4. 与导出 DOCX 衔接
   - Mermaid 代码块在导出时转图片插入；
   - 数据型图表导出时按需渲染；
   - 渲染失败默认跳过不占图号，除非开启 chart_fail_placeholder；
   - 不引入 Word 2010+ 专有扩展，保证 WPS/LibreOffice 兼容。

六、BUG 修复重点

1. 编排阶段缺失或时机错误，正文生成前未完成编排。
2. 编排 JSON 结构不完整，needed/priority 字段缺失。
3. 编排结果未传给正文生成模型，图文两张皮。
4. 正文生成输出了图表代码块，与配图阶段重复。
5. 配图与正文混在一起，配图失败导致正文失败。
6. Mermaid 代码未校验直接使用，渲染失败。
7. Mermaid 修复提示词缺失或修复后仍不可渲染。
8. 图表类型未限制，引入与方案无关的图表。
9. 图表数量未全局拍板，前面章节用完全部额度。
10. 图号虚跳、图题格式错误。
11. 与九大章节标准、全局事实、字数控制、导出 DOCX 的衔接断裂。
12. 修复过程中发现的其他所有 BUG。

七、验证与回归

1. 每完成一项引入，运行相关测试，建立基线并对比。
2. 验证：
   - 预编排阶段是否在正文生成前完成；
   - 编排 JSON 结构是否完整、needed/priority 是否合理；
   - 编排结果是否传给正文生成模型、正文是否围绕图表铺垫；
   - 正文生成是否只输出文字/列表/表格，未输出图表代码块；
   - 配图是否在正文全部生成后执行、失败是否不影响正文；
   - Mermaid 是否校验、修复是否生效；
   - 图表类型是否限定、数量是否全局拍板；
   - 图号是否虚跳、图题格式是否正确；
   - 与九大章节、全局事实、字数控制、导出 DOCX 的衔接是否正常。
3. 端到端验证：解析提取 → 提取项目 → 目录生成 → 全局事实 → 正文编排 → 正文生成 → 配图 → 图表生成与渲染 → 审核预检 → 导出 DOCX。
4. 所有测试通过，无回归。

八、输出要求

用中文回答，代码注释用中文。先输出预编排阶段的适配方案，再输出编排 JSON 结构与提示词适配，再输出正文生成与配图分离的落地方式，再输出全局拍板机制，再输出代码修改方案与文件路径，再输出验证结果。提供编排 JSON 等价结构、配图类型对照表、验证对比表。新增配置项说明默认行为与兼容性。所有结论必须有代码依据或测试结果支撑。

## 五、优化点说明

**1. 保留“预编排前置”这一核心创新**
参考文档最有价值的不是某个提示词，而是“配图不是正文写完后再加，而是正文生成前先规划好”这一思路。引入时把预编排作为正文生成的前置阶段固定下来，而不是可选步骤。

**2. 正文生成与配图严格分离**
参考文档明确“图和文字的失败成本不一样”，引入时保留这一原则：正文生成提示词严禁输出图表代码块，配图在正文全部完成后统一执行，配图失败不影响正文结果。

**3. 编排结果传给正文模型，避免图文两张皮**
这是参考文档中容易被忽略但很关键的细节。引入时明确：编排阶段确定的图表意图要传给正文生成模型，让正文提前为图表铺垫。

**4. AI 提名、程序拍板**
保留“needed: true 只进候选池，不代表执行”的设计，最终由程序全局择优、分段控制，避免前面章节用完额度。这是控制成本和防止头重脚轻的关键。

**5. 适配本软件的图表类型约束**
参考文档有 Mermaid 和 AI 生图两类，本软件图表类型更丰富（数据型、甘特图、架构图、劳动力图表），且要求“图表全部自动生成，不设人工配图按钮”。引入时把 `image` 字段扩展为 `chart` 字段，AI 生图默认关闭，不提供用户点击入口。

**6. 保留 Mermaid 校验与修复**
参考文档的 Mermaid 修复提示词非常具体（flowchart TD、ASCII 节点 ID、中文标签加引号、不用简写、不用分号、不加围栏、复杂图简化），这是实际踩过坑总结出来的，引入时完整保留。

**7. 与九大章节、全局事实、字数控制、导出 DOCX 协同**
参考文档是独立讲图文控制，本软件需要与已有机制协同：编排时结合九大章节必含要素判断、读取全局事实标题判断数据支撑、正文按 sort_order 顺序生成、图表不计入正文字数、导出时 Mermaid 转图片且不引入 Word 2010+ 扩展。
