# 目录章节提纲生成工作流程：文档梳理与引入提示词

## 一、两份文档的工作流程梳理

两份文档内容一致，一份带代码与提示词，一份是工作流程总结。核心是**两套方案 + 五个关键机制**。

### 1. 整体架构：两套方案按场景自动选择

| 维度     | 方案一：一次性生成          | 方案二：分步生成               |
| -------- | --------------------------- | ------------------------------ |
| 适用场景 | 短标书（≤3~5 万字）         | 长标书（几万~几十万字）        |
| 模型要求 | 强模型（输出约 8000 token） | 普通模型（输出约 1500 token）  |
| 生成次数 | 1 次                        | 1 + N 次（N=一级章节数）       |
| 并发     | 不适用                      | 多个一级目录可并发             |
| 质量控制 | JSON 格式校验               | check_json 结构比对 + 3 次重试 |
| 防重复   | 天然避免                    | 传入 other_outline 显式约束    |
| 提纲长度 | 受模型输出限制              | 理论无限（分而治之）           |

### 2. 方案一：一次性生成

输入 `overview` + `requirements` → 构建 SystemPrompt（角色+输出规范+JSON 格式）与 UserPrompt → 一次性生成完整三级目录 JSON → 格式校验（合法 JSON）+ 结构校验（id/title/description/children）+ 层级校验（三级完整）→ 输出标准 JSON。

核心规则：一级目录与评分要求一致、统一三级深度、只返回 JSON。

### 3. 方案二：分步生成（四个步骤）

**步骤 1：生成一级目录**
输入 `overview` + `requirements`，输出 `{rating_item, new_title}` 结构。一级目录与评分项一一对应，标题做简单修改不照抄原文。

**步骤 2：节点数量分配**
生成 `nodes_distribution`：`level2_nodes`（每个一级下的二级数量）、`leaf_per_level2`（每个二级下的三级数量）。随机分布，让章节叶子数量有差异，更符合真实标书结构。

**步骤 3：并发逐章生成（关键环节）**

- **3a 代码生成 JSON 框架**：`generate_one_outline_json_by_level1` 预先构建骨架，id 与层级已定，title/description 留空，AI 只填内容；
- **3b 传入 other_outline**：拼接其他章节标题，AI 生成当前章节时参考，确保内容不重叠；
- **3c AI 补全**：SystemPrompt 明确"在原 JSON 上补全 title 和 description，禁止修改结构，禁止修改一级标题，二级根据一级撰写，三级根据二级撰写"；
- **3d check_json 校验**：逐层递归比对 AI 返回 JSON 与传入框架，检查类型匹配、键存在、列表元素格式一致；
- **3e 重试机制**：校验失败重新执行，最多 3 次，连续失败报错由人工介入；
- **3f 保存该章节完整目录**。

**步骤 4：合并所有章节**
按一级目录顺序拼接为完整 JSON，输出最终提纲。

### 4. 五个关键机制

| 机制                   | 解决的问题                                 |
| ---------------------- | ------------------------------------------ |
| 代码生成框架 + AI 补全 | 输出不稳定——结构由程序保证，AI 只填内容    |
| check_json 校验        | 格式错误——逐层递归比对，确保 AI 没破坏框架 |
| 重试机制（最多 3 次）  | 成功率——校验失败自动重试                   |
| other_outline 防重复   | 内容交叉——每章生成时参考同级章节标题       |
| 并发生成               | 效率——多个一级目录同时生成                 |

此外还有**随机节点分布**，让各章节叶子数量有差异，更符合真实标书结构。

### 5. 核心代码与数据结构

```json
{
  "outline": [
    { "id": "1", "title": "", "description": "", "children": [
      { "id": "1.1", "title": "", "description": "", "children": [
        { "id": "1.1.1", "title": "", "description": "" }
      ]}
    ]}
  ]
}
```

`check_json` 的核心逻辑是 `check_structure(target, template, path)` 递归比对：数字类型 int/float 可互换；基本类型必须一致；列表用第一个元素作模板校验所有元素；字典检查所有必需键存在且递归校验。

4. 校验：JSON 语法校验 → Schema 校验（id/title/description/children 字段完整）→ 业务校验（L5 深度、L1 覆盖九大章节、L2 数量 3~5、L4 数量 4~7、编号连续）。
5. 输出：标准 JSON 格式的完整目录。

四、方案二：分步生成

1. 步骤 1：生成一级目录
   - 一级目录与专项施工方案九大章节标准对齐（工程概况、编制依据、施工计划、施工工艺技术、安全保证措施、人员配备、验收要求、应急处置、计算书与图纸）；

   - 输出格式：{ rating_item, new_title } 等价结构，标注原章节与新标题的对应关系；
   - 标题做简单修改，不照抄原文。

2. 步骤 2：节点数量分配
   - 每个 L1 下 L2 数量控制在 3~5 项（本软件约束，替换文档中的随机分布）；
   - 每个 L2 下 L4 数量控制在 4~7 项；
   - L3 作为 L2 与 L4 之间的中间层级，数量按内容需要分配，不设固定约束；
   - L5 作为正文生成的最小叶子节点，数量由 L4 内容深度决定；

   - 3c. AI 补全：SystemPrompt 明确“在原 JSON 上补全 title 和 description，禁止修改 JSON 结构，禁止修改一级标题，二级根据一级撰写，三级根据二级撰写，四级根据三级撰写，五级根据四级撰写，参考 other_outline 避免重复”；

   - 3e. 重试机制：校验失败重新执行该章节生成，最多 3 次；每次重试携带上次错误信息定向修复；连续 3 次失败标记该章节待人工介入，不阻断其他章节；
   - 3f. 保存该章节完整目录。

   - 将所有 L1 章节及其子目录按 L1 顺序拼接为完整 JSON；
   - 由程序统一重排编号（不信任模型输出的编号），保证 L1 至 L5 编号连续、不重复、不跳号；

   - 合并顺序不受并发完成顺序影响。

五、五个关键机制的落地

1. 代码生成框架 + AI 补全
   - 结构由程序保证，AI 只填内容；
   - 框架包含 id、层级、children 结构，title 与 description 留空；
   - 提示词明确“禁止修改 JSON 结构、禁止修改已确定的上级标题”。

2. check_json 校验
   - 逐层递归比对，检查类型、键、列表元素格式；
   - 数字类型 int/float 可互换；基本类型必须一致；列表用第一个元素作模板校验所有元素；字典检查所有必需键存在且递归校验；
   - 校验不通过时返回具体错误位置与原因；
   - 与 Schema 校验、业务校验形成三级校验。

3. 重试机制
   - 校验失败自动重试，最多 3 次；
   - 每次重试携带上次错误信息，定向修复；
   - 连续失败标记待人工介入，不阻断整体流程。

4. other_outline 防重复
   - 每章生成时传入其他 L1 章节标题；
   - 提示词明确要求避免与 other_outline 内容重复或交叉；
   - 与同级章节信息传递机制配合，进一步降低重复。

5. 并发生成
   - 多个 L1 章节可并发生成；
   - 并发数可配置，默认保守值；
   - 并发时保证每章拿到的 other_outline 一致（基于已确定的 L1 标题），不依赖运行时其他章节的生成结果；
   - 合并时按 L1 顺序拼接，不受并发完成顺序影响。

   - 目录排序字段 sort_order 写入，正文生成按此顺序执行；
   - 目录节点 ID 与正文生成、图表生成、导出文档的编号保持一致。

4. 提纲可编辑
   - 生成的目录支持手动修改标题、描述；
   - 支持删除节点、重新排序、重新编号；
   - 编辑后不破坏原有结构，编号由程序统一重排。

9. 提纲编辑后结构被破坏。

## 四、优化点说明

**1. 把参考文档的“评分要求一一对应”适配为“九大章节对齐”**
参考软件是招投标工具，一级目录对齐技术评分要求；本软件是专项施工方案工具，一级目录必须对齐九大章节标准，方案类型特殊章节可增补但不删减。

**2. 把“随机节点分布”替换为“固定数量约束”**
参考文档用随机分布让章节叶子数量有差异；本软件已有明确约束（L2 数量 3~5、L4 数量 4~7），因此 `nodes_distribution` 不再随机，而是按约束分配，由程序校验。

**3. 把“三级目录”扩展到“L1 至 L5”**
参考文档统一三级深度；本软件要求生成至 L5 级，L5 为正文生成的最小叶子节点，因此一次性生成和分步生成都需覆盖 L1 至 L5，校验规则同步调整。

**4. 保留并强化五个关键机制**
代码生成框架 + AI 补全、check_json 校验、重试机制、other_outline 防重复、并发生成，五个机制全部保留并明确落地方式。特别补充了并发时 other_outline 一致性——这是文档未明确但实际并发场景必须处理的问题。

**5. 补齐核心代码移植方案**
明确 `generate_one_outline_json_by_level1` 与 `check_json` 的等价实现要求，包括 check_json 的递归比对规则（数字 int/float 可互换、基本类型一致、列表用首元素作模板、字典检查必需键），确保移植后行为一致。

**6. 补齐编号重排与提纲可编辑**
参考文档方案二有“合并所有章节”，但未强调重编号；本软件明确要求程序统一重排 L1 至 L5 编号，不信任模型输出。同时补充提纲可编辑要求，编辑后不破坏结构、编号统一重排。
