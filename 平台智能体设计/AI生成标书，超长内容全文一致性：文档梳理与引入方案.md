# 超长内容全文一致性：文档梳理与引入方案

## 一、两份文档的核心机制梳理

两份文档内容一致，一份详述工作流，一份讲思路来源。核心是：**不给 AI 几十万字上下文，而是给整份标书建立一份独立的“事实底稿”。**

### 1. 问题根源

长标书前后不一致（工期90天变120天、响应2小时变4小时、人员数量设备型号反复变化、质保3年变1年），根本原因是**为了保证生成速度做了多线程并发，每个叶子节点相互独立**，彼此不知道其他章节写了什么。

### 2. 为什么长上下文和摘要都不行

**长上下文不可行**：参考内容太多（招标文件、工程量单、知识库、原方案），容易爆上限；《Lost in the Middle》论文证明关键信息放长上下文中间时模型表现明显下降；分章节并发生成时每个请求只看当前章节，不知道其他章节写了什么。只在提示词写“请保证全文一致”基本等于没写。

**摘要不可行**：摘要必须串行或较小并发；普通摘要是总结性质的，参考资料里很少有实质性内容。极端例子：招标文件要求“必须在90天内完工”，30天、60天、90天都算90天完工，并发编写时不同小节可能出现不同工期。

### 3. 核心认知：全局事实不是招标要求摘要

“招标人要求工期不超过90天”只是**要求**；“本方案项目总工期为90天”才是后续正文可以统一使用的**事实**。这是整套方案的理论基础。

### 4. 三步工作流

**第一步：生成全局事实变量**
按模型上下文限制切分文件 → 分段提取事实 → 知识库补充不冲突的技术设定 → 已有方案扩写优先保留原方案人员设备周期服务承诺 → 合并重复项删除空泛要求 → 形成轻量事实清单 → 用户查看修改。

事实格式如：“关于XX问题统一采用XX方案。”产品周期类、售后服务承诺类、项目组织配置类分别列出。

**第二步：每个章节只读取需要的事实**
事实不能全部塞进每次请求，否则浪费 Token 还会产生新干扰。正文编排阶段 AI **只看到全局事实的标题**，判断当前章节需要哪些事实（输出 `facts.titles` 列表）；真正生成时程序根据标题取出完整事实内容，**只注入当前章节**。

提示词两条硬约束：提供了相关全局事实时必须优先使用不得前后矛盾；没有提供时不要主动编造人员、周期、质保、品牌、型号。

**第三步：生成后审计全文**
生成前做了约束也不能默认 AI 一定遵守，知识库素材、已有方案、正文扩写、用户手工修改都可能重新带入旧数据。两种审计方式：

**普通修复**：按目录顺序把超长正文分组，每组和全局事实一起交给 AI，只检查已明确写出的事实冲突；AI 返回冲突章节、冲突原文、违反事实；修复时返回 `old_text`/`new_text` 精确修改，**程序只有在 `old_text` 能唯一命中当前小节时才替换**，找不到或多处相同都拒绝修改并重新尝试。

**Agent 修复**：准备 `global-facts.md` 和 `technical-plan.md` 两个文件，Agent 搜索关键词、分段读取、建立索引、多轮修改 `technical-plan.md`。正文每个章节有固定开始结束标记和章节 ID，Agent 完成后程序重新解析校验（章节是否被新增删除重排、章节 ID 和标记是否完整、修改是否在允许范围内、哪些小节真的变化），校验通过只回写变化小节，失败保留原正文。**把超长上下文问题变成 Agent 更擅长的“搜索文件并修改文件”。**

### 5. 一致性边界

不能 100% 保证。如果全局事实本身是错的，后面的正文只会非常一致地一起写错。自动审计擅长找工期、人员、数量、型号、质保、响应时间这类明确冲突，但对履约可行性、隐含逻辑和法律责任，仍需专业人员复核。

### 6. 两类用户场景

**想随便写一份标书的用户**：AI 把包括人名等内容都一并初始化，生成结果完整，无需人工二次修改。

**想要可落地技术方案的用户**：全局事实在 AI 解析后支持用户手动添加、编辑、删除，AI 只负责整理哪些必须统一，统一成什么内容让用户根据实际情况填写。

### 7. 核心结论

不要把全文一致性全部押在 Prompt 上。**应该把事实做成独立数据，把引用关系做成编排结果，把一致性做成生成后的审计任务。** 长上下文解决的是“能不能输入”，这套工作流解决的才是“几十万字能不能始终说同一套话”。

```text
请将参考文档《AI生成标书，如何保证超长内容的全文一致性》与《重写版》的三步工作流、全局事实设定、编排选事实、生成注事实、普通修复、Agent 修复、一致性边界引入本软件的全局事实模块、正文生成模块、审核预检模块，适配“建筑工程专项施工方案编写”定位。

一、任务计划（必须先执行）
使用 EnterPlanMode 或 TodoWrite 制定计划，列出：全局事实模块、正文生成模块、审核预检模块的现有实现；三步工作流的落地位置；普通修复与 Agent 修复的实现方式；与九大章节分类、L1-L5 层级、字数控制、图表编排的协同；一致性边界；风险点与验证方式；执行顺序与优先级（P0/P1/P2）。

二、建立核心认知

1. 全局事实不是文件摘要
   - “招标人要求工期不超过90天”只是要求；
   - “本方案项目总工期为90天”才是后续正文可统一使用的事实；
   - 全局事实是“本方案统一采用的事实”，不是“文件里写了什么”。

2. 不一致的根源
   - 并发生成时每个 L5 叶子节点相互独立，彼此不知道其他章节写了什么；
   - 长上下文和普通摘要都解决不了；
   - 只在提示词写“请保证全文一致”等于没写，AI 不知道哪些必须统一、冲突时听谁的。

3. 解决思路
   - 不给 AI 几十万字上下文，而是给整份方案建立独立的事实底稿；
   - 生成前确定全文统一使用哪些事实；
   - 生成时只把当前章节需要的事实交给 AI；
   - 生成后检查全文有没有违反这些事实。

三、第一步：生成全局事实

1. 触发时机
   - 目录生成完成后、正文生成前；
   - 按模型上下文限制切分文件，分段提取事实；
   - 提取后续正文会反复使用、必须保持一致的内容。

2. 提取流程
   - 从施工图、勘察报告、施工组织设计、招标文件、地勘报告、专项方案原稿分段提取事实；
   - 用知识库补充更具体、且不冲突的技术设定；
   - 如果是已有方案扩写，优先保留原方案中的人员、设备、周期和服务承诺；
   - 合并重复项，删除空泛要求，形成轻量事实清单；
   - 事实生成后先让用户查看修改，因为 AI 可以统一口径，但工期、质保、人员、设备最终能不能承诺只有编制人知道。

3. 事实格式
   - 每条事实采用“关于XX问题统一采用XX方案”的格式；
   - 短小、明确、可直接引用；
   - 按九大章节分类：工程概况类、编制依据类、施工计划类、施工工艺技术类、安全保证措施类、人员配备类、验收要求类、应急处置类、计算书与图纸类；
   - 每个分类下列出具体事实项，如工程概况类含工程名称、地点、规模、结构形式、专项参数；施工计划类含总工期、分阶段周期、开竣工日期。

4. 事实数据结构
   - GlobalFactGroup：id、title、category、facts 列表、updated_at；
   - 每条事实：id、content、source、confidence；
   - 支持用户手动添加、编辑、删除。

5. 两类用户场景
   - 想快速出稿：AI 把包括人名、设备型号、参数等内容都初始化，生成结果完整，无需人工二次修改；
   - 想要可落地方案：AI 只负责整理哪些必须统一，统一成什么内容由用户根据实际情况填写。

四、第二步：编排选事实、生成注事实

1. 编排阶段
   - AI 只看到全局事实的标题，不看到完整内容；
   - 判断当前 L5 章节需要哪些事实，输出 facts.titles 列表；
   - 与图表编排、表格编排合并为统一的正文编排 JSON；
   - 编排 JSON 结构：writing_focus、facts.titles、knowledge.item_ids、table.needed/purpose、mermaid/chart/image 的 needed/title/priority/reason。

2. 生成阶段
   - 程序根据 facts.titles 取出完整事实内容；
   - 只注入当前章节需要的事实，不全部注入；
   - 避免上下文过载，避免无关事实干扰。

3. 提示词硬约束
   - 提供了相关全局事实时，必须优先使用，不得前后矛盾；
   - 没有提供时，不要主动编造人员、周期、质保、品牌、型号；
   - 关键数据必须与全局事实一致。

4. 与并发生成的关系
   - 正文扩写、单章节重新生成也走同一套逻辑；
   - 即使各章节并发生成，它们仍然引用同一份外部事实底稿；
   - 并发时 facts.titles 基于编排结果确定，不依赖运行时其他章节的生成结果。

五、第三步：生成后审计全文

1. 触发时机
   - 正文全部生成完成后；
   - 知识库素材、已有方案、正文扩写、用户手工修改都可能重新带入旧数据，必须审计。

2. 普通修复
   - 按目录顺序把超长正文分组，每组和全局事实一起交给 AI；
   - 只检查已经明确写出的事实冲突（工期、人员、数量、型号、质保、响应时间）；
   - AI 返回冲突章节、冲突原文、违反事实；
   - 修复时返回 old_text/new_text 精确修改；
   - 程序只有在 old_text 能唯一命中当前小节时才替换；
   - 找不到或多处相同都拒绝修改并重新尝试，避免为修一个数字误伤整章；
   - 同时检查编号一致、图号不虚跳。

3. Agent 修复
   - 准备 global-facts.md 和 technical-plan.md 两个文件；
   - Agent 不需要一次读完并修完全文，可以搜索关键词、分段读取、建立索引、多轮修改 technical-plan.md；
   - 把超长上下文问题变成 Agent 更擅长的“搜索文件并修改文件”；
   - 正文每个章节有固定开始结束标记和章节 ID（L1 至 L5）；
   - Agent 完成后程序重新解析校验：章节是否被新增删除重排、章节 ID 和标记是否完整、修改是否在允许范围内、哪些小节真的发生变化；
   - 校验通过后只回写发生变化的小节，失败则保留原正文。

4. 审计输出
   - 冲突清单：章节、冲突原文、违反事实、修复建议；
   - 修复记录：哪些小节被修改、修改前后对比；
   - 审计报告：供审核预检模块读取。

六、一致性边界（必须明确）

1. 不能 100% 保证一致。
2. 如果全局事实本身是错的，后面的正文只会非常一致地一起写错。
3. 自动审计擅长找工期、人员、数量、型号、质保、响应时间这类明确冲突。
4. 履约可行性、隐含逻辑、法律责任、计算书与图纸的合理性，仍需专业人员复核。
5. 这套方案真正解决的是：不再让每个章节随机编一套事实；把几十万字的人工交叉检查缩小为少量事实清单和冲突小节复核；修改冲突时只动必要位置，不重写已经正确的内容。

七、与各模块的衔接

1. 与全局事实模块
   - 全局事实按九大章节分类存储；
   - 支持用户手动添加、编辑、删除；
   - 支持版本管理与回滚；
   - 提供 facts.titles 清单供编排阶段使用，提供完整事实内容供生成阶段使用。

2. 与正文生成模块
   - 编排阶段输出 facts.titles 到正文编排 JSON；
   - 生成阶段按 facts.titles 注入完整事实；
   - 提示词硬约束必须优先使用不得矛盾、未提供不编造；
   - 与顺序生成、字数控制、图表编排协同，事实不计入正文字数。

3. 与审核预检模块
   - 审计结果作为审核预检的输入；
   - 审核预检可读取审计报告、冲突清单、修复记录；
   - 审核预检补充人工复核项：履约可行性、隐含逻辑、法律责任、计算书合理性。

4. 与导出 DOCX 衔接
   - 修复后只回写变化小节，不影响未变化部分的格式与编号；
   - 导出的 DOCX 与审计后正文一致；
   - 不引入 Word 2010+ 专有扩展。

八、BUG 修复重点

1. 把全局事实做成文件摘要，而非“本方案统一采用的事实”。
2. 全局事实全部注入每次请求，导致上下文过载。
3. 编排阶段未输出 facts.titles，生成阶段无法精准注入。
4. 编排阶段看到完整事实内容而非标题，浪费 Token。
5. 提示词缺少“优先使用不得矛盾”“未提供不编造”硬约束。
6. 并发生成时 facts.titles 依赖运行时其他章节，导致不一致。
7. 普通修复中 old_text 未做唯一命中校验，误伤整章。
8. Agent 修复后未校验章节完整性，章节被新增删除重排。
9. Agent 修复失败时未保留原正文。
10. 审计只查工期不查人员、数量、型号、质保、响应时间。
11. 未明确一致性边界，对自动审计产生不切实际预期。
12. 与九大章节分类、L1-L5 层级、字数控制、图表编排、导出 DOCX 的衔接断裂。
13. 修复过程中发现的其他所有 BUG。

九、验证与回归

1. 每完成一项引入，运行相关测试，建立基线并对比。
2. 验证：
   - 全局事实是否为“本方案统一采用的事实”而非文件摘要；
   - 全局事实是否按九大章节分类、是否支持用户编辑；
   - 编排阶段是否只看到标题、是否输出 facts.titles；
   - 生成阶段是否按 facts.titles 精准注入、是否只注入当前章节；
   - 提示词硬约束是否生效；
   - 并发生成时是否引用同一份事实底稿；
   - 普通修复是否唯一命中才替换、是否拒绝多义匹配；
   - Agent 修复是否校验章节完整性、是否只回写变化小节、失败是否保留原正文；
   - 审计是否覆盖工期、人员、数量、型号、质保、响应时间；
   - 一致性边界是否明确、审核预检是否补充人工复核项；
   - 与各模块衔接是否正常。
3. 端到端验证：解析提取 → 提取项目 → 目录生成 → 全局事实 → 正文编排 → 正文生成 → 配图 → 审计修复 → 审核预检 → 导出 DOCX。
4. 用真实长方案（10 万字以上）实测，验证全文一致性。
5. 所有测试通过，无回归。

十、输出要求

用中文回答，代码注释用中文。先输出三步工作流在本软件的落地方案，再输出全局事实的九大章节分类与数据结构，再输出编排选事实、生成注事实的实现方案，再输出普通修复与 Agent 修复的实现方案，再输出一致性边界与审核预检衔接，再输出代码修改方案与文件路径，再输出长方案实测结果与验证对比。提供 GlobalFactGroup 数据结构、正文编排 JSON 结构、审计报告格式、验证对比表。新增配置项说明默认行为与兼容性。所有结论必须有代码依据或测试结果支撑。
```

## 五、优化点说明

**1. 保留“全局事实不是文件摘要”这一核心认知**
这是整套方案的理论基础，也是最容易被误解的地方。很多工程做全局事实时只做“文件摘要”，结果 AI 知道文件里写了什么，但不知道“本方案统一采用什么”。引入时把它放在最前面，作为所有后续设计的前提。

**2. 保留“三步工作流”作为整体框架**
生成前确定事实 → 生成时只给当前章节需要的事实 → 生成后审计全文。三步缺一不可：只做第一步，事实有了但没注入；只做第二步，注入了但没审计；只做第三步，审计了但事实本身是随机生成的，审计没有标准。

**3. 保留“编排选事实、生成注事实”这一关键设计**
事实不能全部塞进每次请求，否则浪费 Token 还产生干扰。编排阶段 AI 只看到标题，生成阶段程序按标题取出完整事实，这是本方案最优雅的设计——既不牺牲精准度，又不牺牲性能。

**4. 保留“普通修复唯一命中才替换”这一细节**
很多工程做全文一致性修复时，让 AI 重写整章，结果改一个数字误伤整章。参考文档的 `old_text`/`new_text` 精确修改 + 唯一命中校验，是实际踩过坑总结出来的，引入时完整保留，并补充“同时检查编号一致、图号不虚跳”。

**5. 保留“Agent 修复把超长上下文问题变成搜索文件修改文件”这一思路**
普通修复对明确冲突有效，但几十万字反复分组审计返回 JSON 再逐条修复，工作流复杂。Agent 修复让 Agent 搜索、分段读取、多轮修改文件，程序校验后只回写变化小节，这是解决超长文本修复的实用思路。

**6. 补齐“与九大章节分类的适配”**
参考软件是招投标工具，全局事实按产品周期、售后承诺、组织配置分类；本软件是专项施工方案工具，全局事实必须按九大章节分类（工程概况类、编制依据类、施工计划类、施工工艺技术类、安全保证措施类、人员配备类、验收要求类、应急处置类、计算书与图纸类），并在每个分类下列出具体事实项。

**7. 补齐“一致性边界”并延伸到审核预检**
参考文档明确“不能 100% 保证”“全局事实本身错则一致地错”“履约可行性需人工复核”。引入时保留边界，并把它延伸到审核预检模块：审计结果作为审核预检输入，审核预检补充人工复核项，包括履约可行性、隐含逻辑、法律责任、计算书与图纸合理性。

**8. 补齐“与已有机制的协同”**
本软件已有全局事实模块、正文生成模块、审核预检模块，引入时明确协同方式：全局事实模块负责事实存储与用户编辑；正文生成模块的编排阶段输出 `facts.titles`、生成阶段按 titles 注入；审核预检模块读取审计报告并补充人工复核。避免全局事实机制成为孤立模块。

**9. 强调“用真实长方案实测”**
参考文档的问题是在 10 万字以上长标书场景下暴露的。引入时明确要求用 10 万字以上真实长方案实测，而不是只用短样例验证。短样例能过不代表长方案能过，这是全文一致性问题的核心场景。
