### Task 3 · 查重模块升级（目录相似度 + 文档同源指纹）

| 项 | 说明 |
|---|---|
| 参考实现 | 易标 `buildOutlineComparison`（目录比对）+ `extractMetadata` 指纹体系 |
| 本软件原状 | 目录相似度用 Jaccard，对目录规模敏感且**完全丢失顺序信息**；无文档同源判断 |
| 改后 | 覆盖率 + LCS 顺序双指标加权；新增 RSID / PDF 结构 / WPS 痕迹三类指纹 |

**目录相似度算法替换**

原 Jaccard 的两个硬伤：

1. **规模敏感**：3 章的小目录被 30 章的大目录覆盖时，Jaccard 分母取并集 → 相似度被稀释到 0.1，明显抄袭却报"低风险"。
2. **丢顺序**：目录条目集合相同但顺序完全打乱（章序错乱本身就是硬性废标风险），Jaccard 仍给 1.0。

改后：覆盖率（`|交集| / min`）+ LCS 顺序相似度 + 加权综合分（0.45 / 0.35 / 0.2），阈值 0.75 / 0.55 / 0.35 分级。

新增函数：`normalize_outline_title()`、`bigram_dice_similarity()`、`lcs_similarity()`（滚动数组实现，避免 O(m·n) 内存）、`outline_risk_from_score()`、`_bigram_containment()`、`is_near_synonym_title()`。

> **对参考实现的一处修正**：易标的近义标题判定用二元组 Dice，阈值 0.86。但中文短标题（4~6 字）天然偏低——`施工组织设计` vs `施工组织设计方案` 只有 0.833，会被漏判。本实现增加「包含度」判据（`|交集| / min ≥ 0.95` 且长度差 ≤ 4 且短标题 ≥ 4 字），两条判据取或。

**文档同源指纹**

- `_extract_docx_fingerprints()`：Word RSID（`rsidRoot` 编辑会话根 ID + 指纹哈希 + 计数）、WPS/金山账号痕迹
- `_extract_pdf_fingerprints()`：PDF 版本、对象数、Trailer ID、增量保存次数、签名数、附件数
- `_SAME_SOURCE_RULES` + `compare_same_source()`：共用 RSID 根 → 高风险；共用 WPS 账号痕迹 → 中风险
- `analyze_metadata()` 新增 `fingerprints` / `same_source_pairs` 字段与 `same_source` 类型异常项
- `export_report()` 新增「综合相似度表格」「近义标题明细」「五、文档同源指纹」章节

> 定位：指纹只作**线索**不作**定性**，报告中附免责说明——同一投标人投不同标段本就同源，不能直接当围标证据。

### Task 4 · 废标检查：错别字定位校验

| 项 | 说明 |
|---|---|
| 参考实现 | 易标 `rejectionCheckTask.cjs::findVerifiedTypoPosition` / `createVerifiedTypoExcerpt` / `createLineLocationHint` |
| 本软件原状 | 只做 `original in text` 布尔判断并写个 `validated` 标记；AI 幻觉条目照样进报告 |
| 改后 | 三级匹配定位 + ±8 字摘录 + 行号提示；定位失败的条目显式丢弃并计数 |

原实现的两个后果：

1. **"狼来了"效应**：AI 幻觉出的错别字（原文根本没有）进入报告，人工复核逐条找不到，最终整份错别字检查结果都不被信任。
2. **定位靠猜**：没有位置信息，长文档里只能靠 AI 自述的"第 3 段第 2 句"，基本不可用。

新增函数：

- `_build_compact_index_map()`：构建「去空白」文本到原文的索引映射
- `locate_text_span()`：三级匹配 —— 精确 → 去空白（AI 常吃掉/补上换行）→ 忽略引号差异（AI 常把 `""` 写成 `“”`）
- `build_verified_excerpt()`：±8 字摘录，压平换行便于报告展示
- `build_line_hint()`：按字符偏移反推行号
- `verify_spelling_error()`：定位校验 + 补齐 `position` / `excerpt` / `line_hint`；兼容 `original` / `wrong` / `wrongText` 三种历史字段名
- `check_spelling_dimension()` 重写：丢弃定位失败条目（`discarded_count` 写入日志便于评估模型质量）+ 按 `(original, position)` 去重

已删除旧函数 `_validate_spelling_position`（确认全库零引用）。

> **排查结论（保留为防御性代码）**：`verify_spelling_error` 里"先在 quote 内定位再把 quote 落到原文"的回退分支当前**不可达**。
> 论证：`locate_text_span` 的三级匹配对 needle 都是单调的——若 needle 是 quote 的子串，则第 k 级变换后的 needle 必是第 k 级变换后的 quote 的子串；又因 quote 能在原文命中某一级 j，故 needle 必能命中第 j 级，与 `position < 0` 矛盾。
> 已在源码注释写明，若日后新增非单调匹配级（如模糊编辑距离）该分支才会生效。

### Task 5 · 废标项检查三轮流程 + 宿主侧证据核验

| 项 | 说明 |
|---|---|
| 参考实现 | 易标 `rejectionCheckTask.cjs::runRejectionItemCheck`（三轮）+ `rejectionPrompts.ts` |
| 本软件原状 | 单轮「分段直出 JSON」：把检查项清单 + 投标文件每段一起塞给 AI，要求直接吐 JSON |
| 改后 | 三轮：范围分析（自由文本）→ 逐项检查（Markdown 初稿）→ 定稿（严格 JSON）；任一轮失败自动降级单轮 |

**为什么单轮不够**

1. **格式压力挤占判断质量**：模型要同时做「对照条款推理」和「输出严格 JSON」，
   格式约束会牺牲判断质量，也更容易凭空补出原文没有的条目。
2. **没有范围收敛 → 稳定误报**。这是最要命的一条：
   - 「未加盖单位公章」「未密封」「未现场递交」这类**纸质/线下事项**，
     电子投标文件根本无从判断，AI 却会稳定地报出来；
   - 解析后的 Markdown 里**图片/扫描件正文本来就不存在**，
     AI 会大量误报「资质证书缺失」「营业执照未提供」。
3. **没有位置核验**：易标的错别字检查有 `findVerifiedTypoPosition` 做 offset 校验，
   废标项检查反而只有字段非空校验，`bidEvidence` 只能是 AI 自述，人工复核无从下手。

**三轮设计（并做了一处成本优化）**

| 轮次 | 输入 | 输出 | 要求 JSON |
|---|---|---|---|
| 第一轮 范围分析 | 检查项清单 + **投标文件目录结构线索** | 哪些条款可核验、排除项、重点章节 | 否 |
| 第二轮 逐项检查 | 上述 + 第一轮结论 + 投标文件分段 | 结构化 Markdown 初稿 | 否 |
| 第三轮 定稿 | 上述全部 | 去重合并、删不合格条目后的 JSON | 是 |

> **成本优化**：第一轮只喂投标文件的**目录结构线索**（复用既有 `duplicate.extract_toc`），
> 不喂全文。范围分析依赖的是结构信息而非正文细节，这样第一轮输入从数万字压到几千字，
> 成本与延迟显著下降而判断质量不受影响。结构线索不足 5 条时回退文首 3000 字兜底。

**第三轮提示词的关键约束**（直接针对上面两个误报源）

- 明确排除签字、盖章、密封、纸质正副本、现场递交、开标现场行为；
- **结构性线索规则**：判定「材料缺失」前必须确认章节标题、目录项、附件标题、
  材料清单项、表格条目、页码线索、图片占位线索**全都找不到**痕迹；只要有任一线索，
  就应视为已提交，不得仅因图片正文不可见而定为缺失；
- `quote` 必须**逐字摘自原文**，不得改写——宿主会用它做定位校验，改写过的摘录会被判为无法核验。

**宿主侧增强（超出参考实现）**

- `verify_rejection_evidence()`：复用错别字检查那套 `locate_text_span`（三级匹配）+
  `build_verified_excerpt` + `build_line_hint` 做**证据原文核验**。
  - 命中 → `validated=True` + `position` / `excerpt` / `line_hint`；
  - 未命中 → `validated=False`（**不丢弃**，标记供人工重点复核）；
  - 无摘录（材料缺失类）→ `validated=None` + `evidence_kind="structural"`。
- `_assign_item_codes()`：给检查项分配唯一稳定编号，并对 AI 回填的 `check_item_id`
  做归属校验（`code_matched`），防止模型自造条款编号扩大检查范围。
- `_normalize_severity()`：易标用 `high/medium/low`，本软件前端约定 `critical/warning/info`，
  做别名归一，避免前端 Tag 取不到颜色配置而显示空白。
- `_dedup_final_issues()`：机械去重兜底（AI 已在第三轮语义去重过），
  按「同编号 + 描述相似度 ≥ 0.85」合并，合并时**优先保留证据已核验的那条**。
- 单轮降级路径与三轮流程**共用同一套收尾**，两条路径产出结构完全一致。

**降级策略（保证不倒退）**

三轮任一轮失败（第一轮空 / 第二轮全空 / 第三轮异常）→ 返回 `None` → 自动回退到原单轮逻辑。
另有环境变量 `REJECTION_THREE_ROUND=0` 可整体关闭三轮。
第三轮**合法返回空数组**（确实没问题）不算失败，不触发降级——否则会白跑一遍单轮。

**前端**

- 结果列表新增三个核验徽标：`证据已定位`（绿，Tooltip 显示行号）、
  `证据待核验`（橙，提示可能是改写或误报）、`未对应检查项`（灰，提示模型扩大范围）、
  `已合并 N 条`（蓝）；
- 顺手修掉一个既有渲染缺陷：「位置：」标签后**没有输出 `item.location` 的值**；
- 「标记误报」按钮改为**始终可用**（原来被 `!item.validated` 门禁，而该字段此前
  全库无任何写入点，等于恒真——现在它有真实语义了，不能再拿它当门禁）。

**报告导出**

`export_report()` 新增「废标项证据核验」概览（已定位 / 未能核验 / 结构性线索三类计数），
以及每条目下的「证据定位」行（已核验给出行号，未核验给出提示）。

### Task 6 · 目录生成审核门禁 `app/services/ai/outline_gate.py`（新建）

| 项 | 说明 |
|---|---|
| 参考实现 | 易标 `outlineGenerationTaskV2.cjs` 的 `outline_review` 阶段 |
| 本软件原状 | `_self_check_v51` 只有「本地正则查重 + AI 自检提示词」两件事，结论只进日志，前端与用户都不知道 |
| 改后 | 宿主算确定性事实 → 机械可修的先修 → AI 拿事实做语义审 → 合并成一份裁决写入 `v51_state.gate_report` |
| 影响面 | 目录是硬性废标风险点；此前一批「结构性缺陷」全靠运气 |

**摸清参考实现的真实结构**

参考实现**不是**「两道会短路的门禁」，而是：

1. 宿主先跑一遍确定性校验，把统计结果落成 `outline-review-context.json`；
2. AI 收到这份 context，提示词里明确写着「结构事实直接采用 context 结果，**不要重新统计、不要编写脚本**」；
3. AI 只做语义层判断，返回 issue 列表；
4. 四状态收敛 `passed` / `simple_fix` / `user_feedback` / `user_refuse`——**不自动打回重生成**，靠问用户收敛。

这个设计的价值在于：让 AI 别自己去数节点、自己去找重复。既省 token，也避免 AI 数错。

**相对参考实现补上的几项**（都是本软件实际踩过的坑）

| 能力 | 为什么必须补 |
|---|---|
| **占位符残留检测** | `__XXX__` / `{{}}` / `待补充` / `TODO` / `XXXX`。框架会打印 `has missing variables` 警告，但此前**没有任何地方检查最终目录里是否真的残留了占位符** |
| **id 缺失 / 非法 / 不连续检测** | 参考实现有 JSON Schema 校验（`^[1-9]\d*(?:\.[1-9]\d*){level-1}$`），本软件此前只在生成时赋值、**从不校验** |
| **标题长度上下限** | 3~30 字。单字标题（"岗"）和 30+ 字的整句标题都是明显缺陷，此前无人过问 |
| **评分项覆盖的标题级比对** | 原 `_check_scoring_coverage` **只比数量**——8 个完全跑偏的章节也能通过 |
| **字数预算 → 目标叶子数** | 见下方「顺带修掉的真 BUG」 |

**发现并修掉的真 BUG**

`outline_common._ensure_min_children`（`outline_common.py:777`）补全出来的新节点只有
`title` / `level` / `children`，**没有 `id`**；而它在 `_fix_all_ids`（`workflows_outline_v51.py:1647`）
**之后**运行，又发生在最终审核之前——于是**用户会在前端看到一批无 id 节点**，
按 id 定位编辑时会改错对象。门禁的 `renumber_outline_ids()` 正好修掉它，
且修复动作记录在 `verdict["auto_fixed"]` 里，不静默。

`expected_leaf_count` 此前声明了却**无任何调用方赋值**，`derive_target_leaf_count()`
只被测试调用过——即叶子数区间检查实际是**死代码**。现已补上 `parse_word_budget()`，
从「评分要点 + 招标要求 + 项目范围」文本里解析字数预算（支持「不少于 20000 字」
「2 万字以上」「10000~20000 字」「约 3 万字」等写法）再推导目标叶子数。

**设计立场：门禁只产出结论，不做阻断**

AI 审查失败时降级为「仅确定性结论」并**放行**——不因为一次审查超时就毁掉整份已经生成好的目录
（参考实现在这里会直接让任务失败）。同理，原实现会接受 AI 返回的 `fixed_outline` 并**整体替换目录**，
但提示词从未要求该字段，静默接受 AI 重写整棵目录有丢节点风险；现改为只收集问题，
由前端/用户决定是否修改。

**是否跑 AI 审查**（`should_run_ai_review`）

- 有确定性问题 → **必跑**（既然宿主都发现问题了，语义层判断值得一并拿到）；
- 没问题 → 只在节点数 > 80 时跑，**保持既有延迟特征**（原实现就是 >80 节点才做 AI 深度检查）。

**类别策略表** `CATEGORY_POLICY`（14 类 → 严重度 + 是否需要用户确认）

`error` 级或 `confirmation_required=True` 的条目 → 裁决 `user_feedback`（必须让人看一眼）；
其余可机械修复的 warning/info → `simple_fix`；无 issue → `passed`。

**提示词**：复用既有 `OUTLINE_V51_SELFCHECK_SYSTEM`（注册表不变，用户仍可在提示词管理页编辑），
只把 user prompt 换成 `build_gate_user_prompt()` 产出的事实前置版。

### Task 7 · 正文一致性修补：精确补丁引擎 + 真实落文

| 项 | 说明 |
|---|---|
| 参考实现 | 易标 `contentGenerationTask.cjs` 的 `auditing` 阶段（全文一致性检查） |
| 本软件原状 | 有一致性审计（能找出冲突），但**「自动修复」是假的**——见下方真 BUG |
| 改后 | 移植「两级定位 + 唯一性要求」的精确补丁引擎；自动修复真正改写正文；新增 AI 补丁修复路径 |
| 影响面 | 一致性修复是标书定稿前的最后一关，改错一个字比不改更糟 |

**先修掉的真 BUG（高严重度）**

`consistency_auditor.apply_autofix()` 号称「应用自动修复」，实际只做了两件事：
把 `consistency_conflicts` 记录标成 `resolved=1`、写一个 `resolved_value`。
**`sections.content` 一个字都没动。** 后果有两个：

1. 接口回「冲突已修复，统一值为 X」，前端弹「已应用修复」——**用户以为正文改了，实际没改**；
2. 冲突被标 `resolved` 后从待处理列表消失——**问题被隐藏，而不是被解决**。

现在：真实落文 → 只有确实写入成功才标 `resolved` → 返回真实报告（改了哪些章节、各替换几处、
哪些未能安全替换）。

**顺带修掉的第二个真 BUG（中严重度）**

`consistency_conflicts` / `consistency_audit_log` 两张表原先只在 `main.py` 启动钩子里、
用**硬编码路径** `backend/data/bid_assistant.sqlite3` 创建，绕过了 `BID_ASSISTANT_DATA_DIR`。
后果：配置了自定义数据目录时（测试环境正是如此），表被建到真实库里，应用实际使用的库里
没有 → 一致性审计一调用就 `no such table`。现收归 `db.init_db()`，与其余 schema 同一入口。

**移植的核心资产：两级定位 + 唯一性要求**

参考实现真正值钱的不是提示词，而是这套补丁应用语义：

1. **先试行号区间**：AI 给的 `start_line`/`end_line` 区间内文本逐字等于 `old_text` → 按区间替换；
2. **否则退化到精确字符串匹配，且必须唯一**：
   - 出现 0 次 → 拒绝（AI 编造了原文）；
   - 出现多次 → 拒绝（上下文不足，要求补充更多上下文）。

**为什么不做模糊匹配**：正文是最终交付物，改错一个字比不改更糟。宁可拒绝、交回人工，也不要猜。

**相对参考实现补上的两项**

| 能力 | 为什么必须补 |
|---|---|
| **数字边界保护** | 本软件的 `FACT_PATTERNS["工期"]` 只捕获 `(\d+)`，值是 `"30"` 这种极短串。不加保护，替换 `30` 会把 `"300 个日历天"`、`"3.30 元"`、`"1300 元"` 里的 `30` 一起改掉——这是灾难性的 |
| **区间重叠整批拒绝** | 多个待替换值互相包含时（`AB` 与 `ABC`），字符区间会重叠。区间编辑靠下标定位，半吊子替换比不改更糟，故整批拒绝并交回人工 |

**两条使用路径**

| 路径 | 入口 | 适用场景 | 手段 |
|---|---|---|---|
| 宿主确定性 | `POST /consistency/conflicts/{id}/autofix` | 同一事实被写成两种**取值**（工期 30 / 45） | 把旧值统一成目标值（字符区间替换） |
| AI 语义 | `POST /consistency/repair/{project_id}` | 同一事实用**不同措辞**表达（正文「2026 年 5 月竣工」vs 事实「工期 90 天」） | AI 产出 `{old_text, new_text}` 局部补丁 |

**AI 路径的安全设计**：AI **只产出局部补丁，正文由宿主改写**。AI 编造的 `old_text` 会被唯一性
校验拒绝，编造的小节编号会被丢弃（只接受本次送审范围内的编号）——**幻觉无法污染正文**。
这是相对「让 AI 整段重写」的核心优势。

**冲突状态收敛用可验证判据**：AI 补丁不绑定具体 `conflict_id`，所以**不靠补丁反推冲突已解决**。
改为落文后重判：某条冲突的多个取值中若仍有 ≥2 个能在正文里找到，就保持未解决；只剩 ≤1 个才标已解决。
这样不会出现「谎报修复」。

**提示词**：新增 `CONSISTENCY_PATCH_SYSTEM`（注册表 56 → 57）。

**前端**：`ConsistencyPage` 原无条件弹「已应用修复」——现在按后端返回的 `status` 区分展示
（`ok` → success，`no_change` → warning），并新增「预览 AI 补丁」/「AI 补丁修复」按钮与结果卡片
（逐条展示被拒绝的补丁原因与 AI 判定无法局部修复的条目）。

### Task 8 · 任务组互斥锁：sqlite 行级互斥 + 心跳超时（跨进程安全）

| 项 | 说明 |
|---|---|
| 参考实现 | 易标 `taskService.cjs` 的 `lockPolicy: 'group-exclusive'` + `assertTaskCanStart` |
| 本软件原状 | **没有任何任务组互斥**；`/generate-content` 入口零校验 |
| 改后 | 锁下沉到 sqlite 行级唯一约束 + 心跳续约 + 超时回收；接入正文生成全生命周期 |
| 影响面 | 重复点击「生成正文」会双跑、进度错乱、AI 成本翻倍、正文互相覆盖 |

**为什么不能照搬参考实现**

参考实现是 **Electron 单进程**桌面应用，它的锁分两层：

1. 内存层：`const activeTasks = new Map()`（`taskService.cjs:320`），键是任务类型；
2. 持久层：工作区状态文件里的 `xxxTask.status`——只有
   「`status === 'paused'` 就拒绝启动同组新任务」这一条**能跨重启生效**。

本软件是 **FastAPI + Celery 的多进程部署**（`app/tasks/__init__.py::generate_section_content`
在独立 worker 进程里跑），所以内存 Map 在 worker 之间**完全失效**。同理，
`GenerationManager._tasks`（`dict[project_id, GenerationTask]`）与
`TaskRegistry`（进程内 asyncio 单例）也都只是单进程可见。

**因此把锁下沉到数据库**：`task_locks` 表 + **部分唯一索引**
`uq_task_locks_active ON task_locks(lock_key) WHERE status='active'`。
唯一的仲裁者是 sqlite，任何进程、任何 worker 都看到同一份锁状态。

> 为什么用**部分**唯一索引：唯一性只约束「活跃」行，已释放/已过期的历史行可以保留，
> 既保证互斥，又留了一份锁的审计轨迹（`GET /projects/{id}/tasks/locks` 可查）。

**锁粒度：任务组 × 项目（对参考实现的有意修正）**

参考实现是单工作区的，`group` 天然等于全局。本软件一个库里装多个项目，
若照搬「组级全局锁」，两个**不同项目**就无法并发生成正文——这是功能倒退。
所以锁键是 `"{group}:{project_id}"`：同项目同组互斥，不同项目互不干扰。

分组沿用参考实现的语义：`technical-plan`（招标解析/目录生成/全局事实/正文生成）、
`rejection-check`、`duplicate-check`、`export`。

**先修掉的真 BUG（高严重度）：正文生成入口零并发保护**

`generation_manager.create_task` 原实现直接 `self._tasks[project_id] = task`，
**没有任何前置检查**，`/generate-content` 入口也没有任何活跃任务校验。重复启动的后果：

1. 内存任务被**静默覆盖**——旧生成循环仍在跑，但它的进度更新会被记到新 `generation_id` 上；
2. `generation_tasks` 里插入**第二行 running**，`get_project_progress` 按 `started_at DESC LIMIT 1`
   只看得见新的，旧任务变成孤儿；
3. 两个循环并发写同一批 `sections`，正文互相覆盖，AI 成本翻倍。

现在：先抢锁 → 冲突抛 `TaskLockConflict`（内存/DB 零改动）→ 抢到锁后若创建过程出错则回滚释放锁。
SSE 入口把冲突转成 `{'status':'error','code':'TASK_LOCK_CONFLICT','message':...}` 的友好事件
（原实现异常会直接穿透生成器，SSE 连接无提示断开）。

**先修掉的真 BUG（高严重度）：残留任务判定在多进程下会误杀**

`get_project_progress` 原判据是「DB 里有 running/paused 行，但**本进程**内存里没有对应实例
→ 标记 `failed`，并把该项目 `sections` 的 `generating` 全部改成 `failed`」。

这条判据在多进程下是**破坏性的**：Celery worker / 另一个 uvicorn worker 正在生成时，
API 进程的内存里当然没有该实例 → 正在跑的正文被当场判死。

现在：先看锁——**锁仍活跃且未过期 → 说明确有进程持有它 → 原样返回，不做任何修正**
（响应里带 `owned_elsewhere: true`）；锁已过期/不存在才是真残留，走原有修正逻辑。
判定用 `task_lock.read_lock_state(conn, ...)` 复用当前连接，而不是 `get_active_lock`——
后者自己开 `get_db()`，退出时会 `commit()`，会把外层事务提前提交。

**先修掉的真 BUG（高严重度）：`rollback_dirty_sections` 从来没生效过**

`generation_manager.rollback_dirty_sections` 的 SQL 写了
`error_message = COALESCE(error_message, '任务异常中断，已自动回滚')`，
但 **`sections` 表根本没有 `error_message` 列**（见 `db.py` 的建表语句）。
于是这条 UPDATE 必然抛 `no such column: error_message`，被外层 `except Exception`
吞成一条 warning、整个事务 ROLLBACK——

**后果**：`sections` 的 `generating` 残留、`section_generation_progress` 的 `processing` 残留
**从来没被清理过**，断点续传会一直把这些章节当成「正在生成」而跳过。
修法：去掉对不存在列的写入（章节级错误信息本就由 `section_generation_progress.last_error` 承载）。
该函数此前**零测试覆盖**，所以坏了很久没人发现；本轮补了 4 条。

**心跳与超时**

| 机制 | 设计 |
|---|---|
| TTL | `DEFAULT_TTL_SECONDS = 1800`（30 分钟） |
| 续约点 | `update_section_progress`（每个章节进度更新），按 `HEARTBEAT_INTERVAL_SECONDS = 60` 节流 |
| 回收时机 | 每次 `acquire` 前先回收过期锁；应用启动时 `reclaim_stale()` 再回收一次 |
| 续约失败 | 返回 `False` 并打 warning。**只告警不中断**——正文已生成一半，中断只会留下更破碎的状态；但日志留痕，便于事后判断正文是否被并发写过 |
| 释放校验 owner | 必须匹配 `owner_id`，否则不释放。防止「已被超时抢占的旧任务在收尾时把新持有者的锁一起释放」（ABA） |

**与参考实现的一处有意差异（已在代码注释里写明，别当 bug 去"修"）**

参考实现还会检查「持久化的 `contentGenerationTask.status === 'paused'` 就拒绝启动同组新任务」，
并把「恢复」作为唯一豁免。本模块**没有**实现这条，因为本软件的「暂停」语义不同：
`task_control.pause_generation` 会真正 `set cancel_event` 并 `await` 取消 asyncio 任务，
暂停后的生成循环**确实已经停了**，那条 `paused` 记录只是休眠存档；而心跳只在
`update_section_progress` 里发，暂停后自然停止续约、30 分钟后过期。

后果：暂停超过 30 分钟后同项目可以启动新任务——这是可接受的，旧循环已经停了。
若将来要严格对齐，需额外加「paused 行 → 拒绝」判据，并同时给恢复流程一个显式豁免位
（否则会把自己的恢复路径挡住）。

**新增接口**

| 接口 | 用途 |
|---|---|
| `GET /projects/{id}/tasks/locks` | 查看本项目活跃锁（组标签、任务标签、持有者、剩余秒数、是否 stale） |
| `POST /projects/{id}/tasks/locks/reclaim` | 手动回收已超时锁（「确认持有者已死、但不想等 TTL 也不想重启」的兜底） |

**新增文件**：`app/services/task_lock.py`（锁模块，纯 DB 操作，不调 AI）。

### Task 9 · 后台任务持久化与中断对账 `app/services/task_snapshot.py`（新建）

| 项 | 说明 |
|---|---|
| 参考实现 | 易标 `recoverInterruptedOutlineGenerationTask`（`taskService.cjs:1002-1093`） |
| 本软件原状 | 目录生成的任务状态只活在进程内存里，进程被强杀时**一行都不落库** |
| 改后 | 运行期持续写 `background_tasks` 快照 + 独立心跳协程；启动对账把幽灵任务收敛成中断；任务状态接口暴露 `recovery_options` |

**参考实现到底做了什么（先澄清语义，避免移植错）**

易标的 `recoverInterruptedOutlineGenerationTask` **不是断点续跑**，而是**启动时的诚实对账**：

1. 若任务停在 `outline-selection` 阶段且 Agent 会话仍可复用 → 保留现场，等用户回来选目录；
2. 否则把任务从 `running` / `paused` 改成 `error`，写入固定文案「上次目录生成未完成，请重新生成目录。」，
   同时把持久化的 Agent 任务标 `interrupted`、清掉半成品模板。

真正的「续跑」依赖它的 Agent 运行时（`task-state.json` + Pi SDK session），**不可移植**。
可移植、且本软件确实缺的是第 2 条：**别让用户面对一个永远「运行中」的幽灵任务**。

**本软件的缺口（改前实测）**

- `v51_tasks` 表只在 `_run_outline_task` 的 `finally` 里写一次 → 进程被 `SIGKILL` / 断电时
  `finally` 不执行，**一行都不落库**，重启后完全看不到「上次跑到哪一步」；
- `expired_at` 是「保存时刻 + 2 小时」的固定值，**运行期间不会续期**；
- `TaskRegistry` 只是进程内 asyncio 单例，重启即空；
- **目录生成入口零并发保护**：Task 8 只把组锁接进正文生成，目录生成侧一直裸奔。

**新表 `background_tasks`**

运行期就持续存在的任务快照。关键设计：

- **部分唯一索引** `uq_background_tasks_running ON background_tasks(project_id, task_type) WHERE status='running'`
  —— 与 Task 8 的 `task_locks` 同构：只约束「运行行」，终态行留作审计轨迹；
- **存活判据 = 心跳超时**（`DEFAULT_STALE_SECONDS = 300`），**不是**「进程重启了所以全死了」。
  后者在多 worker 部署下会把先启动进程正在跑的任务全部误杀 —— Task 8 修过同类缺陷；
- 心跳间隔 `HEARTBEAT_INTERVAL_SECONDS = 60`，满足 `间隔 × 2 < 锁 TTL(1800)`；
- **读侧 / 写侧分离**：`list_interruptions()` 纯读（供轮询接口），`reconcile_stale()` 写侧
  （只在启动钩子 + 任务入口调用）；
- 每个 `(project_id, task_type)` 只暴露**最新**一条中断（前端 `RecoveryBanner` 用 `opt.type`
  当 React key，重复会撞 key）；
- 状态机：`running` / `interrupted` / `completed` / `failed` / `cancelled` / `superseded`。

对外接口：`register` / `heartbeat` / `update_progress` / `finish` / `get_by_task_id` /
`list_running` / `list_interruptions` / `interruption_summary` / `reconcile_stale` /
`acknowledge` / `read_state`（在调用方连接上读，不 commit —— 与 `task_lock.read_lock_state`
同样的理由：`get_db` 退出时会 `commit()`，嵌套调用会把外层事务提前提交掉）。

**接入点**

- `app/db.py`：`init_db()` 挂载 `background_tasks` 表与部分唯一索引；
- `app/routers/sse/sse_outline.py`：抢「技术方案」组锁（`outline-generation`，锁键含 `project_id`）
  → 登记快照 → 起独立心跳协程（L2 填充 / AI 自检可能十几分钟没有事件，不能挂在事件流上）
  → `_phase_callback` 写进度 → `finally` 停心跳 + 落终态 + `asyncio.shield` 释放锁；
- `app/main.py`：启动钩子调 `reconcile_stale()`，把上次异常退出的 running 行收敛为 interrupted 并打日志；
- `app/routers/tasks.py`：`GET /tasks/status` 增 `interrupted_<type>` 与 `recovery_options`；
  新增 `GET /projects/{id}/tasks/interrupted`、`POST /projects/{id}/tasks/interrupted/ack`；
- 前端 `RecoveryBanner.tsx`：区分「可恢复」与「已中断，需重新发起」，按钮文案随之变化。

**同时修掉的 3 个真 BUG**

| 严重度 | 缺陷 | 后果 |
|---|---|---|
| 高 | **目录生成入口零并发保护** | 双击「生成目录」→ 两个 `_run_outline_task` 并发跑 → 双份 AI 调用 + 两次 `_clear_and_save_outline` 的 DELETE+INSERT 竞态 + `v51_state` 互相覆盖 |
| 高 | **`is_reconnection` 判据对并发入口失效** | 原判据 `task_info.started_at < time.time() - 0.1`，对**两次请求间隔 < 0.1 秒**的并发入口完全失效（第二个请求拿到刚创建 50 毫秒的同一任务 → 判「不是重连」→ 又起一个协程）。改为 `getattr(task_info, "_task", None) is not None`（确定性事实） |
| 高 | **`load_v51_state_from_db` 无条件覆盖活跃状态** | 结尾 `_v51_states[project_id] = state` 会用 DB 行重建并覆盖内存中正在运行的 `V51TaskState`。而 `cancel_v51_task` / `resume_v51_task` 都是「先 `get_v51_state()` 再改字段」→ 覆盖后改的是新对象，工作流检查的是旧对象 → **「停止生成」静默失效**（用户以为停了，AI 还在烧）、审核 `resume_event` 永远等不到。修法：`V51TaskState.active_run` 标记 + 加载守卫 + `set_v51_active_run()` |

**自测暴露的第 4 个 BUG（中）**

`acknowledge` 只更新 `status = 'interrupted'` 的行，而 `list_interruptions` 会把「心跳超时的
running 行」也报告为中断。多 worker / 未重启场景下启动对账还没跑到那条 → 用户看到中断横幅、
点确认，接口返回 0 → **横幅永远消不掉**（用户对着假中断反复点击）。
修法：`acknowledge` 先在本项目（可选 `task_type`）范围内收敛 stale running，再标已知晓，
保证「`list_interruptions` 报告得出来的，`acknowledge` 就确认得掉」。

> 为什么不在 `acknowledge` 里做全库收敛：全库收敛本身幂等，但会在**别的项目**的审计轨迹里
> 留下与本项目无关的噪声。收敛范围用 `_reconcile_rows(..., project_id=..., task_type=...)` 限定，
> 并配了回归用例 `test_acknowledge_reconcile_scope_is_limited_to_project`。

### Task 10 · 任务组锁的横向补齐（横向体检）`app/routers/{rejection,duplicate,export}.py`

| 项 | 说明 |
|---|---|
| 起因 | Task 8 建了 `TASK_GROUPS` 分组注册表（11 个 task_type / 4 个组），但只把锁接进了「技术方案」组的 2 条路径 |
| 体检方法 | 用「谁 import 了 `task_lock`」反查真实接锁点，再与注册表求差集 |
| 发现 | **3 个组登记了但生产零调用方**（废标项检查 / 标书查重 / 文档导出）；另有 4 个 task_type 是照搬参考软件的僵尸登记项 |
| 改后 | 接锁点从 2 个增至 **5 个**，「技术方案」以外的三组全部落地 |

**体检的判据：会不会产生不可恢复的损害**

不按「有没有并发风险」一刀切，而按后果分级：

| 功能 | 形态 | 并发后果 | 处置 |
|---|---|---|---|
| 文档导出 | 同步 + SSE，写文件 | **两个请求同时 `build_docx` 写同一输出文件 → 文件损坏** | 修 |
| 废标项检查 | `BackgroundTasks` 三轮 AI | 双击 → 两轮完整三轮 AI、两行任务记录、结果互相覆盖 | 修 |
| 标书查重 | `BackgroundTasks` AI 分析 | 双击 → 双份解析 + 双份 AI、结果互相覆盖 | 修 |
| 全局事实生成 | 同步 await AI | 只覆盖同一字段（后写覆盖前写，用户看到的是最后一次），成本翻倍 | 评估后**不接** |
| 无效与废标项解析 | 同步 await AI | 纯读 + 返回，无写 | 评估后**不接** |

**修掉的 3 个真 BUG**

| 严重度 | 缺陷 | 后果 |
|---|---|---|
| 高 | **导出锁是进程内的** | `_export_locks` 是 `dict[int, asyncio.Lock]`，多 worker 下每个进程各一把 = 没有互斥；`TASK_GROUPS` 里的 `export` 组因此一直没有调用方。改为 Task 8 的 sqlite 行级组锁 |
| 高 | **SSE 导出把构建启动在锁外面** | 原顺序是「`if export_lock.locked(): 409` → `create_task(to_thread(_run_build))` → 生成器里才 `async with`」。而 `asyncio.to_thread` 会**立即**把 `_run_build` 提交到线程池 → `build_docx` 全程跑在锁外，两个并发请求都能通过 `locked()` 检查。修法：锁在路由层先抢到，`create_task` 挪进生成器体（即「拿到锁之后」才开始构建） |
| 高 | **废标检查 / 标书查重入口零防重复** | `POST /rejection/start`、`POST /duplicate/start` 直接 `create_task` + `bg.add_task`，注册表里登记的 `rejection-check-run` / `duplicate-analysis` 从未被使用 |

**一处必须做对的生命周期细节**

`BackgroundTasks` 模式下请求早已返回，锁**必须**在任务收尾的 `finally` 里释放 ——
在请求处理函数里释放等于「任务还没跑锁就没了」，互斥形同虚设。两个路由因此都把
`(lock_key, owner_id)` 作为参数传给 `_run_safely`。

另外 `duplicate` 的**缓存命中分支**不会起后台任务，锁没有收尾者，必须当场释放 ——
否则该项目 30 分钟内再也发不起查重（被自己的锁挡住）。

**发现的僵尸登记项（记录，未清理）**

`TASK_GROUPS` 里有 4 个 task_type 在本软件**完全没有对应功能**，是从参考软件照搬的：
`bid-section-extraction`（多标段识别）、`bid-analysis`（招标文件解析）、
`outline-adjustment`（目录 AI 调整）、`global-facts-adjustment`（全局事实 AI 调整）。

保留而非删除的理由：它们是「预留位」，删掉会让将来对齐参考实现时重新推导；
但必须在报告与测试里**显式登记**（`test_unwired_registry_entries_are_documented`
断言「未接锁的恰好是这 6 个」），防止清单无声漂移。

**顺带发现（未修，记录）**

`POST /duplicate/start` 没有 `Depends(get_current_user)`，而同族的
`POST /rejection/start` 有。属于鉴权一致性问题，与本轮「并发保护」主题无关，
且改动会影响前端调用契约，故不在本轮处理。

> - **`table-cleaning`（表格清理）**：参考实现只在用户把「表格需求」设为 `none`（不要表格）时

>   贸然移植会产生一堆没有调用方的死代码（本项目已下线过 6 个死模板，不宜重蹈）。
>   **结论：等真有「不要表格」的需求时再做。**
> - **`original-auditing`（原方案覆盖检查）**：只服务于「已有方案扩写」工作流，且需要
>   「原方案来源段切分」这一前置能力（参考实现用 `ORIGINAL_PLAN_SEGMENT_MAX_CHARS = 6000`）。
>   本软件有 `workflows_expand.py`（扩写流），但是否需要「来源段覆盖度审计」取决于业务侧是否需要
>   「逐段核对原方案内容有没有被保留」。**结论：需先确认业务需求再动手。**
>
> 另需注意：易标在超上下文时还有一套「滚动 patch + 分批定稿 + 全局合稿」的
> 分段流程（`shouldUseSegmentedRejectionFlow`，`limitRatio=0.6`），
> 本软件已有 `split_into_chunks` 分块机制覆盖了同类需求，未单独移植。
