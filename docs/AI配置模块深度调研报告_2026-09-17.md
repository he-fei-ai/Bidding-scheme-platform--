# AI 配置模块深度调研报告

> 调研日期：2026-09-17 · 代码基线：`backend/`、`frontend/`
> 调研方法：四路并行全量代码遍历 + 需求/架构文档对照 + 测试覆盖统计 + **关键论断逐一 grep 复核**

---

## 一、摘要（一页速览）

AI 配置模块是整个平台的**总开关**——所有 LLM 调用、图像生成、提示词编排都由它供参。核心代码约 **5,000 行**（后端 3,700 + 前端 1,400），涉及 6 张数据表、35+ REST 端点、7 个前端页面。

**总体判断：功能丰富度超出需求文档，但安全基线严重不足，「加密」与「配额」两套机制形同虚设。**

| 维度 | 评价 | 说明 |
|---|---|---|
| 功能覆盖 | ★★★★☆ | 主配置 / 厂商配置 / Profile 多档 / 图像配置 / 测试连接 / 用量仪表盘，能力齐全 |
| 架构设计 | ★★★☆☆ | 分层合理，但**双实现漂移**（provider_factory vs ai_provider_service）严重 |
| 安全 | **★☆☆☆☆** | **密钥明文落库**、**base_url 无 SSRF 防护**、**无 admin 角色校验** |
| 可靠性 | ★★★☆☆ | 降级链完整，但无熔断冷却；用量统计链路断链 |
| 文档一致性 | ★★☆☆☆ | 需求文档明显滞后，字段名、路由路径、加密算法描述均与代码不符 |

**四条最关键的发现（均已 grep 复核确认）：**

1. **API Key 明文落库，加密被主动降级**。`encrypt_api_key` 在 `app/` 下**零调用**（只有 `decrypt_api_key` 被引用）；`PUT /ai/config`（`ai_config.py:190`）直接 `INSERT api_key=data.api_key`；更关键的是 `db_migrations.py:837+` 有一条迁移，把全库存量 `ENC:` 密文**统一解密回明文**（注释：「存量 API Key 统一转为明文存储」）。加密组件（Fernet）写好了、密钥也托管了，但被写路径与迁移架空。
2. **base_url 写入无 SSRF 防护**。`_validate_base_url`（`ai_config.py:103-119`）**只校验 scheme 是 http/https**，注释明确写着「本地优先部署允许 http/https（含 localhost 与内网地址）」。写入内网地址后，服务端 `/ai/health`、`/ai/test`、`/ai/models` 会**携带真实 API Key** 向内网友起请求，构成 SSRF + 密钥外带。
3. **无 admin 角色校验**。`ai_config.py:17` 只有 `dependencies=[Depends(get_current_user)]`，全文件 grep `admin` **零命中**。任何登录用户都能改全局配置（`ai_config` 是 `CHECK(id=1)` 单行全局表）、删除 Profile、清空用量历史。叠加 `AUTH_ENABLED` 默认 `false`（`config.py:167`，`get_current_user` 直接返回 mock **admin**），等于匿名可改。
4. **可观测性断链**：`ai_usage_stats` 表永远为空——唯一的写入入口 `record_usage_from_provider`（`provider_factory.py:592`）**全仓零调用者**。前端用量仪表盘、成本统计、日预算进度条读到的是空数据。且 `token_budget_daily` 只用于展示，全库无一处依据 `budget_exceeded` 拦截请求。

## 三、配置模型：来源与优先级

**优先级链**：`默认常量 < DB < 环境变量`，实现在 `provider_factory.get_ai_config()`（`:460`）：
- `:468` 加载 `_AI_CONFIG_DEFAULTS`
- `:497` `config.update(db_config)`
- `:509-511` 最后 `env_config` 覆盖 → **环境变量优先级最高**

**默认常量**（`_AI_CONFIG_DEFAULTS`，`:96-108`）：
`provider_name=agnes` / `provider=openai_compatible` / `model=AGNES_MODEL` / `max_tokens=32768` / `temperature=0.7` / `concurrency=10` / `timeout=120`。

**易踩坑的隐藏分支**：`is_still_default` 逻辑（`:489-507`）—— 当 DB 行仍等于默认值时，只取 `max_tokens/temperature/concurrency/timeout/document_profile`，**丢弃 DB 的 model / base_url / api_key**。即「改了模型但没改厂商名」可能不生效。

**环境变量覆盖清单**（`_load_env_config`，`:431-457`）：`AI_API_KEY` / `DEEPSEEK_API_KEY` / `OPENAI_API_KEY` 三选一；`AI_MODEL` / `DEEPSEEK_MODEL`。

**多租户**：实际是**单租户全局**。`ai_config` 为 `CHECK(id=1)` 单行表，无 `project_id`；`model_configs.user_id` 被 `Depends(lambda: 1)` 硬编码（`ai_config.py:525/541/597`）。**没有项目级 AI 配置**。

## 五、Provider 体系与降级容错

### 5.1 适配器

| 适配器 | 行数 | chat | stream | JSON mode | 限流 | 备注 |
|---|---:|---|---|---|---|---|
| `OpenAICompatibleProvider` | 296 | ✅ | ✅ | ✅ | ✅ 全局信号量 | 覆盖 OpenAI/通义/SiliconFlow/智谱/Agnes，含 Agnes `result` 解包 hack |
| `AnthropicCompatibleProvider` | 249 | ✅ | ❌ | ❌ | ❌ | prompt caching、stop_reason 归一 |
| `DeepSeekProvider` | 36 | ✅ | ✅ | ❌ | ✅ | 继承 OpenAI，仅覆盖环境变量 |

**无共同基类**：`base.py` 仅 7 行，只定义 `AIMessage(role, content)`。三者靠鸭子类型协作，`supports_json_mode`、`last_usage` 属性不统一。

### 5.2 降级链

构造顺序（`get_provider_priority_order`，`:329-425`）：
`主配置 → text_provider_configs 已配置（active 插主配置后 / inactive 追加）→ AI Profile → provider_history → _FALLBACK_PROVIDERS`，按 `_normalize_url` 去重。

**失败判定**：靠 **HTTP 状态码**。同步 `_quick_health_check`（`:692`）status ∈ (200, 429) 视为健康（**429 限流被当成健康**）；异步 `get_working_provider`（`:743-790`）200 通过、429/401 跳过、其余 continue。

**无熔断、无冷却、无自动恢复主 provider** —— 每次调用重跑整条链并逐家发探活请求，`provider_history` 只由配置页的测试/保存动作写入，**真实对话失败不写**，成功率与真实健康度脱节。

**已知 bug**：`create_provider_with_fallback`（`:654-655`）用**主配置的 key** 去打所有兜底 URL，DeepSeek/OpenAI 兜底必然 401 空跑。

### 5.3 并发与限流

- 配置项 `concurrency` 被读取（`:502`、`sse_utils.py:325`）但**从未传给 `_make_provider`**（`:131-139` 无该形参）→ 对 provider 无效。
- 实际限流是 `openai_compatible.py:15-16` 的**模块级全局信号量** `asyncio.Semaphore(AGNES_MAX_CONCURRENCY, 默认 5)`，所有实例共享；Anthropic 无限流。
- 超时：工厂默认 120s；OpenAI 按 `max_tokens` 自适应（≥16000→180s、≥8000→120s），httpx read = 1.5×。
- 重试：`max_retries=2`；429 退避 `max(2^(n+1)*3, 5)` 并优先 `Retry-After`，5xx 退避 `2^n × jitter`。

### 5.4 代理

`utils/proxy_config.py` 读 `HTTP_PROXY` / `HTTPS_PROXY`，`get_proxy_url`（`:17`）优先 HTTPS，`build_httpx_proxy_settings`（`:29`）返回 `{"proxy": url}`。

**未注入点**：`_quick_health_check`（`:700`）、`AIProviderService.create_with_fallback`（`:224/268`）不走代理；不支持 `NO_PROXY`。

## 六、密钥管理（最严重的问题）

```
crypto.py: Fernet (AES-128-CBC + HMAC-SHA256)
  密钥取自 BID_ASSISTANT_KEY，缺失则生成并落盘 backend/.secret_key
  ├─ decrypt_api_key  ✅ 7 处调用（读路径正常解密）
   └─ encrypt_api_key  ❌ 生产零调用
```

**写入路径全部明文**：

| 写入点 | 位置 | 行为 |
|---|---|---|
| 主配置 | `ai_config.py:190` | `INSERT api_key=data.api_key` 直接明文 |
| 厂商配置 | `ai_config.py:948` | 明文 |
| 图像配置 | `ai_config.py:564/1024` | 明文，且会把已加密值解密后回写 |
| Profile | `profile_service.py:121-123/188-189` | 明文 |

**雪上加霜**：`db_migrations.py:837+` 的迁移 32 主动把全库 `ENC:` 密文**解密为明文**（注释「存量 API Key 统一转为明文存储（幂等，兼容历史 ENC: 加密数据）」）。即使历史上有密文，启动迁移后也会全部变明文。

**脱敏做得正确**：`_display_api_key`（`ai_config.py:35-44`）统一返回 `***已配置***`，覆盖主配置/厂商配置/图像配置/Profile；`profile_service` 默认 `include_key=False`；测试连接不回显密钥。但这是**读路径防护**，磁盘上仍是明文。

**其他泄露面**：
- `/ai/health`（`:356/358`）回显 `base_url`，`:353/266` 回显上游 `resp.text[:200]`
- `/ai/test`（`:381`）回显原始异常 `{e}`
- `record_usage_from_provider`（`:606`）把 `api_key[:8]` 当 provider 标识写库
- `openai_compatible.py:167` 把响应前 500 字写 warning

## 八、前端

**`AIConfigPage.tsx`（748 行）** 三个 Tab：
1. **AI Profile**（`ProfileManager`，70-364）：Profile 增删改、设为默认、应用到主配置；表单含 `token_budget_daily`、`rate_limit_per_min`、`json_mode`、`task_type` 等；内置 4 个预设。
2. **用量统计**（`UsageDashboard`，369-454）：调用次数 / Token / 成本 / 成功率 / 预算进度 + 清理旧数据。
3. **健康度**（`HealthPanel`，459-501）：7 天健康分。

**入口分散问题**：`AIConfigPage` 名为「AI 模型配置」却**只读 Profile 档位**，真正编辑主配置的入口在 `TextConfigPage`（走 `/ai/provider-configs/{name}/activate`）。`AIConfigPage` 还有 5 个死导入（`getImageModelConfig`、`saveImageModelConfig`、`testImageConnection`、`getImageModelProviders`、`getUsageTrend`）。

**安全**：
- 密钥框为 `Input.Password`；数据源 `/ai/profiles` 不含密钥 → 无回显。
- `ImageConfigPage:84` / `TextConfigPage:63` 有 `setFieldsValue({api_key: config.api_key})` 明文回填模式，当前后端返回 `***已配置***` 所以安全，但属**脆弱模式**——读接口一旦改回真值即暴露。
- localStorage 只存 `auth_token`，未存密钥。配置页无 `dangerouslySetInnerHTML`。

**前后端对齐**：逐条核对，前端调用的接口后端**均存在**，未发现引用不存在的接口；反向有 5 个后端接口前端未接（`/ai/config` GET/PUT、`/ai/provider-history`、`/ai/image-model/quick-setup`、`/ai/image-model/usage`、`/ai/health`）。

## 十二、风险清单

### P0（建议立即处理）

| 问题 | 位置 | 说明 |
|---|---|---|
| **API Key 明文落库** | `ai_config.py:190/948/564/1024`、`profile_service.py:121` | `encrypt_api_key` 生产零调用；`db_migrations.py:837+` 主动把密文转明文。数据库文件泄露 = 全部厂商密钥泄露 |
| **base_url 无 SSRF 防护** | `_validate_base_url:103-119` | 只校验 scheme，注释明确放行 localhost/内网。写入内网地址后 `/ai/health`、`/ai/test`、`/ai/models` 携真实 Key 发起服务端请求 |
| **无 admin 角色校验** | `ai_config.py:17` | 全文件 grep `admin` 零命中。任何登录用户可改全局配置、删 Profile、清历史 |
| **鉴权默认关闭** | `config.py:167` | `AUTH_ENABLED` 默认 false，`get_current_user` 返回 mock admin → 匿名可改配置 |
| **弱默认密码** | `config.py:169` | `AUTH_INITIAL_PASSWORD` 默认 `admin123` |

### P1

- **可观测性断链**：`record_usage_from_provider` 零调用 → `ai_usage_stats` 空表；Anthropic 完全不采集；`tokens_used` 恒为 0。
- **配额未强制执行**：`token_budget_daily` 只展示不拦截。
- **双实现漂移**：`provider_factory` 与 `ai_provider_service` 各有 `get_config`/`create_provider`/`create_with_fallback`/`get_provider_priority_order`；后者缓存 TTL 300s 且 `clear_config_cache` 零调用。
- **concurrency 配置无效**：读了不传，实际限流是模块级全局信号量（默认 5）。
- **429 被判为健康**：`_quick_health_check:710`、`try_provider_health_check:826`。
- **兜底用错密钥**：`create_provider_with_fallback:654-655` 用主配置 key 打所有兜底 URL。
- **`Depends(lambda: 1)`** 硬编码 user_id（`ai_config.py:525/541/597`），身份与 token 脱钩。
- **`/prompts` GET 未鉴权**（`prompts.py:16/50`）。
- **危险操作无审计无回滚**：5 个删除/覆盖端点无二次确认。
- **代理未全覆盖**：`_quick_health_check`、`AIProviderService.create_with_fallback` 不走代理；不支持 `NO_PROXY`。

### P2（技术债）

- **`providers/base.py` 仅 7 行**，无抽象基类，三者靠鸭子类型，属性不统一。
- **硬编码**：`"gpt-4o"` 兜底散布 6+ 处（`:144/312/351/437/579/643/752/797`）；`_FALLBACK_PROVIDERS` 写死 URL/模型（`:39-91`）；`_PRICING` 价格表（`usage_stats.py:30-49`）。
- **魔法数字**：32768/16384/4096、120/180/240、`max_retries=2/3`、信号量默认 5。
- **异常静默**：`provider_factory.py:229/276/323`、`ai_provider_service.py:96/106/129/170/372` 全部 `logger.debug` 后返回空；`ai_config.py:187/1129` 空 `pass`。
- **死代码**：`record_usage_from_provider`；`AIConfigPage` 5 个死导入；`ai_provider_service` 大量别名仅供测试。
- **协议兼容 hack**：对所有 `openai_compatible` 无脑发 `response_format=json_object`（`:89-90`）可能 400；`detect_provider_type` 用 URL 子串（`:116-119`），自建反代易误判。
- **小 bug**：`anthropic_compatible.py:236` 日志字符串未插值 `{attempt + 1}`；`RetryableError` 定义在首次使用之后（`:245`）；`get_ai_config:466` 直接返回缓存对象，可被调用方改坏。

## 十三、改进建议

**第一步 —— 把加密接回去（最高优先级）**
在 4 个写入点（`ai_config.py:190/948/564/1024`、`profile_service.py`）调用已有的 `encrypt_api_key`；**删除 `db_migrations.py:837+` 的「密文转明文」迁移**，改为反向的「明文转密文」迁移。读路径已有 `is_encrypted` 兼容判断，改造成本可控。顺带修 `_validate_base_url`，接入已有的 `utils/ssrf.py:is_safe_http_url`（内网放行改为显式白名单开关，默认关闭）。

**第二步 —— 鉴权收紧**
`ai_config.py` 路由依赖加 `_require_admin`（`api_keys.py:30` 已有现成实现，直接复用）；删掉 `Depends(lambda: 1)`；给 `prompts.py` GET 补依赖；`AUTH_ENABLED` 与 `AUTH_INITIAL_PASSWORD` 的默认值反转（生产默认开 + 无默认密码）。

**第三步 —— 修断链**
给 `record_usage_from_provider` 接上调用方（在 `openai_compatible` / `anthropic_compatible` 的 chat 出口统一记录），补 Anthropic 采集；把 `budget_exceeded` 接成硬拦截；把 `concurrency` 真正传进 `_make_provider`。

**第四步 —— 收敛双实现**
确认 `ai_provider_service.py` 仅测试使用后，或删除，或改为 `provider_factory` 的薄代理（统一缓存 TTL 与失效入口）。同样处理 `create_with_fallback` 的两份实现。

**第五步 —— 补护栏与测试**
5 个危险操作端点加二次确认 + 审计日志表 + 配置版本回滚；补 `/ai/profiles` 系列与用量端点的 HTTP 层测试；前端引入 vitest 覆盖配置页。
