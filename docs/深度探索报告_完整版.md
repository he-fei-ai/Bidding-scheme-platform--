**提示词总数：66 个**（含共享规则 3 个）

### 2.2 注册机制

`_registry.py` 中的 `_reg()` 函数：

- 自动提取 `{VAR}` 和 `__VAR__` 两种占位符变量
- 存入全局 `_ALL_PROMPTS` 字典
- 注册元数据：`key`、`category`（前端分组标签）、`label`（中文标签）、`variables`

### 2.3 缓存策略

```
get_prompt(key) 流程
   │
   ├─ 1. 缓存未加载？ → _load_prompt_cache()
   │                        └─ 从 DB prompt_templates 表 SELECT
   │                            异常时缓存 = {}（不抛错）
   ├─ 2. 缓存中存在 key？ → 返回 DB 内容（覆盖硬编码）
   └─ 3. 回退到 _ALL_PROMPTS[key]['content']
            ├─ 存在 → 校验变量缺失并记录警告
            └─ 不存在 → 返回空字符串 ""
```

### 2.4 按分类的提示词清单

| 分类 | 数量 | 典型提示词 | 用途 |
|------|------|-----------|------|
| 文件解析 | 14 | `PROJECT_OVERVIEW_PROMPT`, `SCORING_REQUIREMENTS_PROMPT` | 招标文件分析 |
| 目录生成 | 18 | `OUTLINE_V51_LEVEL1_SYSTEM`, `OUTLINE_REVIEW_SYSTEM` | 三级目录生成+审核 |
| 正文生成 | 5 | `CONTENT_GENERATION_SYSTEM`, `CONTENT_CONTINUE_PROMPT` | 章节正文+续写 |
| 图表类 | 11 | `ARCHITECTURE_ARRANGE_SYSTEM`, `COMPARISON_GENERATE_SYSTEM` | 5种图表编排+生成 |
| Mermaid | 6 | `MERMAID_REPAIR_PROMPT`, `FLOWCHART_GENERATE_SYSTEM` | Mermaid代码+修复 |
| 配图 | 2 | `ILLUSTRATION_ARRANGE_SYSTEM`, `ILLUSTRATION_PLAN_SYSTEM` | AI插画编排+方案 |
| 检查 | 5 | `REJECTION_CHECK_SYSTEM`, `SPELLING_CHECK_SYSTEM` | 废标/错别字/逻辑 |

### 2.5 关键设计决策

1. **DB 优先覆盖**：允许运维人员通过 DB 修改提示词，无需改代码
2. **两阶段图表链路**：编排（轻量预筛）→ 生成（深度编排），避免每次做完整推理
3. **共享规则注入**：`_shared.py` 统一管理标题编号规范、禁用词列表
4. **变量自动提取**：`_reg()` 自动提取占位符，配合 `validate_prompt_variables()` 编译期检查
5. **纯净输出约束**：几乎所有提示词末尾强调"严禁附加解释或 Markdown 代码围栏"
6. **兜底策略全覆盖**：每个提示词都有兜底规则

### 2.6 调用链全景

```
业务代码 → get_prompt(key) → _cache 查询 → 回退到 _ALL_PROMPTS
    │
    ▼
组装 messages (system + user prompt)
    │
    ▼
workflows_base.py:collect_json_response()
    ├─ 尝试 json_mode 调用
    ├─ JSON 解析失败 → JSON_REPAIR_PROMPT 修复
    └─ 修复失败 → 降级重试
```

### 3.3 V5.1 vs V2/V3 核心区别

| 维度 | V5.1 | V2/V3 |
|------|------|-------|
| **一级生成** | AI 根据评分点自由生成 | 28 章固定模板 + AI 补充 |
| **骨架构建** | 预构建骨架，AI 只填标题 | 模板 + AI 全量生成 |
| **并发模式** | 全并发 + 流水线队列 | 首条串行预热 + 并行 |
| **审核机制** | 多阶段人工审核（L1/L2/Final） | 无 |
| **断点续生** | 支持（DB 持久化 + 乐观锁） | 不支持 |
| **三级标题** | 多样化生成算法（5 级策略） | AI 直接生成 |
| **容错策略** | 单节点失败默认填充，不中止整体流程 | 整体失败 |
| **自检** | 本地检查 + AI 深度检查 | 仅业务校验 |

### 3.4 断点续生机制

```
V51TaskState 状态管理:
  project_id, current_phase, edited_outline,
  level1_outline, full_outline,
  resume_event (asyncio.Event), cancelled,
  _confirm_version (乐观锁)

持久化:
  save_v51_state_to_db() / load_v51_state_from_db()
  → v51_tasks 表，2 小时过期
  → 完整上下文（summary, scoring_points, industry_profile 等）

断点续生流程:
  1. 前端加载 OutlineEditorPage → fetchPendingV51Task()
  2. 检测到未完成任务 → 显示恢复横幅
  3. 用户点击"恢复生成" → 重新建立 SSE 连接
  4. 后端 load_v51_state_from_db() 恢复状态 → 从 current_phase 继续
```

### 3.5 SSE 事件类型

| 事件 | 说明 | 触发时机 |
|------|------|----------|
| `connected` | 连接建立 | 初始 |
| `generating.phase=context` | 提取项目数据 | 开始 |
| `generating.phase=outline_phase` | 步骤推进 | 每阶段 |
| `generating.phase=children` | 子目录生成进度 | L2 每章完成 |
| `generating.phase=heartbeat` | 心跳（10s 间隔） | 无事件时 |
| `generating.phase=v51` | V5.1 状态信息 | 状态恢复 |
| `review_needed` | 需要人工审核 | L1/L2/Final 审核点 |
| `review_auto_confirm` | 自动确认 | auto_confirm=True |

| `completed` | 生成完成 | 成功结束 |
| `error` | 错误 | 任何异常 |
| `stopped` | 已停止 | 用户取消 |

## 4. 正文生成模块（Content）

### 4.1 整体流程（5 阶段）

| 阶段 | 函数 | 说明 |
|------|------|------|
| **① 初始化** | `_try_get_provider()` → `_fetch_project_data_async()` → `_build_leaf_dicts()` | 获取 AI 提供商、项目数据、构建叶子章节列表 |
| **② 内容编排**（可选） | `orchestrate_content()` | 让 AI 预判每个叶子节点的内容类型 |
| **③ 字数采样预估**（可选） | `estimate_total_words_from_probe()` | 采样头+中+尾 3 章节预估总字数 |
| **④ 并发生成** | `generate_sections()` → `_generate_one()` → `_do_generate_section_with_optimizations()` | 核心生成阶段 |
| **⑤ 后处理** | 兜底扩写 → 一致性审计 → 配图生成 | 补全字数不足、事实检查、自动图表 |

### 4.2 并发控制（3 层信号量）

```
┌─────────────────────────────────────────────────┐
│  GLOBAL_AI_CONCURRENCY_MAX (asyncio.Semaphore)  │ ← 全局：所有项目总并发上限
├─────────────────────────────────────────────────┤
│  _ai_monitor (AIRequestMonitor, max=20)         │ ← 全局：基于 Condition 的等待队列
├─────────────────────────────────────────────────┤
│  DynamicSemaphore (初始值 = concurrency 参数)     │ ← 项目级：实际并发度
│    └─ AdaptiveConcurrencyController               │    ← 动态调整：根据响应时间
└─────────────────────────────────────────────────┘
```

### 4.3 自适应并发控制器

- 滑动窗口 20 次请求，每 3 次检查一次调整
- 平均响应时间 > 30s → 并发减 1（最低 1）
- 平均响应时间 < 8s 且失败率 < 5% → 并发加 2（最高 10）

### 4.4 降级链

```
collect_json_response() 统一 JSON 生成入口:
  1. json_mode 尝试（response_format=json_object）
     ├─ 超时（60s）→ 降级到非 json_mode 重试
     │   └─ 标记 json_mode_timeout_cache（30s 内跳过 json_mode）
     ├─ 提供商错误 → 降级到非 json_mode
     │   └─ 标记 json_mode_unsupported（10 分钟内跳过 json_mode）
     └─ 成功但解析失败 → JSON 自修复
         └─ 将原始输出 + 错误回喂给 AI，要求输出严格 JSON
             └─ 修复失败 → 重试（max_retries=1）
```

### 4.5 质量重试

```python
while retry_count <= max_retries:   # 默认 max_retries=2
    temperature = min(0.7 + 0.15 * retry_count, 0.95)  # 递增温度
    content = await generate_section_content(...temperature=当前温度...)
    
    quality = await evaluator.evaluate_content(content)
    if quality["score"] >= quality_threshold:  # 默认 70 分
        break  # 达标
```

### 4.6 质量评估（5 维度）

| 维度 | 权重 | 评估方式 |
|------|------|----------|
| 字数达标率 | 20% | 规则：实际字数 vs 目标字数 |
| 结构完整性 | 25% | 规则优先，＜40 分时触发 AI 评估 |
| 专业性 | 25% | 规则优先（行业关键词密度），＜40 分时触发 AI 评估 |
| 重复度 | 15% | 规则：段落指纹匹配 |
| 相关性 | 15% | 规则默认 70 分，＜40 分时触发 AI 评估 |

### 4.7 续写机制

```python
max_rounds = max(5, target_chars // 1000)  # 最多 ~10 轮
stall_rounds = 0
MIN_INCREMENT = 30    # 单轮新增字数阈值
MAX_STALL = 2          # 允许连续停滞轮次
```

- 每轮用尾部 2000 字 + 头部摘要的增量上下文
- 检测到连续 2 轮无进展（<30 字）则提前退出

### 4.8 分层消息结构（9 层 V2.1）

```
1. System Prompt（CONTENT_GENERATION_SYSTEM + 标题编号规范）
2. 全局事实变量（_format_facts_for_prompt）
3. 项目概述
4. 知识库素材（RAG 检索结果）
5. 上级章节（防止越界）
6. 同级章节（防止重复）
7. 编排决策（预判图表类型）
```

### 8.3 性能瓶颈分析

#### 瓶颈 1：SQLite 写锁串行化

**问题**：SQLite 写操作是串行的（文件级锁）。当并发正文生成时，多个章节同时写入 DB 会排队。

**影响**：高并发下（>10 并行章节），DB 写入成为瓶颈。

**建议方案**：
- 使用内存缓冲区批量写入（每 5 秒或 20 条合写一次）
- 或迁移到 PostgreSQL（支持并发写）

#### 瓶颈 2：内存缓存无容量限制

**问题**：`SectionContentCache` 默认 max_size=100，但其他缓存（如 `_prompt_cache`、`mermaid_renderer` 缓存）无显式容量限制。

**影响**：长期运行可能内存泄漏。

**建议方案**：
- 为所有缓存添加 `max_size` 和 TTL 配置
- 统一使用 `@lru_cache` 或 `cachetools.TTLCache`

#### 瓶颈 3：SSE 队列溢出静默丢弃

**问题**：`_NotifyQueue` 继承 `asyncio.Queue`，默认无上限。队列打满时入队不阻塞也不报错。

**影响**：极端情况下事件丢失，前端进度显示不准确。

**建议方案**：
- 设置 `maxsize` 参数
- 添加队列满时的告警日志

#### 瓶颈 4：全量 pytest 偶发崩溃（WinError 5）

**问题**：`backend/.pytest_cache` 在中文路径偶发访问拒绝（exit -1 无输出）。

**影响**：CI 不稳定。

**修复**：已在 `pyproject.toml` 中配置 `cache_dir = "tests/.pytest_cache"`，但需确认是否完全解决。

#### 瓶颈 5：大文件文本提取性能

**问题**：OCR 解析和 PDF 提取对大文件（>50MB）消耗显著。

**建议方案**：
- 添加文件大小限制的前端提示
- 大文件自动分页处理
- 后台异步解析 + 进度通知

## 9. 总结与建议
