### 🎯 真凶：数据库连接池耗尽（有日志实锤，非推测）

进一步抓取失败用例的日志，拿到了**确定性的报错**而非推测：

```
ERROR app.routers.projects:projects.py:22 列出项目失败: Database connection pool exhausted (max=32, active=32)
ERROR app.main:main.py:375 数据库错误: ... | PUT /api/v1/ai/config
ERROR app.main:main.py:375 数据库错误: ... | POST /api/v1/projects/999/sections/999/generate-illustration
RuntimeError: Database connection pool exhausted (max=32, active=32)
FAILED tests/test_integration.py::test_projects_crud - assert 500 == 200
FAILED tests/test_integration.py::test_ai_config_with_encryption - RuntimeErr...
FAILED tests/test_integration.py::test_arrange_illustration_endpoint - Runtim...
```

**机制**（`app/db.py::DBPool`）：

- `DBPool(max_connections=32)` 按**线程**缓存连接（`_all_connections: list[(thread_id, conn)]`）；
- `_reap_dead_thread_connections()` 只在**线程已死**且空闲超 60s 时才回收，
  并且有 **10s 冷却**；**存活线程持有的连接永不回收**；
- 全量套件里每个 `asyncio.run()` 都新建事件循环与 `ThreadPoolExecutor`，
  idle worker 线程 `is_alive()` 恒为 True → 连接只增不减 → 32 打满；
- 一旦打满，`get_connection()` 抛 RuntimeError，**整个进程后续所有数据库操作全部 500**，
  于是**与池毫不相干的用例**（`test_projects_crud` 等）跟着红。这完美解释了
  「单独复跑全过、全量里红、失败集合每次不同」。

**「不是我的改动」的决定性证据**：把本轮新增的测试文件整个排除后重跑全量
（`--ignore=tests/test_bugfix_2026_09_18_task_layer.py`），**同样 4 条、同样 `pool exhausted`**
（1705 passed / 4 failed）。

**本轮顺带做的修复（高）**：`_reap_dead_thread_connections` 的 10s 冷却会让「刚死掉的线程」
的连接在冷却期内无法释放，而调用方紧接着就判池满抛错。现改为**判池满之前先强制再扫一次**
（`force=True` 跳过冷却；`self._lock` 是 `RLock`，可重入，安全）。
新增 2 条回归（N 组）：`force=True` 确实跳过冷却完成回收；无连接可回收时仍照常抛池满
（不能吞掉这个致命信号）。

**已彻底修复（接续上一段，`2026-09-18` 收尾）**：真正打满 32 个配额的是**存活**线程
（asyncio 默认 `ThreadPoolExecutor` 的 idle worker 永不退出），强制回收（`force=True`）救不回来。
本轮按上面写的方案落地了 **世代号（generation）抢占机制**：

| 改动 | 位置 | 说明 |
|---|---|---|
| 新增 `POOL_IDLE_RECLAIM_SECONDS = 30.0` | `app/db.py` 模块常量 | 「存活但空闲超 30s」即视为可抢占 |
| 新增 `_reclaim_idle_connection(exclude_thread_id)` | `DBPool` | 池满时的**最后一道抢救**：挑「最久未用」的那根连接关闭并移出池；**跳过调用方自己与主线程**；只递增**被抢占线程**的世代号（其他线程不受影响） |
| 新增 `self._thread_epoch` / `_local.epoch` | `DBPool.__init__` / `get_connection` | 线程本地记录取连接时的世代号；`get_connection()` 复用线程本地缓存**前**先校验，不一致就丢弃旧连接重建 —— 保证被抢占的线程**不会**拿到已 `close()` 的 sqlite3 对象 |
| 池满抛错前调用抢占 | `get_connection` | 顺序：死线程回收（含 `force`）→ 空闲抢占 → 仍满才抛 `pool exhausted` |
| `_acquire_healthy_connection` 重试分支改用 `discard_connection` | `app/db.py` | 顺带修掉同源的配额泄漏：此前 I/O 重试时只 `close()` + 清 `_local`，连接仍留在 `_all_connections` 里占配额，而本线程存活、死线程回收永远救不回来 |

**为什么这样是安全的**：关键难点是「关闭别的线程的连接，那线程下次就用到了已关闭的对象」。
世代号解决了这一点 —— 抢占方**只**递增被抢占线程的世代号，该线程下次 `get_connection()` 时
`_thread_epoch[tid] != _local.epoch`，会先丢弃旧连接再重建，且不影响其他任何线程的缓存。
抢占还要求「空闲超 30s」（每次复用连接都会刷新 `_last_used`），尽量不误伤正在干活的连接。

新增 5 条回归（O 组，`tests/test_bugfix_2026_09_18_task_layer.py::TestOIdleConnectionReclaim`）：
① 抢占成功且只递增被抢占线程的世代号；② **被抢占的线程能自行重建**（在它里面执行
`SELECT 1` 验证不是已关闭连接）；③ 池满时新线程取连接不再抛错；④ 刚用过的连接不被抢占
（仍照常抛 `pool exhausted`，不能吞掉这个致命信号）；⑤ 主线程连接永不被抢占。

| 高 | **连接池配额被「存活但空闲」线程永久占满** | 这是全量测试长期红灯的真凶（详见「一之二 · 🎯 真凶」）：`_reap_dead_thread_connections` 只回收**已终止**线程的连接，而 asyncio 默认 `ThreadPoolExecutor` 的 idle worker 永不退出、每个新事件循环还会新起一批线程。一旦 32 个配额打满，`get_connection()` 抛 `RuntimeError`，**此后整个进程的所有数据库操作全部失败、只能重启** —— 对用户就是「点了生成，什么都没发生」 | 新增 `_reclaim_idle_connection()` 作为池满前的最后抢救：抢占「最久未用且空闲 > 30s」的连接（跳过调用方自己与主线程）。安全性由**世代号（generation）**保证 —— 抢占时只递增被抢占线程的 `_thread_epoch`，该线程下次 `get_connection()` 校验 `_local.epoch` 不一致即丢弃重建，**不会**拿到已 `close()` 的 sqlite3 对象；其他线程缓存不受影响 |
| 中 | **I/O 重试路径泄漏配额** | `_acquire_healthy_connection` 的 I/O 重试分支只 `conn.close()` + 清 `_local.connection`，连接仍留在 `_all_connections` 里占配额；而本线程是存活线程，死线程回收永远救不回来。`database is locked` 一旦连续出现，每重试一次就漏一个配额 | 改走 `_pool.discard_connection(conn)`，真正从池的所有索引中摘除 |

### 7. 已知设计状态（非缺陷）：6 个 Celery 任务包装器当前「休眠」

收尾复查时抓到的一件事 —— 必须点明，但不属于本轮要静默改掉的缺陷：

- `app/tasks/__init__.py` 的 6 个 `@celery_app.task` 包装器（`parse_and_extract_file` / `generate_section_content` / `generate_docx_export` / `process_knowledge_document` / `run_rejection_check` / `run_duplicate_check`）实现都**正确**、本轮已修到可导入 + 可派发；
- 但**全库没有任何调用方**触发它们 —— 没有 `.delay()` / `.apply_async()` / `send_task()`，也没有 `dispatch_task()` 调用点（grep 实锤）；
- 6 项功能实际由 **routers → `services.*` 直连路径（或 SSE 流）** 执行，例如 `routers/duplicate.py` 直接 `await duplicate.run_duplicate_check(task_id)`、`routers/rejection.py` 直接 `await rejection.run_rejection_check(...)`、`routers/sse/sse_content.py` 走 SSE。

也就是说，这 6 个包装器是「与 SSE/直连路径并存的**平行实现**，当前休眠」。它们**不是空任务**（有真实实现），也**没有造成「功能无结果」**（功能在另一路径正常跑）。

**为何本轮不强行接线**：两套实现行为并不完全一致（例如 celery 版的 `run_rejection_check` 不支持 `dimension=`、章节生成的 celery 版不接 SSE 进度回调）。把 6 个 router 改成 `dispatch_task(...)` 触发，会**改变现有 SSE 行为**且引入 celery 部署耦合，属架构决策，不能静默做。

| 项 | 说明 | 建议 |
|---|---|---|
| 6 个 Celery 包装器休眠 | 已注册但无调用方；功能由 SSE/直连路径执行 | 若计划上 celery 集群异步卸载，由 6 个 router 改为 `dispatch_task(name, args, kwargs, allow_inline=True)` 触发（无 broker 时自动回退就地执行，零风险）；否则应移除装饰器或加注释标明「非入口」，避免误导后人以为是异步入口 |
| `dispatch_task` 当前仅自测/beat 用到 | 除 `run_scheduled_reports`(beat) 与单测外无业务调用方 | 同上，是否启用 celery 派发由部署形态决定 |

## 七、测试说明（踩坑记录）

1. **`app.db` 没有 `DB_PATH` 属性** —— `conftest.py` 已把 `BID_ASSISTANT_DATA_DIR` 指向独立临时目录并 `init_db()`，测试直接建项目即可，不要 patch 库路径。
2. **mock 内部协程必须 `async def`** —— `_generate_level3_v51`/`_self_check_v51` 在主链路是 `await` 的，`lambda` 替身会以 "object list can't be used in 'await' expression" 失败。
3. **mock 延迟导入要 patch 源模块** —— `files.py` 内是 `from ..db import get_db`（函数体内），必须 patch `app.db.get_db`。
4. **源码断言要排除注释行** —— 修复注释会原文引用旧的错误写法，对全文做子串断言会永远失败。
5. **`run_full_audit` 是同步方法** —— 返回 `AuditResult`，冲突在 `.conflicts`，不要 `asyncio.run` 包。
6. **不要并行跑多个全量套件** —— 实测会导致 `test_db_pool.py` 出现 `sqlite3.OperationalError` 假红灯（单独复跑 6 passed）。
7. **不要在测试运行期间改源文件** —— 「源检查类」用例（`inspect.getsource`）会读到半成品，实测 `test_perf_bottleneck_fixes.py` 出现假红灯（单独复跑 90 passed）。
8. **手搓 `starlette.Request` 必须给全 ASGI scope** —— `tests/test_auth_service.py::test_no_token_disabled_mode` 原本只传 `type/headers/method/path`，缺 `query_string`；在 `get_current_user_dependency` 补上 `?token=` 回退（BUG-FIX 2026-09-18 P1，修复中间件与依赖的单腿断链）后，`request.query_params` 会以 `KeyError: 'query_string'` 炸掉。真实 ASGI 请求的 scope 必带该键 → 属**测试假设错**，补 `"query_string": b""` 即可，不要为此改实现。
9. **⚠️ 全量红灯未必是回归，先排除「并发编辑」** —— 本轮实测同一份代码连续三次全量：13 failed → 11 failed → 0 failed，失败项每次不同、单独复跑均通过。根因是**代码库被另一个进程并发修改**（mtime 佐证见「一之二」）。判据：① 失败是否集中在 `inspect.getsource` 类用例；② 单独复跑该文件是否全过；③ `ls -lt` 看源文件 mtime 是否仍在跳动。三者皆中即可判定为环境干扰，别去改实现
10. **CRLF 文件的多行块替换** —— `workflows_outline_v51.py` 是全 CRLF，多行 `old_string` 按 LF 匹配会失败；`Edit` 工具对**单行**替换能正确保持 CRLF，**多行块**建议写一次性补丁脚本（`read_bytes` → 统一替换 → `write_bytes`，脚本内 `assert count == 1`），改完立即复核 CRLF 计数与 AST。
11. **同一文件连续发多个 `Edit` 会静默丢失** —— 本轮在 `app/db.py` 上连续发 3 条编辑，其中 `__init__` 那条**报成功但未落盘**（后两条正常），直到跑测试报 `AttributeError: 'DBPool' object has no attribute '_thread_epoch'` 才发现。**对策：每条编辑后立刻 `grep` 复核关键符号**，不要等测试报错才发现。
12. **抓「并发编辑」用 mtime 快照 diff，比静置观察更可靠** —— 对 `app/**/*.py` 做两次 mtime 快照（间隔 60s、期间**自己不碰任何文件**）后 diff，能抓到静置看不出的短写窗口。本轮实测抓到 `content_cleaning.py` / `mermaid_common.py` / `export.py` / `tasks/__init__.py` 被外部改写；并发编辑还会留下**半截改动**（改了赋值漏改引用 → 导出直接 `NameError`），所以改完必须复查新符号的**所有**引用点，并回头校验自己的改动没被覆盖。
13. **别把「环境干扰」当终点：漂移的红灯里可能藏着真缺陷** —— 本轮一度把 4 条红灯归因为「并发编辑 + 并发跑测」，直到抓取失败用例日志才看到 `Database connection pool exhausted (max=32, active=32)`。**判据升级**：环境干扰只能解释「失败集合随机漂移」，一旦**某几条失败稳定复现**（连续多次全量都是同样 4 条），就必须去抓日志找确定性根因，不能停在「大概是环境问题」。
