## 二、废标检查（Rejection Check）

### 2.1 功能概述

废标检查模块旨在对标书终稿进行多维度的 AI 风险审查，帮助用户在上传前发现可能导致废标或扣分的隐患。支持对 **多份投标文件** 同时检查，并支持从项目工作台直接导入招标文件与技术方案。

**检查维度**（三类并行）：

| 维度         | 检查内容                                                     | 输出形式                   |
| ------------ | ------------------------------------------------------------ | -------------------------- |
| **废标项**   | 对照招标文件的“无效标”、“废标”条款，判断投标响应是否触犯     | 风险列表 + 原文引用 + 建议 |
| **错别字**   | 全文扫描常见错别字、用词不当、标点错误                       | 错误列表 + 位置 + 修改建议 |
| **逻辑谬误** | 检查自相矛盾、数据不一致、逻辑跳脱（如工期/人员/设备前后不符） | 问题列表 + 上下文定位      |

### 2.2 用户故事

| 编号  | 用户角色 | 故事                                                        | 验收标准                                   |
| ----- | -------- | ----------------------------------------------------------- | ------------------------------------------ |
| RC-01 | 投标专员 | 从项目工作台一键导入当前标书的招标文件和技术方案            | 选中项目后，自动填充招标文本和投标方案正文 |
| RC-02 | 投标专员 | 手动上传多份投标文件（.docx/.pdf）进行批量检查              | 支持多文件上传，结果按文件分组展示         |
| RC-03 | 投标专员 | 系统自动从招标文件中提取废标项清单，可手动增删改            | 提取准确率 ≥90%，支持用户编辑检查项        |
| RC-04 | 投标专员 | 三类检查并行执行，进度实时反馈，单项失败不影响其他项        | 并发执行，错误独立提示，支持单维度重试     |
| RC-05 | 审核人   | 检查结果按“废标项/错别字/逻辑”分 Tab 展示，可标记误报并隐藏 | 误报标记后永久隐藏，支持恢复               |
| RC-06 | 投标专员 | 对长招标文件，系统采用滚动分段策略避免超出上下文窗口        | 自动分段，全局合稿，不丢失上下文           |

### 2.3 交互流程（三步向导）

```
Step 1：选择文档
   ├─ 从项目导入：选择已有项目 → 自动填入招标原文 + 技术方案正文
   ├─ 手动上传：上传招标文件（.docx/.pdf） + N 份投标文件（.docx/.pdf）
   └─ 确认后进入 Step 2

Step 2：配置检查项
   ├─ 系统 AI 自动从招标文件提取无效/废标条款 → 展示为检查项列表
   ├─ 用户可编辑、删除、新增检查项（自定义）
   ├─ 可开关三类检查（废标/错别字/逻辑）的启用/停用
   └─ 点击“开始检查”

Step 3：检查结果展示
   ├─ 三类结果分 Tab（废标项 / 错别字 / 逻辑谬误）
   ├─ 每个结果卡片包含：问题描述、原文引用、风险级别、修改建议
   ├─ 支持操作：标记为误报（隐藏）、复制错误原文、单 Tab 重新检查
   ├─ 若上传多份投标文件，结果按文件分组（筛选器）
   └─ 支持导出检查报告（.docx 或 .pdf）
```

### 2.4 技术实现要点

#### 2.4.1 文本提取

复用平台 `services/files.py` 的多格式提取能力（`python-docx` / `pypdf` / LibreOffice），将上传的招标文件和投标文件转为纯文本，并保留段落结构与页码信息。

#### 2.4.2 废标项提取

通过 AI 从招标文件中识别“无效标”、“废标”、“否决投标”等关键词段落，结构化输出检查项。采用 `collect_json_response` 统一校验（见技术架构 4.4.5），确保 JSON 格式合规。

#### 2.4.3 滚动分段策略（长上下文）

当招标文件或投标文件超过 LLM 上下文窗口（如 128K）时，采用 **滚动审阅 → 候选定稿** 策略：

- **滚动审阅**：将全文按固定大小（如 20000 字符）切分为多个片段，每个片段与前一个片段重叠 2000 字符（保证上下文连贯），分别送入 AI 提取本片段内的风险项。
- **候选去重**：收集所有片段的候选风险项，按语义相似度合并（利用 embedding 或字符串相似度）。
- **全局合稿**：将去重后的候选风险项作为输入，再次调用 AI 进行最终审查和归并，输出统一清单。

该策略已在前端 `rejectionCheckTask.cjs` 中验证，最大可处理 200 万字符的文档。

#### 2.4.4 错别字检查

- 先按文档段落切分，每段调用 AI 识别错别字（利用语言模型），返回错误位置（段落索引 + 句子偏移）。
- 对识别结果进行 **原文位置校验**：用编辑距离或正则匹配确保建议替换词在原文中的位置准确，避免误报。
- 对识别出的错误列表进行后处理合并（连续错误合并为同一处）。

#### 2.4.5 逻辑谬误检查

- AI 综合分析全文中的工期、人员配置、设备型号、金额等关键数据，检查前后一致性。
- 采用“矛盾检测”提示词，要求 AI 以列表形式输出冲突点，附上相互矛盾的两个片段引用。

#### 2.4.6 多投标文件并发

对每一份投标文件，三类检查均并发执行（使用 `asyncio.gather`），任一维度失败不影响其他维度。结果按文件 ID 分组存储，前端通过筛选器切换查看。

#### 2.4.7 误报管理

前端本地存储用户标记为“误报”的检查项 ID（`localStorage` 或 `IndexedDB`），后续加载结果时自动过滤。用户可一键恢复所有误报。

### 2.5 数据模型（补充）

```sql

    id INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id INTEGER,                         -- 可选，关联项目

-- 检查项模板（可复用）
CREATE TABLE rejection_templates (
    id TEXT PRIMARY KEY,
    name TEXT,
    description TEXT,
    category TEXT,                              -- 废标/错别字/逻辑
    is_custom BOOLEAN DEFAULT 0
);
```

## 三、标书查重（Duplicate Check）

### 3.1 功能概述

标书查重模块用于对 **多份投标文件** 进行多维度相似度检测，帮助识别潜在围标串标行为（如文件雷同、目录相似、图片重复等）。可选择性上传一份招标文件作为白名单，过滤掉招标文件自身内容的影响。

**四维度检测**（并发执行）：

| 维度       | 检测手段                                                     | 输出形式                |
| ---------- | ------------------------------------------------------------ | ----------------------- |
| **元数据** | 提取 docx/PDF 的文件属性（作者、创建时间、修改时间、公司、最后保存者等） | 属性对比表，异常项高亮  |
| **目录**   | 提取各文件的章节标题结构（支持显式目录块、Markdown 标题、语义标题） | 重复标题组 + 相似度矩阵 |
| **正文**   | 分句后规范化（去停用词、标点归一），去重句群                 | 跨文件重复句子列表      |
| **图片**   | 提取所有图片的 SHA-256 哈希值，比较完全相同图片              | 图片哈希重复列表        |

### 3.2 用户故事

| 编号  | 用户角色 | 故事                                                       | 验收标准                                       |
| ----- | -------- | ---------------------------------------------------------- | ---------------------------------------------- |
| DC-01 | 投标专员 | 上传多份投标文件（2~10 份），系统自动启动四维度分析        | 四维度并发执行，进度实时反馈                   |
| DC-02 | 投标专员 | 可选择性上传招标文件，系统将其内容作为白名单过滤           | 招标文件内容不参与重复判定，仅用于排除公共部分 |
| DC-03 | 合规经理 | 查看目录相似度矩阵（两两对比），识别高度相似章节           | 矩阵用颜色标识相似度等级（红/黄/绿）           |
| DC-04 | 合规经理 | 查看正文重复句子列表，区分“完全相同”和“高度相似”           | 分组展示，并标注来源文件                       |
| DC-05 | 投标专员 | 系统对图片进行哈希比对，识别完全相同图片                   | 列出重复图片及所在文件                         |
| DC-06 | 系统     | 对同一组文件的相同四维度分析结果生成唯一签名，避免重复计算 | 签名一致时直接返回缓存结果                     |

### 3.3 交互流程（两步）

```
Step 1：选择文件
   ├─ 上传 2~10 份投标文件（.docx/.pdf）
   ├─ 可选上传招标文件（作为白名单）
   └─ 点击“开始查重”

Step 2：结果展示（四个 Tab）
   ├─ 元数据：表格列出各文件的作者、创建时间、修改时间、公司等 → 异常项标红/橙
   ├─ 目录：显示重复的目录标题组 + 两两相似度矩阵（热力图）
   ├─ 正文：按重复句子分组，显示句子原文、来源文件、位置
   ├─ 图片：列出重复图片哈希值及对应文件
   └─ 支持导出查重报告（.docx / .xlsx）
```

### 3.4 技术实现要点

#### 3.4.1 正文提取与规范化

- 使用 `python-docx` / `pypdf` 提取全文文本。
- 移除图片占位符（如 `![]()`、`<img>`）。
- 结构化分句：对 HTML 表格按单元格拆分，对 Markdown 管道表按行列拆分，普通文本按句号/分号/换行分句。
- 规范化：去除标点符号、数字、空白，统一大小写，去除停用词（可选），得到“句子指纹”。

#### 3.4.2 招标文件白名单过滤

若上传了招标文件，则将其所有句子加入白名单 Set。在正文重复检测时，忽略与白名单完全匹配的句子，避免招标文件自带内容干扰判断。

#### 3.4.3 目录提取（纯程序，无 AI）

- 优先读取 Word 中的显式目录（`TOC` 字段）或 PDF 中的书签。
- 若无，则根据 Markdown 标题（`#` `##`）或文档中“第X章”等语义模式提取层级标题。
- 对提取出的标题列表，两两比较 Jaccard 相似度（按词）或编辑距离，生成相似度矩阵。

#### 3.4.4 正文重复检测

- 将每个文件的分句结果，构建一个全局句子 → 文件 ID 列表的倒排索引。
- 对每个句子，若出现次数 > 1，则记录为重复组。
- 同时支持“高度相似”检测：对未完全相同的句子，使用 MinHash/LSH 或简单 Jaccard 相似度，设置阈值（如 >0.8）归为一组。

#### 3.4.5 图片哈希

- 解析 Markdown/HTML 图片语法，提取图片源路径（或内联 base64）。
- 对每个图片，读取其字节数据，计算 SHA-256 哈希。
- 按哈希值分组，输出重复组。

#### 3.4.6 并发执行

启动检查后，**正文内容提取**与 **元数据提取** 先并发完成；正文提取完成后，**目录/正文/图片** 三维度并发分析。全部维度成功或部分失败后，汇总结果。

#### 3.4.7 签名机制

对同一组文件（按文件 ID 排序 + 招标文件 ID），生成唯一签名（`createSignature`，基于文件路径、修改时间等）。若签名一致且历史分析状态为 success，则直接复用上次结果，避免重复计算。

### 3.5 数据模型（补充）

```sql

CREATE TABLE duplicate_checks (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    file_ids JSON,                              -- 参与查重的文件 ID 列表
    tender_file_id INTEGER,                     -- 招标文件 ID（可选）
    signature TEXT UNIQUE,                      -- 唯一签名
    status TEXT,                                -- running / completed / failed
    results JSON,                               -- 四维度结果
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

| 方法   | 路径                                     | 说明                       |
| ------ | ---------------------------------------- | -------------------------- |
| `POST` | `/api/duplicate/start`                   | 启动查重任务               |

## 四、知识库（Knowledge Base）

### 4.1 功能概述

知识库模块将企业历史标书、技术方案、施工组织设计等文档转化为 **结构化知识条目**（标题 + 摘要 + 正文），供编写新方案时检索引用。知识库是用户的 **长期资产**，数据持久存储在本地 SQLite 中，支持跨项目复用。

**核心能力**：
- 文档上传 → 自动切块 → AI 提取候选知识条目 → 人工审核（或自动通过） → 入库
- 知识条目在正文生成阶段被检索，作为上下文素材注入 AI 提示词
- 支持目录增强（Step03）和正文编排（Step04）两个集成点

### 4.2 用户故事

| 编号  | 用户角色   | 故事                                                         | 验收标准                                         |
| ----- | ---------- | ------------------------------------------------------------ | ------------------------------------------------ |
| KB-01 | 技术负责人 | 上传历史标书（.docx/.pdf），系统自动解析为知识条目           | 支持批量上传，解析进度可见                       |
| KB-02 | 技术负责人 | 系统自动将文档切块、去重、合并，并 AI 提取候选标题/摘要      | 提取结果覆盖率高，无价值片段被筛除               |
| KB-03 | 技术负责人 | 浏览、编辑、删除知识条目，支持全文搜索                       | 搜索命中标题或正文关键词                         |
| KB-04 | 投标专员   | 在编写新方案时，系统自动从知识库检索相关条目，并注入生成上下文 | 目录生成时补充缺失的三级目录，正文生成时提供素材 |
| KB-05 | 系统管理员 | 从旧版 `index.json` 迁移数据到新版 SQLite 结构               | 迁移过程可控，只迁移成功文档，保留源文件         |
| KB-06 | 投标专员   | 知识库中的条目可按行业/分类筛选，支持标签管理                | 分类与平台 12 行业知识库对应                     |

### 4.3 知识库流水线（完整处理流程）

知识库模块采用 **幂等流水线** 设计，每步状态可追踪，支持断点续传。每一步处理结果均落盘，避免重复计算。

```
文档上传（原始文件）
    │
    ▼ 1. copy_source
复制原件到知识库存储目录（保留原始文件名）
    │
    ▼ 2. convert_markdown
将文档转为 Markdown 格式（使用 python-docx + pandoc 或纯文本提取）
    │
    ▼ 3. build_blocks
切块 + 语义合并 + 筛除无价值块（页码、目录、封面、签字页、重复头尾）
    │
    ▼ 4. extract_first_items
AI 首次提取候选知识条目（标题 + 摘要 + 正文）
    │
    ▼ 5. extract_supplement_items
AI 补充提取（对遗漏部分进行二次扫描）
    │
    ▼ 6. merge_candidates
合并去重（按语义相似度合并），生成最终候选列表
    │
    ▼ 7. match_batches
按批次（batchSize）分批 AI 匹配——将候选条目与原文档块对应，补全正文内容
    │   （采用纯 user 多消息优化 prompt cache，固定全文前缀 + 变量批次）
    │
    ▼ 8. recover_missing
最多两轮补漏：检查未匹配的块，重新尝试匹配
    │
    ▼ 9. save_result
程序回填完整正文，生成覆盖率报告，写入知识库表
    │
    ▼ 完成（status = success）
```

#### 4.3.1 各阶段说明

- **切块与筛选**：按标题、段落分隔，合并过短块；利用规则（如页码模式、目录关键词）剔除无效块。
- **AI 提取候选**：使用 `collect_json_response` 确保输出 JSON 格式，每个候选含 `title`、`summary`、`keywords`。
- **AI 匹配**：为减少 token 消耗，采用“固定全文前缀（缓存命中）+ 批次变量”的 Prompt Cache 优化策略，实测成本降低 ~90%。
- **覆盖率报告**：统计成功匹配的块数 / 总块数，帮助用户评估导入质量。

### 4.4 知识库应用场景集成

#### 4.4.1 目录生成增强（Step03）

在 AI 生成目录时，系统从知识库检索与当前项目行业、评分点相关的知识条目，将其标题/摘要作为补充素材，提示模型可以参考这些条目来完善三级目录结构。具体采用 **additions-only** 模式：只补充缺失的三级目录，不修改已有目录结构。

#### 4.4.2 正文生成（Step04）

- **编排阶段**：AI 判断每个章节是否需要引用知识库，并推荐相关知识条目 ID（轻量引用，只传 `id` + `title` + `resume`）。
- **生成阶段**：将选中知识条目的完整正文（`content`）嵌入到用户提示词中，作为参考素材，供 AI 润色和改写（注意：不直接复制，而是参考后用自己的语言重写）。

#### 4.4.3 知识库检索

提供检索接口，支持关键词搜索、按行业/标签筛选，可手动选择知识条目插入到当前章节的上下文中。

### 4.5 数据模型

```sql
-- 知识库文档（原始文件）
CREATE TABLE knowledge_documents (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    filename TEXT NOT NULL,
    file_path TEXT NOT NULL,
    file_type TEXT,                             -- docx / pdf
    status TEXT DEFAULT 'pending',              -- pending / copying / converting / extracting / matching / recovering / saving / success / error
    step_log JSON,                              -- 每步执行记录
    markdown_path TEXT,                         -- 转换后的 markdown 文件路径
    blocks JSON,                                -- 切块结果 [{index, text, type}]
    candidates JSON,                            -- 候选条目列表
    match_result JSON,                          -- 匹配结果
    coverage REAL,                              -- 覆盖率 (0~1)
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 知识条目（最终入库）
CREATE TABLE knowledge_items (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    summary TEXT,
    content TEXT NOT NULL,                      -- 完整的正文片段
    keywords TEXT,                              -- JSON 数组
    industry TEXT,                              -- 所属行业
    tags JSON,                                  -- 自定义标签
    source_doc_id INTEGER,                      -- 来源文档 ID
    source_ref TEXT,                            -- 原文位置引用
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 知识库使用记录（用于统计）
CREATE TABLE knowledge_usage (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    item_id INTEGER,
    project_id INTEGER,
    section_id INTEGER,                         -- 被引用的章节
    used_in TEXT,                               -- outline_enhance / content_generation
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 4.6 迁移兼容（从旧版 JSON 升级）

平台内置迁移工具，检测到旧版 `data/knowledge/index.json` 存在时，弹出对话框提示用户确认迁移。迁移规则：
- 只迁移 `status=success` 的文档
- 校验迁移后关键字段（如 `title`, `content`）非空，条目数一致
- 迁移完成后，删除旧 JSON，保留原始文件（`source/` 和 `content.md`）
