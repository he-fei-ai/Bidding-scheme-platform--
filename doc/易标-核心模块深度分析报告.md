# 易标投标工具箱 — 核心模块深度分析报告

> 本文档是对"易标投标工具箱 v2.14.3"核心工作流程、提示词体系、路由架构和代码逻辑的深度探索结果，可作为同类软件开发的参考标准。

---

## 一、软件总览

**易标投标工具箱**是一款基于 Electron + Vite + React + TypeScript 的桌面客户端应用，专为标书编写场景设计。核心能力涵盖：招标文件解析、技术方案目录生成、正文自动生成、DOCX 导出、知识库管理、标书查重、废标项检查等功能。

### 技术栈

| 层次 | 技术选型 |
|------|---------|
| 桌面框架 | Electron（Main/Preload/Renderer 三进程模型） |
| 前端框架 | React 18 + TypeScript + Vite |
| UI 组件 | Radix UI（无样式基础组件）+ 全局 CSS |
| 数据存储 | SQLite（better-sqlite3）+ localStorage + 文件系统 |
| AI 服务 | OpenAI 兼容 API（SSE 流式 + JSON 容错修复链路） |
| 文档解析 | 本地引擎（mammoth/pdf-parse/pdfjs-dist）+ MinerU 云端 API |
| DOCX 导出 | docx 库 + unified/remark 生态（Markdown → AST → Docx Blocks） |
| 埋点统计 | Cloudflare Workers（独立 Analytics 服务） |

### 架构边界

```
┌─────────────────────────────────────────────────────────┐
│                    Electron 桌面客户端                    │
│                                                         │
│  ┌──────────────┐    ┌──────────────┐    ┌───────────┐ │
│  │   Renderer   │◄──►│   Preload    │◄──►│   Main    │ │
│  │ (React/TS)   │    │(contextBridge)│    │ (.cjs)    │ │
│  │ ESM 模块      │    │ 安全 API 桥接 │    │ CJS 模块   │ │
│  └──────────────┘    └──────────────┘    └───────────┘ │
│       │                       │                │        │
│       │  window.yibiao         │   IPC 通道      │  本地文件│
│       │  唯一入口              │   请求-响应     │  SQLite │
│       └───────────────────────┴────────────────┴────────┘ │
│                                             │            │
│                                     本地磁盘存储                    │
│                                     userData/workspace/                   │
└─────────────────────────────────────────────────────────┘
```

**关键原则：**
- Renderer 不直接访问 Node API（`fs`、`path`、`ipcRenderer`），只通过 `window.yibiao` 调用
- IPC 文件只做通道注册和参数转发，业务逻辑全部在 `electron/services/*.cjs`
- 耗时任务（AI 请求、文件解析、导出转换）全部在 Electron Main 后台执行
- Renderer 只负责启动任务、订阅事件、读取 Store 快照和展示状态

## 二、文件解析模块

### 2.1 模块职责

将各类文档（PDF、Word、DOCX、Markdown 等）转换为统一的 Markdown 格式，供后续标书分析、大纲生成、内容编写使用。

### 2.2 支持的文档格式

| 扩展名 | 本地解析 | MinerU-Agent | MinerU-精准 |
|-------|---------|-------------|------------|
| `.txt` | ✅ | ❌ | ❌ |
| `.md`, `.markdown` | ✅ | ❌ | ❌ |
| `.docx` | ✅ | ✅ | ✅ |
| `.pdf` | ✅ | ✅ | ✅ |
| `.doc`, `.wps` | ✅ (LibreOffice/COM 转 docx) | ✅ | ✅ |
| `.ppt`, `.pptx` | ❌ | ✅ | ✅ |
| `.xls`, `.xlsx` | ❌ | ✅ | ❌ |
| 图片 (png/jpg/bmp...) | ❌ | ✅ | ✅ |
| `.html` | ❌ | ❌ | ✅ |

### 2.3 解析器选择逻辑

```javascript
// 决策树
1. 读取用户配置 file_parser.provider
2. 如果配置的 provider 支持该扩展名 → 使用该 provider
3. 如果配置的 provider 不支持，但 local 支持 → fallback 到 local
4. 如果都不支持 → 返回 unsupported
```

默认 provider 为 `'local'`，可在设置页面切换为 `'mineru-agent-api'` 或 `'mineru-accurate-api'`。

### 2.5 本地解析引擎详情（doc2markdown/convert.mjs）

**格式检测**（按优先级）：
1. 读取文件头 8 字节自动识别
2. `%PDF-` 前缀 → PDF
3. `PK` (0x50 0x4b) → DOCX
4. `D0 CF 11 E0` → Legacy Word (.doc/.wps)
5. 后缀匹配 → Markdown/PDF/DOCX/Legacy

**各格式处理流程**：

| 格式 | 处理链 |
|------|--------|
| Markdown | chardet 编码检测 → iconv 解码 → BOM 去除 → 换行标准化 |
| DOCX | mammoth (DOCX→HTML) → cheerio 清理 → turndown (HTML→Markdown)，表格特殊保留 |
| PDF | pdf-parse（文字）+ pdfjs-dist（表格/图形），双引擎提取，去重和位置聚类 |
| Legacy Word | LibreOffice / WPS COM / Microsoft Word COM 先转为 .docx → 走 DOCX 流程 |

Legacy Word 转换后端优先级：
- `.wps` 文件：WPS COM → LibreOffice → Microsoft Word COM
- 其他 `.doc`：LibreOffice → WPS COM → Microsoft Word COM

### 2.6 图片资产系统

**协议**：`yibiao-asset://imported-images/{encodedBatchId}/{encodedFileName}`

**存储路径**：`userData/workspace/imported-images/{batchId}/image-NNNN.ext`

**图片源类型**：

| 来源 | 处理方式 |
|------|---------|
| Base64 data URI | 解码后保存 |
| 远程 URL (http/https) | fetch 下载（10 秒超时） |
| ZIP 内图片 (MinerU) | 从 AdmZip entries 提取 |
| 本地相对路径 | 安全路径校验后读取保存 |

### 2.7 解析结果存储

**文件系统**：
- 招标文件 Markdown：`workspace/technical-plan/tender.md`（原子写入：tmp → rename）
- 导入的图片资产：`workspace/imported-images/{batchId}/`

**SQLite 元数据**（`technical_plan_meta` 表）：

## 三、目录生成模块

### 3.1 模块定位

目录生成是技术方案工作流的 **Step 3**，位于"招标文件解析"(bid-analysis)之后、"全局事实设定"(global-facts)之前。

### 3.2 完整工作流程

```
Step 1: 提取技术评分大类 (extractRequirementGroups)
         ↓ 输出: [{ requirement_id: "R1", title: "", description: "", detail_points: [] }]
         
Step 2: 构建一级目录 (buildTopLevelOutlineFromGroups)
         ↓ 输出: [ { id: "1", title: R1.title, children: [...] } ]
         
Step 3: 并发生成二三级目录 (buildAligned → generateAlignedChildrenForGroup)
         ↓ 先串行第 1 个 → 等待 5 秒 → 并行处理剩余
         
Step 4: 知识库补目录 (enhanceOutlineWithKnowledgeAdditions) — 可选
         ↓ 同上并发模式
         
Step 5: 最终审核 (runFinalOutlineGate)
         ↓ AI 审核 → 未通过则切换到 OpenCode Agent 自主修复
         
Step 6: 保存目录 (workspaceStore.updateTechnicalPlan)
         ↓ 清除下游正文相关状态
```

### 3.3 两种工作模式

| 模式 | workflowKind | 触发条件 | 差异 |
|------|-------------|---------|------|
| 普通技术方案 | `technical-plan` | 仅上传招标文件 | 从技术评分要求提取目录 |
| 已有方案扩写 | `existing-plan-expansion` | 额外上传原方案 | 保留原方案目录 + AI 补充缺口 |

已有方案扩写的两条子路径：
- **`original-only`**：仅从原方案提取目录，不调用 AI 补充
- **`ai-complement`**：保留原方案一级目录前缀，AI 补充缺失的一级和二三级目录

### 3.4 目录数据结构

```typescript
interface OutlineItem {
  id: string;                    // "1", "1.1", "1.1.1"
  title: string;                 // 标题
  description: string;           // 描述/说明
  source_requirement_id?: string; // "R1", "R2"...
  source_requirement_title?: string;
  knowledge_item_ids?: string[];
  children?: OutlineItem[];        // 最多三级
  content?: string;                // 正文生成后填充
}

interface OutlineData {
  outline: OutlineItem[];    // 根目录数组（一级目录）
  project_name?: string;
  project_overview?: string;
}
```

### 3.5 目录编辑与正文持久化恢复

**保存原因分类**：

| 原因 | 含义 | 是否清除正文任务 |
|------|------|-----------------|
| `sort` | 同级目录排序 | 否 |
| `edit` | 编辑标题/描述 | 是 |
| `delete` | 删除节点及子树 | 是 |
| `add-root` | 添加一级目录 | 是 |
| `add-child` | 添加子目录 | 是 |
| `replace` | 全量替换（AI 生成） | 是 |

**正文内容持久化恢复机制**（最精妙的设计之一）：
1. 快照已有正文：`loadOutlinePersistenceSnapshot()`
2. ID 映射追踪节点变化（如排序后 `1.1` 变成 `1.2`）
3. 智能恢复：`buildOutlineWithPersistedContent()` 根据映射恢复对应节点的正文
4. 正文状态恢复：`restoreMappedContentRows()` 恢复 content_sections 和 content_plans

**技术评分大类提取 Prompt**：

## 四、正文生成模块

### 4.1 模块定位

正文生成是技术方案工作流的 **Step 5**（content-edit 阶段），是整个软件最复杂的模块，约 6300 行代码。

### 4.2 完整工作流程（9 个阶段）

```
Phase 1: planning（正文编排）
  → 为每个叶子小节调用 AI 决定：表格/Mermaid/AI配图/知识库/事实变量/写作重点
  → 全局择优：表格上限分配、AI配图上限分配
  
Phase 2: restoring（原方案还原）— 仅 existing-plan-expansion 模式
  → AI 判断原方案段落归属到哪个叶子小节
  → 直接重建已有还原的小节
  
Phase 3: 最低字数采样 + 目录扩展
  → 采样 3 个小节预估字数
  → 若不足目标字数的 80%，执行最多 3 轮补目录
  
Phase 4: generating（正文生成）
  → 带缓存预热的并发正文生成（先 1 个 → 等 5 秒 → 并发 N 个）
  
Phase 5: expanding（最低字数兜底扩写）
  → 对字数最少的章节进行 insert/replace 局部扩写
  → 直到达到 minimumWords
  
Phase 6: original-auditing（原方案覆盖审计）— 仅 expansion 模式
  → 检查已还原小节是否保留了原方案实质内容
  → AI JSON patch 修复 或 OpenCode Agent 自主修复
  
Phase 7: auditing（全文一致性审计）
  → 按 30 万字分组，审计正文与事实变量的冲突
  → AI JSON patch 修复 或 OpenCode Agent 自主修复
  
Phase 8: table-cleaning（去表格）— 当 tableRequirement='none' 时
  → AI 将表格块转换为普通文字描述
  
Phase 9: illustrating（配图）
  → AI 生图: 并发 2
  → Mermaid: 并发 5，含最多 3 轮自动修复
```

### 4.3 并发控制策略

| 资源类型 | 默认并发数 | 配置来源 |
|---------|----------|---------|
| 正文文本生成 | 10 | `aiConfig.concurrency_limit` |
| AI 生图 | 2 | `aiConfig.image_model.concurrency_limit` |
| Mermaid 图 | 5 | 本地常量 `MERMAID_IMAGE_CONCURRENCY` |

**WorkerPool 架构**：
```javascript

```

### 4.4 暂停/恢复机制

**三层暂停**：
1. **任务级暂停**：`taskControl.isPauseRequested()` → 当前阶段完成后停止
2. **队列级暂停**：`AI_QUEUE_SCOPE_PAUSED` → 丢弃排队中未发出的请求
3. **持久化暂停**：暂停时将 sections/plans/runtime 全部落盘，下次启动自动恢复

**恢复流程**：
```javascript
// Resume 时从 previousState 加载 contentGenerationRuntime
const resume = Boolean(payload.resume);
const storedPlan = resume ? (previousState || {}) : (workspaceStore.loadTechnicalPlan() || {});
let contentRuntime = normalizeContentGenerationRuntime(resume ? storedPlan.contentGenerationRuntime : {});
```

## 五、DOCX 导出模块

### 5.1 模块职责

将技术方案正文（Markdown 格式的目录树）转换为 Word 文档（`.docx`），支持自定义页面设置、标题样式、编号格式、页脚等。

### 5.2 完整调用链路

```
Renderer: TechnicalPlanHome.exportWord()
  │  1. 读取最新 export_format 配置
  │  2. 订阅进度回调 onWordExportProgress(callback)
  │  3. window.yibiao.export.exportWord(payload)
  ▼
preload.cjs: ipcRenderer.invoke('export:word', payload)
  ▼
exportIpc.cjs: ipcMain.handle('export:word')
  │  sendProgress = (progress) => event.sender.send('export:word-progress', ...)
  ▼
exportService.exportWord(payload, onProgress)
  │  buildDocxResult() → parseMarkdown() → markdownNodesToDocx() → Packer.toBuffer(doc)
  │  fs.writeFileSync(filePath, buffer)
  ▼
返回 { success, path, message, warnings }
```

### 5.3 Markdown → DOCX 转换流程

```
Markdown 文本
    │
    ├─ normalizeMarkdownTablesForDocx()  // 表格语法规范化
    │
    ├─ unified().use(remarkParse).use(remarkGfm).parse()  // MD → MDAST
    │
    ├─ markdownNodesToDocx(nodes, context)  // 核心遍历函数
    │     │
    │     ├─ heading → Paragraph (6 级标题样式)
    │     ├─ paragraph → Paragraph (inlineRuns 处理行内元素)
    │     ├─ list (ordered/bullet) → Paragraph[] with numbering (3 级嵌套)
    │     ├─ table → Table (计算列数、合并单元格、首行表头)
    │     ├─ blockquote → Paragraph (左蓝边框 + 浅灰背景)
    │     ├─ code (mermaid) → Paragraph with ImageRun (mermaid.ink API)
    │     ├─ code (other) → Paragraph (Consolas + 浅灰背景)
    │     ├─ html → cheerio 解析后分发
    │     └─ thematicBreak → 水平分割线
    │
    └─ Packer.toBuffer(doc)  // 生成 DOCX Buffer
```

### 5.4 行内元素渲染

```
text → TextRun
strong → TextRun(bold=true)
emphasis → TextRun(italics=true)
delete → TextRun(strike=true)
inlineCode → Consolas 字体 + 蓝色
link → ExternalHyperlink
image → ImageRun (异步加载)
break/<br> → TextRun(break=1)
html → cheerio 解析后 htmlInlineRuns()
```

### 5.5 图片和 Mermaid 图处理

**普通图片来源**：

| 来源类型 | 处理方式 |
|----------|---------|
| Data URL (`data:`) | Base64 解码 |
| yibiao-asset:// | 从 workspace 目录读取 |
| http(s):// | fetch 下载 |
| file:// 或绝对路径 | fs.readFileSync |
| 相对路径 | path.resolve + fs.readFileSync |

**图片处理流水线**：
```
loadImage(source) → normalizeImageForDocx(WebP→PNG) → imageSize() → clamp to 520px → new ImageRun()
```

**Mermaid 图转换**（通过 mermaid.ink 在线服务）：
```
mermaid 源代码 → JSON.stringify({code, theme:'default'}) → pako 压缩 → base64url 编码
→ https://mermaid.ink/img/pako:<encoded>?type=png&bgColor=!white
```
重试策略：最多 2 次重试，每次间隔 3 秒。

## 六、提示词（Prompts）系统

### 6.1 双层存储架构

| 层级 | 位置 | 职责 |
|------|------|------|
| Renderer 侧共享 prompt 库 | `src/shared/prompts/` | 通用 prompt，可被测试和复用 |
| Main 侧内嵌 prompt | `electron/services/*.cjs` | 业务特定 prompt，减少跨文件依赖 |

### 6.2 Prompt 构建模式

**统一消息格式**：
```typescript
interface ChatMessage {
  role: 'system' | 'user' | 'assistant';
  content: string;
}
```

**典型构建模式**：
```
模式 A（简单场景）:
  system: 角色定义 + 输出格式约束
  user:   输入数据

模式 B（多轮递进）:
  buildXxxAnalysisMessages():   第一轮 — 分析范围
  buildXxxInspectionMessages(): 第二轮 — 基于分析结果检查
  buildXxxFinalMessages():      第三轮 — 去重合并定稿
```

**关键特征**：
- system 消息仅用于角色定义
- user 消息承载全部数据
- 结构化指令嵌入（明确的 JSON 格式要求和字段约束）
- 不使用 assistant 角色（单向指令，无历史对话上下文）

### 6.3 Prompt 缓存优化策略

**三阶段预热模式**：
1. 首条串行：先生成第一个子任务，建立 prompt cache 基础
2. 等待 5 秒：`waitForPromptCacheWarmup()` 让 AI 服务商完成缓存预热
3. 并发执行：剩余子任务并行发出，共享同一个 prompt cache

**适用场景**：目录生成、知识库补目录、正文生成等所有并发 AI 调用阶段。

### 6.4 JSON 容错链路

```
collectJsonResponse()
  │
  ├─ 第 1 次: chatWithConfig() → parseJsonContent() → normalizer() → validator()
  │     └─ 失败 → repairJsonResponse() → 发送修复 prompt → 重试
  │
  ├─ 第 2 次: 同上
  │     └─ 失败 → 显示进度 "连续N次校验失败"
  │
  ├─ 第 3 次: 同上
  │     └─ 失败 → 抛出最终错误
  │
  └─ 全部失败 → 切换到 OpenCode Agent 自主修复
```

### 7.3 Preload 桥接

```javascript
// preload.cjs 使用 contextBridge.exposeInMainWorld
contextBridge.exposeInMainWorld('yibiao', {
  appName: '易标投标工具箱',
  platform: process.platform,
  getVersion: () => ipcRenderer.invoke('app:get-version'),
  
  // 请求-响应模式 (invoke)
  tasks: {
    startBidAnalysis: (payload) => ipcRenderer.invoke('tasks:start-bid-analysis', payload),
  },
  
  // 事件推送模式 (on + 取消订阅)
  tasks: {
    onTaskEvent: (callback) => {
      ipcRenderer.send('tasks:subscribe');  // 先注册 sender
      const listener = (_event, payload) => callback(payload);
      ipcRenderer.on('tasks:event', listener);
      return () => ipcRenderer.removeListener('tasks:event', listener);  // 返回取消函数
    },
  },
});
```

## 九、任务管理与并发控制

### 9.1 任务组锁策略

| 任务组 | 锁策略 | 说明 |
|--------|--------|------|
| `technical-plan` | `group-exclusive` | Step02/03/04/05 共用技术方案工作区，组内互斥 |
| `duplicate-check` | `group-exclusive` | 标书查重外层是一轮分析任务 |
| `rejection-check` | `group-exclusive` | 废标项解析和检查共用同一检查缓存 |
| `knowledge-base` | `scope-exclusive` | 按 documentId 加锁 |

### 9.2 后台任务约定

1. 所有耗时 AI、文件解析、批处理、生成、检查、导出转换必须在 Electron Main 后台任务中执行
2. Renderer 只负责启动任务、订阅事件、读取 Store 快照和展示状态
3. 页面卸载不能取消任务，也不能作为任务失败信号
4. 页面重新挂载后必须先读取 Store，再订阅任务事件
5. 如果 Store 中存在 running/pausing 状态但 Main 没有对应 active task，应标记为"上次任务未完成"

### 9.3 清空规则

- 重新生成某一步时，只清空该步骤旧结果和后续步骤结果，不清空前置输入
- 目录重新生成、编辑、添加或删除后，必须清空旧正文内容和正文生成缓存
- 清空动作应在 Main 侧任务确认启动后执行

## 十一、总结

本报告覆盖了易标投标工具箱的六大核心模块：

| 模块 | 核心文件 | 代码规模 | 关键设计 |
|------|---------|---------|---------|

| 正文生成 | `contentGenerationTask.cjs` | ~6300 行 | 9 阶段流水线、WorkerPool 并发、暂停恢复、字数兜底 |
| DOCX 导出 | `exportService.cjs` | ~1800 行 | Markdown AST 转换、自定义样式、Mermaid.ink API |

1. **职责分离清晰**：IPC 只转发、Service 写逻辑、UI 只做展示

3. **容错机制完善**：JSON 修复链路、Agent 自主修复、重试策略
4. **状态管理严谨**：Store 落盘、暂停恢复、事务保护
5. **可扩展性强**：模块化服务、插件化解析器、配置化导出样式
